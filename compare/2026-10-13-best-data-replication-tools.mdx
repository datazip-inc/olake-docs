<TLDR title='Key takeaways'>

"Replication" means four different jobs. You might want a standby copy for failover, a copy for reports, a copy in a data lake, or a one-time move to a new database.

Start with your database's own replication for a standby or read copy.

Reports in a warehouse point to Fivetran, Estuary, Artie, Airbyte or Google Datastream.

Iceberg tables on storage you control point to Debezium Server or [OLake Go](/docs/understanding/compatibility-catalogs/).

Big Oracle estates point to Oracle GoldenGate, Qlik Replicate or Striim, and a move into AWS points to AWS Database Migration Service (DMS).

- **Replication is NOT backup.** [PostgreSQL's docs](https://www.postgresql.org/docs/current/warm-standby.html) say restoring a backup takes much longer than failing over to a standby.
- **Two-way replication is hard.** [AWS DMS](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html) says its two-way mode has no conflict resolution, and [Oracle GoldenGate's FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html) warns of update conflicts and loops.

</TLDR>

## What data replication means

[AWS defines data replication](https://aws.amazon.com/what-is/data-replication/) as copying data from one location to another to keep several synchronized copies. In this post, "source" is where the data starts and "target" is the copy.

| Job | What it does | Keeps copy in step? | Typical use |
| --- | --- | --- | --- |
| Replication | Copies data and keeps the copy current | Yes, continuously or on a schedule | Standby, reports, lake |
| Backup | Saves a point-in-time copy to restore from | No, only at the time of the backup | Recovery after loss or error |
| Migration | Moves data once to a new system | Only until cutover | Changing database or cloud |
| ETL (extract, transform, load) | Copies data and reshapes it on the way | Depends on the tool | Building clean reporting tables |

### Full copy, incremental copy and change data capture

![Full copy resends every row, incremental copies changed rows, and change data capture reads each change from the log](/img/blog/2026/10/best-data-replication-tools-copy-methods.webp)

A full copy resends the whole table every run. An incremental copy asks only for rows changed since the last run, and that needs a "changed at" column that is updated on every edit.

Change data capture (CDC) reads the database's transaction log, which is the file where the database writes down every change in order. [AWS says](https://aws.amazon.com/what-is/data-replication/) log-based detection is preferred for databases because it is efficient and captures changes with low latency.

A "changed at" column can miss rows that were deleted for good, since a deleted row leaves no timestamp behind.

### Synchronous vs asynchronous

Synchronous means the source waits until the replicas confirm each write. [AWS says](https://aws.amazon.com/what-is/data-replication/) this suits mission-critical data but is sensitive to network delay.

Asynchronous means the source does not wait, but [PostgreSQL's docs](https://www.postgresql.org/docs/current/warm-standby.html) say transactions not yet shipped are lost if the primary fails badly.

### One-way or two-way

Most replication is one-way. The source takes the writes and the target is a read-only copy. Two-way replication lets both sides take writes, and that's where conflicts show up.

![One-way replication flows from source to copy; two-way needs loopback prevention and conflict rules so changes do not echo back](/img/blog/2026/10/best-data-replication-tools-one-vs-two-way.webp)

AWS DMS supports two-way replication on Oracle, SQL Server, MySQL, PostgreSQL and the two Aurora editions. Its [docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html) are blunt about the limits. It is not a full multi-master solution, it does not include conflict detection or resolution, and it suits data that is operationally segregated between the two nodes.

## The 12 data replication tools

### Built into your database

#### 1. Native database replication (PostgreSQL and MySQL): standby copies and read replicas

**At a glance**
- Method: The database's own log, shipped to another server
- Price: Included in the database. You pay for the servers.

[PostgreSQL's log-shipping standby](https://www.postgresql.org/docs/current/warm-standby.html) is a second server that's ready to take over if the primary fails. [MySQL's replication](https://dev.mysql.com/doc/refman/8.4/en/replication.html) (8.4 reference manual) copies from a source to one or more replicas, and it is asynchronous by default.

**Where it fits**

- No extra product to buy or run. [MySQL's replication manual](https://dev.mysql.com/doc/refman/8.4/en/replication.html) lists scale-out reads, running backups on a replica and analytics on a replica as benefits.
- MySQL also offers semisynchronous replication, where a commit on the source blocks until at least one replica acknowledges it, and delayed replication, where a replica deliberately lags by at least a set time ([MySQL 8.4 replication](https://dev.mysql.com/doc/refman/8.4/en/replication.html)).
- MySQL can replicate all databases, selected databases or selected tables within a database, depending on the configuration ([MySQL 8.4 replication](https://dev.mysql.com/doc/refman/8.4/en/replication.html)).
- PostgreSQL supports physical replication (byte by byte) and logical replication (per object, keyed on the replication identity, usually a primary key) at the same time ([PostgreSQL logical replication docs](https://www.postgresql.org/docs/current/logical-replication.html)).
- A PostgreSQL standby can also answer read-only queries, in which case it is called a hot standby ([warm standby docs](https://www.postgresql.org/docs/current/warm-standby.html)).

**Where it falls short**

- It copies between servers of the same database. PostgreSQL log shipping between different major release levels is in general not possible, and the hardware architecture must match, so a 32-bit to 64-bit copy will not work ([warm standby docs](https://www.postgresql.org/docs/current/warm-standby.html)) (checked Oct 2026).
- PostgreSQL's logical replication does not copy the database schema, DDL commands, sequence data or large objects, and it only replicates tables, so views and materialized views raise an error ([PostgreSQL logical replication restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html)) (checked Oct 2026).
- An unread replication slot, the bookmark PostgreSQL keeps for a reader, keeps log files on disk and can fill storage. The docs say slots persist across crashes and know nothing about their consumers, and a slot that is no longer needed should be dropped ([PostgreSQL logical decoding docs](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html)) (checked Oct 2026).
- Log shipping is asynchronous: transactions not yet shipped are lost if the primary suffers a catastrophic failure ([warm standby docs](https://www.postgresql.org/docs/current/warm-standby.html)) (checked Oct 2026).
- MySQL replication is asynchronous by default, so a replica can trail the source, and replicas do not need to stay connected ([MySQL 8.4 replication](https://dev.mysql.com/doc/refman/8.4/en/replication.html)).

### Enterprise platforms

#### 2. Oracle GoldenGate: Oracle estates and two-way setups

**At a glance**
- Method: Reads redo or transaction logs, the database's record of changes
- Price: Per OCPU (Oracle's compute unit) on Oracle Cloud, metered by the minute, per the [OCI billing page](https://docs.oracle.com/en/cloud/paas/goldengate-service/ocigg/ocpu-management-and-billing.html) (checked Oct 2026). We do not quote an on-premises licence price.

[Oracle's FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html) says GoldenGate captures, transforms and delivers transactional changes across systems in real time. You can run it in one-way, two-way and multi-directional setups.

**Where it fits**

- Oracle's FAQ lists Oracle, MySQL, PostgreSQL, SQL Server and Db2 (LUW, z/OS and i) among supported databases, with Amazon RDS, Aurora, Google Cloud and Azure database services, and also names Kafka, Snowflake and Apache Iceberg as targets ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)).
- It documents one-way, two-way and multi-directional setups, and advises conflict detection and resolution policies plus primary or unique keys on all replicated tables ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)).
- The FAQ says it supports change capture from MongoDB and MongoDB Atlas, and two-way replication between MongoDB databases ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)).
- For Oracle databases, the FAQ says GoldenGate 26ai supports 19c to 26ai and later, and GoldenGate 19c and 21c support 11.2.0.4 to 21c ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)) (checked Oct 2026).
- The FAQ says OCI GoldenGate is a fully managed service where Oracle handles backups, patching and upgrades, while GoldenGate on the OCI Marketplace is customer-managed. Self-managed deployments run on a VM, bare metal or Kubernetes ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)).

**Where it falls short**

- The [FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html) lists Apache Iceberg among targets, but the write details sit in the separate GoldenGate for Distributed Applications and Analytics (DAA) docs. [Oracle's Iceberg page](https://docs.oracle.com/en/database/goldengate/big-data/26/gadbd/apache-iceberg.html) lists Glue, Hadoop, Nessie, Polaris and REST catalogs but, in the version we read, states no write limits such as delete handling.
- It cannot capture from Salesforce, Teradata or TimesTen ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)) (checked Oct 2026).
- The FAQ warns that two-way setups need careful planning because they can cause update conflicts, replication loops, data divergence, latency sensitivity and operational complexity ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)).
- The FAQ says the Classic Architecture (administered with GGSCI) is de-supported in 26ai, and the other model is the REST-based Microservices Architecture ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)) (checked Oct 2026).
- On OCI, billing is per OCPU: you pick a base size of 1 to 24 OCPUs (1 to 8 with Auto-Scale, which reaches 3 times the base), and each hour is billed at the larger of the service size and the OCPUs actually consumed ([FAQ](https://docs.oracle.com/en/database/goldengate/core/26/coredoc/ogg-frequently-asked-questions.html)) (checked Oct 2026).
- We don't quote an on-premises dollar price.

**Check before you rely on it:** ask Oracle for a written quote for your own core count, because we do not quote an on-premises price.

#### 3. Qlik Replicate: mixed legacy and mainframe sources

**At a glance**
- Method: Log-based, which [Qlik calls "zero footprint"](https://www.qlik.com/us/products/qlik-replicate) (a vendor claim we did not test)
- Price: Capacity bands by data volume and job runs, no list prices, per the [Qlik pricing page](https://www.qlik.com/us/pricing/data-integration-products-pricing) (checked Oct 2026)

[Qlik's product page](https://www.qlik.com/us/products/qlik-replicate) lists Oracle, SQL Server, Db2, MySQL, PostgreSQL and mainframe sources.

Replicate is client-managed software, so you install it yourself on Windows Server or Linux ([Qlik support matrix](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/Support%20Matrix/supported_win_platforms.htm)).

**Where it fits**

- [Qlik's product page](https://www.qlik.com/us/products/qlik-replicate) lists mainframe sources and relational, warehouse and cloud-platform categories, and says Replicate works across hundreds of sources and targets.
- Replicate May 2026 added an IBM IMS source endpoint, an IBM Db2 for LUW target endpoint and a Cloudera Iceberg target, and added MariaDB 11.8 and Kafka 4.1 and 4.2 support ([Qlik May 2026 release notes](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/Release_Notes/features.htm)).
- Qlik's [release notes](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/Release_Notes/features.htm) say Qlik Open Lakehouse, a Qlik Talend Cloud feature, writes Iceberg tables. They describe a route where Replicate lands data in S3 and an Open Lakehouse pipeline onboards it into Iceberg tables ([release notes](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/Release_Notes/features.htm)).
- On an Oracle source, Replicate can read the redo logs with either Oracle LogMiner or Qlik's own Replicate Log Reader, and the docs list separate limits for each ([Qlik Oracle source limitations](https://help.qlik.com/en-US/replicate/May2026/Content/Global_Common/Content/SharedReplicateHDD/Oracle/OracleDB_source_limitations.htm)).

**Where it falls short**

- Prices are not published. The [Qlik pricing page](https://www.qlik.com/us/pricing/data-integration-products-pricing) shows a Contact Us button for each of its four Talend Cloud editions and says usage is measured by data volume moved, job runs and run time (checked Oct 2026).
- On the [pricing page](https://www.qlik.com/us/pricing/data-integration-products-pricing), log-based CDC first appears in the Standard edition list, not in Starter (checked Oct 2026).
- Oracle 21c cannot use LogMiner (Oracle's log-reading tool) with Replicate, only Qlik's own log reader. Also on 21c, immutable tables and blockchain tables are not supported, and CDC is not supported when a schema, table or column name is over 30 characters ([Oracle source limitations](https://help.qlik.com/en-US/replicate/May2026/Content/Global_Common/Content/SharedReplicateHDD/Oracle/OracleDB_source_limitations.htm)) (checked Oct 2026).
- Capturing changes from a pluggable database (PDB) with LogMiner is not supported, and Qlik does not recommend LogMiner on a RAC environment because of unpredictable behavior ([Oracle source limitations](https://help.qlik.com/en-US/replicate/May2026/Content/Global_Common/Content/SharedReplicateHDD/Oracle/OracleDB_source_limitations.htm)) (checked Oct 2026).
- Replicate's own Iceberg target in the May 2026 release is Cloudera Iceberg. Other Iceberg routes run through Qlik Open Lakehouse in Talend Cloud ([release notes](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/Release_Notes/features.htm)).

#### 4. Striim: Oracle-heavy streaming

**At a glance**
- Method: Log-based
- Price: Developer tier free up to 25 million events a month; Cloud and Platform say "contact us", per the [Striim pricing page](https://www.striim.com/pricing/) (checked Oct 2026)

For Oracle, [Striim's docs](https://www.striim.com/docs/en/oracle-database-cdc.html) give you two readers, Oracle Reader (LogMiner) and OJet. Both read Oracle 11g and higher.

**Where it fits**

- [Striim's Oracle docs](https://www.striim.com/docs/en/oracle-database-cdc.html) position Oracle Reader (LogMiner) for 20 to 80 GB of CDC data an hour and OJet for 150+ GB an hour. Both read Oracle 11g and higher, RAC and PDB/CDB. We have not tested either figure.
- Its GG Trail Reader can read existing Oracle GoldenGate trail files (versions 11g, 12c, 18.1 and 19.1) without extra LogMiner sessions ([Oracle docs](https://www.striim.com/docs/en/oracle-database-cdc.html)).
- Striim's docs say the [Iceberg Writer](https://www.striim.com/docs/en/iceberg-writer.html) has Merge mode, which mirrors source inserts, updates and deletes, and Append Only mode, which treats every operation as an insert. Its docs add schema evolution that propagates DDL changes, and at-least-once recovery.
- Its [docs](https://www.striim.com/docs/en/s3-tables-writer.html) say the S3 Tables Writer writes change and snapshot data into Iceberg tables in Amazon S3 Tables, using Amazon EMR for compute and either the S3 Tables catalog or AWS Glue, with DDL propagation for supported source changes.
- The [pricing page](https://www.striim.com/pricing/) shows a free Developer tier with trial access to premium, standard and 200+ preview connectors, and a Striim Cloud card that says "Pay only for the data you move" (checked Oct 2026).

**Where it falls short**

- The [Iceberg Writer docs](https://www.striim.com/docs/en/iceberg-writer.html) say the only supported data lake in this release is Google Cloud Storage. It also needs a Spark compute service and a catalog, and partitioned tables must be created by hand. Separate S3 Tables and GCP Lakehouse writers exist too (checked Oct 2026).
- The same page limits the catalog to Lakehouse, Nessie or Polaris, supports GCS only as the staging area, and recommends the Hadoop catalog only for development and testing ([Iceberg Writer](https://www.striim.com/docs/en/iceberg-writer.html)) (checked Oct 2026).
- It also says time source data types are written as strings in Iceberg, and recovery is at-least-once ([Iceberg Writer](https://www.striim.com/docs/en/iceberg-writer.html)).
- The [S3 Tables Writer](https://www.striim.com/docs/en/s3-tables-writer.html) requires lowercase table, namespace and column names, which breaks wildcard mappings against sources that use uppercase identifiers (checked Oct 2026).
- Cloud and Platform prices are not published: the [pricing page](https://www.striim.com/pricing/) shows "Contact us for pricing" for both, and Platform says "License the connectors you need" (checked Oct 2026).

#### 5. Fivetran High-Volume Agent (HVA): big enterprise databases, run by a vendor

**At a glance**
- Method: Log-based, through Fivetran's High-Volume Agent (HVA)
- Price: no separate HVA price found; HVA connectors need an Enterprise or Business Critical plan, per [Fivetran billing docs](https://fivetran.com/docs/core-concepts/usage-based-pricing/billing-and-plans) (checked Oct 2026)

[Fivetran's page on High-Volume Agent (HVA) connectors](https://fivetran.com/docs/connectors/databases/hva-connectors) lists Db2 for i, Oracle, SQL Server and other enterprise systems. They run in Fivetran's cloud (SaaS), or in Hybrid mode, where data is processed in your own network.

**Where it fits**

- The [HVA page](https://fivetran.com/docs/connectors/databases/hva-connectors) lists connectors for Db2 for i, Oracle, SQL Server, SAP ERP and three SAP ECC variants.
- Fivetran's [Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service) writes Parquet to your own S3, Azure Data Lake Storage or Google Cloud Storage account. Its docs say Fivetran always creates Iceberg metadata and manages the catalogs and maintenance operations.
- The same page lists optional catalog integrations, including Databricks Unity Catalog and Snowflake catalog-linked databases, and Lake Compute, a hosted DuckDB-based engine for running dbt transformations on the Iceberg tables ([Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service)).
- Per its maintenance notes, Fivetran deletes old snapshots once a day while always keeping at least the last 2, and moves orphan files to an `orphans` folder on the second and fourth Saturdays of each month ([Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service)).
- Fivetran's [usage docs](https://fivetran.com/docs/usage-based-pricing) say a row is counted once a month even if it syncs several times, and every new connection has 14 days of free usage (checked Oct 2026).

**Where it falls short**

- The price is not published. Billing is by [Monthly Active Rows](https://fivetran.com/docs/usage-based-pricing) (rows changed in a month), so you'll want to estimate your change volume first (checked Oct 2026).
- MAR keys are counted separately for each connection and table, so two connections that sync the same data count twice ([usage docs](https://fivetran.com/docs/usage-based-pricing)) (checked Oct 2026).
- The HVA Oracle and HVA SQL Server connectors need the Enterprise or Business Critical plan, and annual contracts have a $12,000 minimum, against a $5 minimum per connection on monthly pay-as-you-go ([billing docs](https://fivetran.com/docs/core-concepts/usage-based-pricing/billing-and-plans)) (checked Oct 2026).
- The Iceberg service does not support position deletes (a way to mark a row as removed by its place in a file), and its page lists only the SaaS deployment ([Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service)) (checked Oct 2026).
- On AWS, it does not support the S3 Glacier Flexible Retrieval, Glacier Deep Archive or Intelligent-Tiering archive tiers, and the Glue catalog allows one table per schema and table name combination in a Region ([Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service)) (checked Oct 2026).
- Iceberg reserves some column names (`_deleted`, `_file`, `_partition`, `_pos`, `_spec_id`, `file_path`, `pos`, `row`), so Fivetran prefixes them with a hash symbol before writing ([Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service)).

### Cloud-native services

#### 6. OLake Go: best for database changes into Iceberg on your own storage

<img src="/img/logo/olake-blue-with-text.svg" alt="OLake" height="32" style={{display: 'block', margin: '2px 0 14px'}} />

**At a glance**
- Method: Log-based change capture ([docs](/docs/))
- Price: Free licence ([Apache 2.0](https://github.com/datazip-inc/olake)); you pay for infrastructure and staff

OLake Go is open source. It reads [PostgreSQL](/docs/connectors/postgres/) logical replication, the [MySQL](/docs/connectors/mysql/) and MariaDB binlog, [MongoDB](/docs/connectors/mongodb/) change streams and [SQL Server](/docs/connectors/mssql/)'s native CDC, then writes Apache Iceberg or Parquet to storage you control.

Engines such as Snowflake, BigQuery, Redshift, Athena, Spark and Trino can read the Iceberg tables it writes, depending on the catalog and the delete format (the [engine compatibility page](/docs/understanding/compatibility-engines/) lists the conditions for each engine).

**What's good**

- It does the first copy and then change capture in one tool ([docs](/docs/)).
- It writes eleven Iceberg catalog types, and handles deletes with equality and positional deletes plus deletion vectors since v0.11.0 ([v0.11.0 release note](/docs/release/ingestion/v0.11.0/), [catalogs](/docs/understanding/compatibility-catalogs/)).
- It installs with Docker Compose and a web UI, a Docker command line, or Helm on Kubernetes ([Docker Compose](/docs/install/olake-ui/), [Docker CLI](/docs/install/docker-cli/) and [Kubernetes](/docs/install/kubernetes/) install pages).
- It follows schema changes: adds, drops and renames are detected, new source columns sync automatically when **Sync new columns automatically** is on, and widening type changes are documented ([schema evolution](/docs/features/schema/)).
- Full loads are split into parallel chunks, and syncs are stateful and resumable: after a crash, network failure or pause, an interrupted run resumes from its last checkpoint instead of starting over ([capabilities](/docs/)).
- It uses a two-phase commit for the Iceberg destination in full refresh, incremental and CDC runs (MongoDB, PostgreSQL, MySQL and SQL Server), tracking per-chunk commit status so syncs avoid inconsistencies and duplicate writes ([capabilities](/docs/)).

**Good to know**
- Change capture covers PostgreSQL, MySQL and MariaDB, MongoDB and SQL Server. Oracle, Db2 and S3 sources load by full refresh or incremental runs, and output is Apache Iceberg or Parquet on storage you choose ([docs](/docs/)).

**Bottom line:** Pick OLake Go if you run PostgreSQL, MySQL, MariaDB, MongoDB or SQL Server and want Iceberg tables on storage you control ([docs](/docs/understanding/compatibility-catalogs/)).

### Managed or vendor-run

#### 7. AWS DMS: moving databases into AWS

**At a glance**
- Method: Log-based
- Price: Replication instance hours or Serverless DCU hours, plus storage. [AWS's DMS pricing page](https://aws.amazon.com/dms/pricing/) lists no separate CDC fee for DMS tasks. For example, dms.t3.medium lists at $0.0745 an hour in us-east-1, on-demand, Single-AZ, per the [AWS price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AWSDatabaseMigrationSvc/current/us-east-1/index.json) (checked Oct 2026)

[AWS says](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html) DMS migrates databases with one-time moves or ongoing replication. A task can do a full load first and then switch to CDC. Under the hood, its [CDC docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html) say it reads Oracle with LogMiner or a binary reader, SQL Server through Microsoft's CDC or replication, MySQL binary logs, PostgreSQL logical slots and the MongoDB oplog.

**Where it fits**

- AWS's docs list two-way tasks on six engines: Oracle, SQL Server, MySQL, PostgreSQL and two Aurora editions ([CDC page](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html)).
- A task can be full load plus CDC, or CDC only for data already on the target ([CDC page](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html)).
- Since DMS 3.5.1, a CDC-only task that starts from an SCN or timestamp can pick up open transactions through the `openTransactionWindow` endpoint setting ([CDC page](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html)).
- For S3 targets, the docs say full-load and CDC files are written as CSV by default, with Apache Parquet as an option, and each CDC row starts with I, U or D to show how the row changed ([AWS DMS S3 target docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Target.S3.html)).
- AWS lists pricing options for on-demand instances, Serverless and Database Savings Plans, and says on-demand is hourly with no long-term commitment ([pricing page](https://aws.amazon.com/dms/pricing/)) (checked Oct 2026).

**Where it falls short**

- [AWS's CDC page](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html) says DMS ongoing replication has no service-level agreement for latency, that it does not provide real-time replication, and that latency can rise to several minutes or longer.
- The two-way mode does not include conflict detection or resolution. Loopback prevention tracks only DML, not DDL, and tasks that use it cannot commit changes in batches, so `BatchApplyEnabled` must be false ([CDC page](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html)) (checked Oct 2026).
- Views can be migrated in full-load tasks only. A CDC-only task or a full load that goes on to CDC includes tables only ([CDC page](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html)) (checked Oct 2026).
- PostgreSQL as a source does not support a custom CDC start time, and the CDC start point is fixed when the task is created, so a different one needs a new task. For Oracle, starting from an SCN or timestamp misses open transactions unless you use the 3.5.1 setting above ([CDC page](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html)) (checked Oct 2026).
- Apache Iceberg is not among the [target endpoints AWS's docs list for DMS](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Introduction.Targets.html), so Iceberg needs a separate step after the files land on S3 (checked Oct 2026).
- On an S3 target, DMS records no ALTER statement when a column is added, dropped or renamed and does not alter earlier records, and the docs say batch apply to S3 might lose data ([S3 target docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Target.S3.html)).

**At a glance**

- Price: Per GiB processed; backfill free for 500 GiB a month, then $0.40 per GiB; a free CDC tier of 100 GiB a month applies only to AlloyDB and Spanner sources, per the [Datastream pricing page](https://cloud.google.com/datastream/pricing) (checked Oct 2026)

Datastream is a CDC and replication service on Google Cloud. Its [sources](https://docs.cloud.google.com/datastream/docs/sources) are MySQL, Oracle, SQL Server and PostgreSQL, plus Spanner, MongoDB and Salesforce.

**Where it fits**

- The [pricing page](https://cloud.google.com/datastream/pricing) says there are no costs for running streams beyond data processed, an idle stream incurs no cost, and events Datastream reads but does not write to the destination are not counted (checked Oct 2026).

- For a SQL Server source, Google documents two methods. The transaction logs method needs fewer resources and retrieves data faster, while the change tables method has lower throughput but fewer limitations and supports encrypted tables ([Datastream SQL Server source docs](https://docs.cloud.google.com/datastream/docs/sources-sqlserver)) (checked Oct 2026).

**Where it falls short**

- The Iceberg destination is BigQuery-managed Iceberg tables in Cloud Storage, and [Google says](https://cloud.google.com/datastream/docs/destination-blmt) streaming to them is "supported only in the append-only write mode". Each table gets a `datastream_metadata` column, and in append-only mode its change type is INSERT for every row (checked Oct 2026).
- Setup needs the Cloud Storage bucket, BigQuery dataset and Datastream connection in the same region, and a BigQuery connection whose service account holds the `storage.admin` role on the bucket ([Iceberg destination](https://cloud.google.com/datastream/docs/destination-blmt)) (checked Oct 2026).

- For PostgreSQL, a stopped stream can leave log files on the source until the disk fills, so Google advises alerting on disk use ([Datastream PostgreSQL source docs](https://cloud.google.com/datastream/docs/sources-postgresql)).
- Google says a processed byte is an internal representation of the source data and for most use cases can be 2 to 5 times larger than the actual data ([pricing page](https://cloud.google.com/datastream/pricing)) (checked Oct 2026).
- The pricing page says the first 500 GB of backfill each month is free, while a footnote calls it a one-time 500 GiB credit per billing account, so confirm which applies ([pricing page](https://cloud.google.com/datastream/pricing)) (checked Oct 2026).
- On the SQL Server transaction logs method, Transparent Data Encryption is not supported, column-level-encrypted data is replaced with NULL, and columns added after a stream is created are not replicated. Streams are limited to 10,000 tables ([SQL Server source docs](https://docs.cloud.google.com/datastream/docs/sources-sqlserver)) (checked Oct 2026).

**Check before you rely on it:** ask Google for the expected delay on your source and size.

#### 9. Debezium: teams that already run Kafka

**At a glance**
- Method: Log-based
- Price: Free licence ([Apache 2.0](https://debezium.io/license/)); you pay for infrastructure and staff (checked Oct 2026)

This entry covers Debezium Server, which sends change events to the sinks listed in its [docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html), including Apache Iceberg.

**Where it fits**

- Its [docs](https://debezium.io/documentation/reference/stable/connectors/index.html) list connectors for MySQL, PostgreSQL, Oracle, MongoDB and more.
- The [Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html) list sinks including Kinesis, Pub/Sub, Pulsar, Redis, Kafka, RabbitMQ, Event Hubs, JDBC and Apache Iceberg.
- The Iceberg sink lists upsert and append modes, offset and schema history storage in Iceberg, and automatic schema evolution. New columns are added by default (`allow-field-addition` is true), and the default file format is Parquet ([Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)).
- When event and key schema information is enabled, destination Iceberg tables are created automatically at first startup ([Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)).
- Offsets can be kept in a file, memory, a JDBC database or Redis, which suits deployments without Kafka ([Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)).
- The [PostgreSQL connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) reads through logical decoding with the pgoutput or decoderbufs plug-in. It takes an initial consistent snapshot on first start and can run a blocking snapshot of one table on demand.

**Where it falls short**

- You run it. The Apache Iceberg sink is [community-maintained in a separate repository](https://debezium.io/documentation/reference/stable/operations/debezium-server.html), and each Debezium Server instance runs one connector (checked Oct 2026).
- The Iceberg sink's `upsert` setting is off by default, which means append-only mode. In upsert mode, deleted rows are kept and marked `__deleted=true` unless you turn `upsert-keep-deletes` off ([Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)) (checked Oct 2026).
- The docs say upsert mode and automatic primary key detection depend on the flattened event structure, and without it the connector runs only in a more limited append-only mode ([Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)) (checked Oct 2026).
- The Server page gives no list of supported Iceberg catalog types. It passes any `debezium.sink.iceberg.*` property to the Iceberg library ([Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)) (checked Oct 2026).
- On PostgreSQL, logical decoding does not report DDL changes, and a table without a primary key produces only create events under the default replica identity ([PostgreSQL connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)) (checked Oct 2026).
- Unchanged TOAST (large) column values outside the replica identity are left out of update events and replaced by a placeholder, and the pgoutput plug-in does not capture values for generated columns ([PostgreSQL connector](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)) (checked Oct 2026).

## What Happens When the Source Table Changes

| Tool or approach | What each tool's own docs say about schema changes |
| --- | --- |
| PostgreSQL logical replication | Does not copy schema changes ([docs](https://www.postgresql.org/docs/current/logical-replication-restrictions.html)) |
| Airbyte CDC | TRUNCATE and table-structure (ALTER) changes are not picked up from the logs ([docs](https://docs.airbyte.com/platform/understanding-airbyte/cdc)) |
| Fivetran | Its usage docs list a full table re-sync after a schema change, such as a new column, as historical Monthly Active Rows, and also list historical data from adding a column among free re-syncs; changed rows in the re-sync still count as paid ([Fivetran usage docs](https://fivetran.com/docs/usage-based-pricing)) (checked Oct 2026) |
| <img src="/img/logo/olake-blue.svg" alt="" height="20" style={{verticalAlign: 'middle', marginRight: '6px'}} />[OLake Go](/docs/features/schema/) | Adds, drops and renames are detected; widening type changes are documented |
| Striim Iceberg Writer | Supports schema evolution ([docs](https://www.striim.com/docs/en/iceberg-writer.html)) |
| Debezium Server with the community Iceberg sink | New fields and wider types work; full schema evolution does not, and a dropped column stays with nulls ([Debezium community Iceberg sink docs](https://raw.githubusercontent.com/memiiso/debezium-server-iceberg/master/docs/iceberg.md)) |

Sources are the links in the table (PostgreSQL, Airbyte, Fivetran, Striim and Debezium sink docs), and OLake Go's [schema page](/docs/features/schema/). Ask every vendor to show you what happens when you add a column and when you narrow a type.

## What to check before you choose

**1. The job.** Failover, reports, a lake and a migration all need different tools.

**2. The delay you will see.** Ask for the real lag. [AWS's docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html) say DMS has no service-level agreement for CDC latency, and [Airbyte runs on a schedule](https://docs.airbyte.com/platform/understanding-airbyte/cdc).

**3. The first copy.** Most tools copy existing rows first and then switch to changes. Test an interrupted snapshot on your biggest table.

**4. Deletes and schema changes.** Timestamp-based copies miss hard deletes, and the table above shows how schema changes are handled.

**5. Log growth on the source.** The [PostgreSQL](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html), [Datastream](https://cloud.google.com/datastream/docs/sources-postgresql) and [DMS](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Task.CDC.html) docs all warn that a stopped slot keeps log files on the source disk. Alert on disk use before you go live.

**6. How the copy is checked.** [AWS lists](https://aws.amazon.com/what-is/data-replication/) a checksum consistency check as the last stage of replication. Ask each vendor how it proves the two sides match.

### A small test for any finalist

We have not run this test on the other tools.

- Create a table with three rows: (1, "a"), (2, "b") and (3, "c"). Start the copy.
- Insert (4, "d"), update row 2 to "b1" and then to "b2", and delete row 3.
- Add a column, then stop the tool mid-run and restart it.
- Expected result on a current-state target: (1, "a"), (2, "b2") and (4, "d"), with no row 3 and no duplicates. Append-only targets, such as Datastream's Iceberg tables, show each change as its own record.
- Finally, read the bill after a week of real change volume.
