## How SQL Server CDC works, in plain terms

Change data capture means spotting the inserts, updates and deletes in a database and sending only those on. In SQL Server, [Microsoft's CDC docs](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) say the source of change data is the transaction log, the file where the database records every change in order.

A job called the capture job reads that log and writes the changes into **change tables**. Each tracked table gets a **capture instance**, which is one change table plus up to two query functions. By default the instance is named `schema_table`, and its change table gets `_CT` added, [per Microsoft](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server).

Every change row carries a log sequence number (LSN) and an operation code. 1 is a delete, 2 is an insert, 3 is the row before an update and 4 is the row after. So an update adds two rows, per [Microsoft's change table reference](https://learn.microsoft.com/en-us/sql/relational-databases/system-tables/cdc-capture-instance-ct-transact-sql).

Two details trip up first-time readers. Don't order by `__$seqval`; use `__$command_id`, which orders changes inside a transaction. And Microsoft recommends calling the `cdc.fn_cdc_get_all_changes_` and `cdc.fn_cdc_get_net_changes_` functions instead of reading the change tables directly ([reference](https://learn.microsoft.com/en-us/sql/relational-databases/system-tables/cdc-capture-instance-ct-transact-sql)).

Two SQL Server Agent jobs do the work, and their defaults matter. [Microsoft's docs](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) say the capture job runs continuously, handles up to 1,000 transactions per scan and waits 5 seconds between scans. The cleanup job runs daily at 2 A.M. and keeps entries for 4,320 minutes (3 days) (checked Oct 2026).

## CDC or change tracking? Your first choice

SQL Server ships two built-in ways to find changed rows. [Microsoft's comparison page](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/track-data-changes-sql-server) says change data capture reads the log after the fact and keeps history, while change tracking records changes as you write and keeps no history.

Change tracking notes that a row changed and gives its primary key (the column that uniquely identifies each row), but not the changed values. That's fine for the latest state, but no use for history.

Your edition can settle things fast. [Microsoft's editions table](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17) lists change data capture as Yes for Enterprise and Standard, and No for Express (checked Oct 2026). Attaching a CDC database, or restoring it with the `KEEP_CDC` option, on an edition without CDC is blocked ([Microsoft](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/track-data-changes-sql-server)).

![CDC keeps values and history on Standard or Enterprise; change tracking keeps only row keys and runs on Express](/img/blog/2026/10/sql-server-cdc-tools-cdc-vs-change-tracking.webp)

Azure SQL Database plays by different rules. [Microsoft says](https://learn.microsoft.com/en-us/azure/azure-sql/database/change-data-capture-overview?view=azuresql) a scheduler replaces the Agent jobs, and databases on the Database Transaction Unit (DTU) model need tier S3 or higher (checked Oct 2026).

## How to turn CDC on

It's two commands, but the permissions differ. Per [Microsoft's enable guide](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/enable-and-disable-change-data-capture-sql-server), `sysadmin` is required to enable CDC for a database, and a `db_owner` can then enable each table.

```sql
USE MyDB;
EXEC sys.sp_cdc_enable_db;
EXEC sys.sp_cdc_enable_table
  @source_schema = N'dbo', @source_name = N'MyTable',
  @role_name = NULL, @supports_net_changes = 1;
```

Per the [same guide](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/enable-and-disable-change-data-capture-sql-server), CDC needs exclusive use of a schema and a user both named `cdc`, so enabling fails if you already have either. Net changes queries need a primary key or unique index on the table. A `@role_name` of NULL (no value) turns off the access role.

On Amazon Relational Database Service (RDS), per its [CDC guide](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.SQLServer.CommonDBATasks.CDC.html), you run `msdb.dbo.rds_cdc_enable_db` instead. AWS also says snapshot and point-in-time restores disable CDC and remove its metadata (checked Oct 2026).

## The 11 best SQL Server CDC tools

### Built into SQL Server

#### 1. Native SQL Server CDC: best when the consumer is your own code

**At a glance**

- Reads SQL Server through: Agent jobs and change tables
- Lands data in: nowhere, you query it
- Price: part of the SQL Server editions that include it, which [Microsoft's editions table](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17) (checked Oct 2026) lists as Enterprise and Standard

Native CDC is the base layer under most tools below, so it's worth knowing on its own. [Microsoft's docs](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) name the query functions that return changes over a range of LSNs.

**What's good**

- It needs no extra software and keeps history, with the values before and after each update, per [Microsoft's change table reference](https://learn.microsoft.com/en-us/sql/relational-databases/system-tables/cdc-capture-instance-ct-transact-sql).
- [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) stopping the capture job loses no change data. It only pauses log scanning.
- Setting `@supports_net_changes` to 1 also generates a net changes function for the capture instance, and [Microsoft's enable guide](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/enable-and-disable-change-data-capture-sql-server) says that needs a primary key or unique index on the table.
- If an existing column changes data type, [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) the change is propagated to the change table.
- On Amazon RDS, once you run `msdb.dbo.rds_cdc_enable_db`, [AWS says](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.SQLServer.CommonDBATasks.CDC.html) any `db_owner` of the database can enable or disable CDC on its tables.

**Where it falls short**

- It only fills change tables ([Microsoft](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server)), so you still need something to move the rows.
- Even in simple recovery mode, [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) the log truncation point doesn't advance until captured changes are gathered, and `CHECKPOINT` won't truncate the log if the capture process isn't running while changes wait to be gathered. So a stopped capture job makes the log grow.
- [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) both capture methods need SQL Server Agent running, and its [editions table](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17) lists change data capture as Yes for Enterprise and Standard and No for Express (checked Oct 2026).
- Ask for a range that starts before the oldest kept change and [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) there could be missing change data from aggressive cleanup. A range outside the valid window makes the query functions fail.
- New columns are ignored until you create a second capture instance, and [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sys-sp-cdc-enable-table-transact-sql) a table can have at most two at once (checked Oct 2026).
- In a capture instance, [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/system-tables/cdc-capture-instance-ct-transact-sql) computed columns always have a value of NULL, and by default a captured column can take at most 65,536 bytes (64 KB) in one INSERT, UPDATE, WRITETEXT or UPDATETEXT statement (checked Oct 2026).

### Run it yourself

#### 2. Debezium: best for teams that already run Kafka

**At a glance**

- Reads SQL Server through: CDC change tables
- Lands data in: Kafka topics, one per table
- Price: free licence, per the [Debezium licence page](https://debezium.io/license/) (checked Oct 2026); you pay for servers and staff

Debezium is an open-source CDC engine. Its [SQL Server connector docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) say it is based on the CDC feature in SQL Server 2016 Service Pack 1 and later, Standard or Enterprise edition (checked Oct 2026).

**What's good**

- It takes a consistent snapshot first, then streams changes and picks up from the last log position after a restart ([docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html)).
- Incremental snapshots copy a table in chunks (1,024 rows by default), and the [SQL Server docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) say they run alongside streaming and can resume after an interruption without losing data (checked Oct 2026).
- The [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) say it can capture from an Always On read-only replica, though CDC must still be enabled on the primary node.
- The [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) cover tuning the SQL Server capture job: a higher `pollinginterval` lowers the load on the database host and raises latency.
- The [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) say its schema history provides the table structure in effect when a change event occurs.

**Where it falls short**

- Offsets are saved on a schedule, so after an outage the [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) warn of duplicate events, so your loads must cope with repeats.
- The [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) say SQL Server CDC isn't designed to store a complete history of changes, so the connector takes a snapshot to set a baseline.
- A table whose schema wasn't in the initial snapshot fails with a missing schema error. The documented fix starts with removing the schema history topic and clearing Kafka Connect offsets, and the [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) say removing offsets should be done only by advanced users.
- The [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) (checked Oct 2026) say it doesn't support schema changes while an incremental snapshot is running, and changing a primary key during one can cause incorrect results.
- Incremental snapshots need the connector to have permission to write to the signaling table ([docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html)).
- `tasks.max` defaults to 1, and the [docs](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html) say it can be raised to at most the number of entries in `database.names` (checked Oct 2026).

### Managed or vendor-run

#### 3. Fivetran: best for teams that want a vendor to run SQL Server loads

**At a glance**

- Reads SQL Server through: change tracking, CDC, Binary Log Reader or Teleport Sync
- Lands data in: warehouses; Apache Iceberg through its [Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service)
- Price: [usage-based, billed on monthly active rows](https://fivetran.com/docs/usage-based-pricing) (checked Oct 2026), so the bill moves with how many rows change

Fivetran's [SQL Server connector docs](https://fivetran.com/docs/connectors/databases/sql-server) list four ways to find changes. Teleport Sync is the odd one out, because it skips SQL Server's change features and instead scans tables and compares row hashes between syncs. If a table has both change tracking and CDC on, Fivetran uses CDC.

**What's good**

- Its [docs](https://fivetran.com/docs/connectors/databases/sql-server) (checked Oct 2026) list four SQL Server methods and point to Teleport Sync when change tracking or CDC can't be enabled.
- Its [connector docs](https://fivetran.com/docs/connectors/databases/sql-server) cover SQL Server 2012 to 2025, with Binary Log Reader on 2016 to 2025 only (checked Oct 2026).
- Its [docs](https://fivetran.com/docs/connectors/databases/sql-server) say CDC data can be read from secondary replicas in an Always On availability group, but SQL Server doesn't allow CDC setup on a secondary, so all CDC setup happens on the primary node.
- With CDC, its [docs](https://fivetran.com/docs/connectors/databases/sql-server) say column type changes propagate automatically, and extra permissions let CDC track DDL changes without re-syncing the modified table.
- For change tracking, its [docs](https://fivetran.com/docs/connectors/databases/sql-server) say Fivetran detects when it couldn't process changes before they were deleted from the change table and triggers a re-sync of that table.
- Its [docs](https://fivetran.com/docs/connectors/databases/sql-server) say it supports the SaaS and Hybrid deployment models for all SQL Server implementations, and Hybrid needs an Enterprise or Business Critical plan (checked Oct 2026).

**Where it falls short**

- With CDC, Fivetran syncs only tables with a single capture instance, so a new column means a new instance and removing the old one ([setup guide](https://fivetran.com/docs/connectors/databases/sql-server/setup-guide) (checked Oct 2026)).
- Change tracking can't sync tables without a primary key or run on a replica ([docs](https://fivetran.com/docs/connectors/databases/sql-server) (checked Oct 2026)).
- With CDC, its [docs](https://fivetran.com/docs/connectors/databases/sql-server) say column type changes propagate but renamed columns, new tables and new columns do not.
- Iceberg goes through [Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service), a separate destination whose docs say it supports the SaaS deployment model (checked Oct 2026).
- [That page](https://fivetran.com/docs/destinations/managed-data-lake-service) also says Fivetran doesn't support position deletes for Iceberg tables, and on AWS the Glue catalog supports only one table per combination of schema and table names within a Region (checked Oct 2026).
- Under [usage-based pricing](https://fivetran.com/docs/usage-based-pricing), rollback syncs may fetch data from the previous month, and those past records count as new unique records toward monthly active rows for the current month (checked Oct 2026).

#### 4. Airbyte: best for self-run SQL Server loads on a schedule

**At a glance**

- Reads SQL Server through: CDC, in scheduled syncs
- Lands data in: warehouses and lakes; Apache Iceberg on S3 through its [S3 Data Lake destination](https://docs.airbyte.com/integrations/destinations/s3-data-lake)
- Price: [Core is free to self-host, Cloud is paid](https://airbyte.com/pricing) (checked Oct 2026)

[Airbyte's SQL Server docs](https://docs.airbyte.com/integrations/sources/mssql) say the connector uses SQL Server CDC with the transaction log, and CDC setup needs db_owner rights. Its CDC sync runs on a schedule, and [Airbyte's CDC docs](https://docs.airbyte.com/platform/understanding-airbyte/cdc) say it doesn't treat CDC sources as infinite streaming sources.

**What's good**

- Core is free to self-host under the Elastic License 2.0 (ELv2), which [Airbyte's licensing summary](https://airbyte.com/why-open-source) says is restricted only for resale as a hosted service (checked Oct 2026). Beside CDC, the connector also has full refresh and incremental modes.
- Its [SQL Server docs](https://docs.airbyte.com/integrations/sources/mssql) say the certified connector offers CDC using SQL Server's own CDC feature, for SQL Server 2016 Service Pack 1 and later (checked Oct 2026).
- Its [S3 Data Lake docs](https://docs.airbyte.com/integrations/destinations/s3-data-lake) say the connector writes Iceberg tables to S3 or S3-compatible storage using a REST, AWS Glue, Nessie or Polaris catalog, and that deduping is merge-on-read.
- The same [S3 Data Lake page](https://docs.airbyte.com/integrations/destinations/s3-data-lake) says it handles adding or removing a column, widening a column and changing the primary key. Because it never rewrites existing Iceberg data files, other schema changes are not handled.
- For truncate refreshes the [S3 Data Lake connector](https://docs.airbyte.com/integrations/destinations/s3-data-lake) writes to a staging branch and swaps it in at the end, so queries read the old version until then. It keeps the staging branch after a failed sync so a retry can recover.
- Its [CDC docs](https://docs.airbyte.com/platform/understanding-airbyte/cdc) say Airbyte adds metadata columns that begin with `_ab_cdc_` for CDC sources.

**Where it falls short**

- Incremental CDC needs a primary key, so tables without one get full refresh only ([docs](https://docs.airbyte.com/integrations/sources/mssql)).
- Delivery is at least once ([docs](https://docs.airbyte.com/integrations/sources/mssql) (checked Oct 2026)). CDC can't be enabled on tables with a clustered columnstore index (a storage layout built for analytics), and `hierarchyid` and `sql_variant` are not processed.
- Its [CDC docs](https://docs.airbyte.com/platform/understanding-airbyte/cdc) say changes made by TRUNCATE or ALTER will not appear in the logs and so not in the destination, and a refresh is required after any new table is added to a CDC connection.
- CDC syncs launch on a sync interval and read the logs up to the sync's start time ([CDC docs](https://docs.airbyte.com/platform/understanding-airbyte/cdc)). The first CDC sync takes a snapshot with a SELECT statement, which is effectively a full refresh.
- On the [S3 Data Lake page](https://docs.airbyte.com/integrations/destinations/s3-data-lake), a Number-type primary key is stored as an Iceberg string, so ordering on it is lexicographic, and objects and unions are written as JSON strings.
- The same page cautions that if compaction runs at the same time as a truncate refresh sync, it deletes files from the current generation and causes data loss. It does not say who handles compaction.

#### 5. Estuary: best when you need to choose between CDC and change tracking

**At a glance**

- Reads SQL Server through: three connectors, CDC, change tracking or batch
- Lands data in: the destinations you choose, such as warehouses and lakes
- Price: not covered here

Estuary's [SQL Server docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) (checked Oct 2026) include a table of its three connectors. CDC is log-based and real time, and it handles tables without a primary key. Change tracking is real time too, stores only primary keys, and can capture computed columns, which CDC can't.

**What's good**

- Its [docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) set out the CDC versus change tracking tradeoff in a table, and say to use the batch connector for views or custom queries.
- The [docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) list three SQL Server connectors plus variants for Azure SQL Database, Amazon RDS and Google Cloud SQL, with setup steps for each platform. They say it is regularly tested against SQL Server 2017 and up (checked Oct 2026).
- The [docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) describe the CDC connector as log-based and real time, suited to full audit history and to tables without a primary key, but for those tables you set a key by hand in the collection definition.
- Change tracking is real time too, stores only primary keys for lower storage overhead on the source, and can capture computed columns, which CDC can't ([docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) (checked Oct 2026)).
- After a schema change, its [docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) say the connector detects a second capture instance and switches over once both are valid. An optional "Automatic Capture Instance Management" setting manages the instances for you.

**Where it falls short**

- CDC can read a replica, but the CDC worker must run on the primary. Change tracking doesn't support read replicas ([docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) (checked Oct 2026)).
- The batch connector polls, so expect latency of minutes to hours ([docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/)).
- Its [docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) say a captured table should have a primary key, and without one you must specify a key manually in the Estuary collection definition.
- The [docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) (checked Oct 2026) say CDC cannot capture computed columns or computed primary keys, and change tracking may combine intermediate changes that happen in rapid succession.
- Automatic Capture Instance Management needs additional permissions ([docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/)).
- Private and BYOC deployments need an annual plan and add fees based on the cloud infrastructure required. Its [pricing docs](https://docs.estuary.dev/getting-started/pricing/) publish no figure for those fees (checked Oct 2026).

### Enterprise platforms

#### 6. OLake Go: best for SQL Server changes into Iceberg or Parquet on your own storage

<img src="/img/logo/olake-blue-with-text.svg" alt="OLake" height="32" style={{display: 'block', margin: '2px 0 14px'}} />

**At a glance**

- Reads SQL Server through: CDC capture instances, [SQL Server 2017 or later](/docs/connectors/mssql/)
- Lands data in: Apache Iceberg or Parquet only
- Price: free licence, you pay for servers and staff

OLake Go is [open source under Apache 2.0](https://github.com/datazip-inc/olake) (checked Oct 2026) and reads SQL Server in four sync modes: full refresh, full refresh plus CDC, CDC only, and full refresh plus incremental (see the [SQL Server connector guide](/docs/connectors/mssql/)).

**What's good**

- The [SQL Server connector guide](/docs/connectors/mssql/) lists parallel chunking, checkpointing and automatic resume for failed full loads. An optional `VIEW DATABASE STATE` grant (`VIEW DATABASE PERFORMANCE STATE` on SQL Server 2022 or later) gives faster chunking for tables without a primary key.
- A "Manage Capture Instance" option creates new capture instances when schemas change, if the user has `db_owner` (see the [guide](/docs/connectors/mssql/)).
- It can read from a read-only secondary replica with `ApplicationIntent=ReadOnly`, while CDC stays enabled on the primary. With Manage Capture Instance on, it asks for the primary's credentials so it can manage capture instances there (see the [guide](/docs/connectors/mssql/)).
- It writes Iceberg tables to eleven catalog types, such as AWS Glue, REST, Polaris, Nessie and Unity (see the [catalogs page](/docs/understanding/compatibility-catalogs/)), or Parquet files if you prefer.
- For Iceberg, a two-phase commit tracks per-chunk commit status in destination state, covering full refresh, incremental and CDC for MSSQL, to avoid inconsistencies and duplicate writes (see the [v0.5.0 release notes](/docs/release/ingestion/v0.5.0/)).
- The [guide](/docs/connectors/mssql/) gives the CDC enable commands for Amazon RDS and Google Cloud SQL, and the source supports SSL modes and SSH tunnels.

**Good to know**

- OLake Go is built for Iceberg and Parquet output, and you run it on your own infrastructure.
- Keep it reading inside the three-day change table window. Computed columns come through as `NULL`, and a clustered columnstore index blocks CDC, as it does in SQL Server itself.


**Bottom line:** Pick it if you want SQL Server changes in Iceberg tables on storage you own and can run a container. Snowflake, BigQuery and Redshift can still query the Iceberg tables it writes, depending on the catalog (see the [compatibility page](/docs/understanding/compatibility-engines/)).

#### 7. Qlik Replicate: best for large mixed estates with an existing Qlik contract

**At a glance**

- Reads SQL Server through: two source connection types (endpoints), a standard SQL Server endpoint and an MS-CDC endpoint
- Lands data in: the targets Qlik supports, listed in its support matrix
- Price: [not published](https://www.qlik.com/us/pricing/data-integration-products-pricing) (checked Oct 2026)

**What's good**

- Qlik's [MS-CDC endpoint docs](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/MicrosoftSQLServer-MSCDC/MicrosoftSQLServer-MSCDC-landing.htm) say it reads Microsoft change tables instead of the log, which Qlik says lowers the risk of data loss from short log retention or unreachable log backups.
- The replication task [turns on MS-CDC for the source tables](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/MicrosoftSQLServer-MSCDC/MicrosoftSQLServer-MSCDC-prerequisites.htm) for you, unless you'd rather do it by hand.
- The same endpoint can also be used to replicate from an Amazon RDS for SQL Server source, per the [endpoint docs](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/MicrosoftSQLServer-MSCDC/MicrosoftSQLServer-MSCDC-landing.htm).
- Its [prerequisites page](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/MicrosoftSQLServer-MSCDC/MicrosoftSQLServer-MSCDC-prerequisites.htm) points to `sys.sp_cdc_change_job` and a small `@pollinginterval` value to reduce latency.
- Qlik's [pricing page](https://www.qlik.com/us/pricing/data-integration-products-pricing) lists "Qlik Open Lakehouse with ingestion and adaptive optimization for Apache Iceberg" in the Standard edition of Qlik Talend Cloud (checked Oct 2026).

**Where it falls short**

- Prices aren't published, and the product is [client-managed software](https://www.qlik.com/us/pricing/data-integration-products-pricing), so you run the server (checked Oct 2026).
- The [prerequisites page](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/MicrosoftSQLServer-MSCDC/MicrosoftSQLServer-MSCDC-prerequisites.htm) says the CT table names must use the default `<SchemaName>_<TableName>_CT` format and the CT table must include the listed columns.
- The MS-CDC capture and cleanup jobs must be running ([prerequisites](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/MicrosoftSQLServer-MSCDC/MicrosoftSQLServer-MSCDC-prerequisites.htm)).
- Microsoft ODBC Driver 18.5 must be installed on the Replicate machine, on Windows or Linux ([prerequisites](https://help.qlik.com/en-US/replicate/May2026/Content/Replicate/Main/MicrosoftSQLServer-MSCDC/MicrosoftSQLServer-MSCDC-prerequisites.htm)) (checked Oct 2026).
- On the [pricing page](https://www.qlik.com/us/pricing/data-integration-products-pricing), log-based CDC first appears in the Standard edition list for Qlik Talend Cloud, not in Starter (checked Oct 2026).

#### 8. Striim: best for log-backup reading and low load on the source

**At a glance**

- Reads SQL Server through: MS SQL Reader (CDC tables) or MSJet (log backups)
- Lands data in: many targets; Iceberg on [Google Cloud Storage](https://www.striim.com/docs/en/iceberg-writer.html) or [S3 Tables](https://www.striim.com/docs/en/s3-tables-writer.html)
- Price: [contact sales, with a Developer tier](https://www.striim.com/pricing/) (checked Oct 2026)

[Striim's SQL Server page](https://www.striim.com/docs/en/sql-server-cdc.html) says MSJet has higher throughput and lower use of the source server's compute, memory and disk than MS SQL Reader (Striim's claim, which we did not test). MS SQL Reader supports older SQL Server versions and more cloud SQL databases.

**What's good**

- You can pick the reader per source: MS SQL Reader for CDC tables, or MSJet for log backups ([docs](https://www.striim.com/docs/en/sql-server-cdc.html)).
- Its [Iceberg Writer docs](https://www.striim.com/docs/en/iceberg-writer.html) list two write modes, Merge and Append Only, and say it propagates DDL changes from supported sources to the Iceberg tables.
- Its [S3 Tables Writer docs](https://www.striim.com/docs/en/s3-tables-writer.html) list APPENDONLY and MERGE modes, with an Optimized Merge option for partial-image CDC, and DDL propagation for supported source operations.
- The [SQL Server docs](https://www.striim.com/docs/en/sql-server-cdc.html) say Striim provides wizards for creating applications that read from SQL Server and write to various targets.
- Its [pricing page](https://www.striim.com/pricing/) lists a self-managed Striim Platform with clustered deployments with HA, and Striim Cloud with dedicated compute and networking.

**Where it falls short**

- MSJet reads log backups on disk, and the [docs](https://www.striim.com/docs/en/sql-server-cdc.html) say backups on tape, virtual devices, mirror backups or Azure Storage aren't supported (checked Oct 2026).
- Its [Iceberg Writer](https://www.striim.com/docs/en/iceberg-writer.html) is Google Cloud Storage only; [S3 Tables](https://www.striim.com/docs/en/s3-tables-writer.html) has its own writer (checked Oct 2026).
- The Iceberg Writer needs a compute engine and a catalog: Google Cloud Managed Service for Apache Spark and a Lakehouse, Nessie or Polaris catalog ([docs](https://www.striim.com/docs/en/iceberg-writer.html)).
- With the Iceberg Writer, partitioned tables need manual table creation, and time source data types are written as strings ([docs](https://www.striim.com/docs/en/iceberg-writer.html)).
- The [S3 Tables Writer](https://www.striim.com/docs/en/s3-tables-writer.html) uses Amazon EMR as the compute engine, and S3 Tables requires lowercase table, namespace and column names, which breaks wildcard mappings against uppercase-identifier sources.
- Both Iceberg writers recover on restart with at-least-once processing ([Iceberg Writer](https://www.striim.com/docs/en/iceberg-writer.html), [S3 Tables Writer](https://www.striim.com/docs/en/s3-tables-writer.html)).

#### 9. AWS Database Migration Service (DMS): best for AWS-centered teams

**At a glance**

- Reads SQL Server through: MS-Replication and MS-CDC
- Lands data in: AWS stores such as S3; the [target list](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Introduction.Targets.html) names S3, Kinesis, Kafka and others, and not Apache Iceberg
- Price: not covered here

DMS uses two methods, per its [SQL Server CDC docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.CDC.html) (checked Oct 2026). On a self-managed server, it uses MS-Replication for tables with primary keys and MS-CDC for tables without. Amazon Relational Database Service (RDS) for SQL Server doesn't support MS-Replication, so DMS uses MS-CDC for all tables there.

**What's good**

- AWS operates it, and the [docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.CDC.html) cover set-up with and without the sysadmin role.
- Its [overview](https://docs.aws.amazon.com/dms/latest/userguide/Welcome.html) says you can run one-time migrations or replicate ongoing changes to keep sources and targets in sync.
- DMS version 3.4.7 and later can set up MS-CDC for the database and all tables automatically, if you are not using a read-only replica ([CDC docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.CDC.html)) (checked Oct 2026).
- Version 3.5.3 adds reading from log backups of Amazon RDS for SQL Server, per the [CDC docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.CDC.html), and Kerberos authentication for SQL Server sources, per the [source docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.html) (checked Oct 2026).
- The [source docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.html) say it supports named instances of SQL Server and can use SSL between the endpoint and the replication instance.

**Where it falls short**

- The [target list](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Introduction.Targets.html) names S3, Kinesis, Kafka and others, and not Iceberg, so Iceberg tables from DMS output would need a step you add.
- Self-managed sources need a distribution database for MS-Replication ([docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.CDC.html)). That's extra set-up work.
- The [source docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.html) (checked Oct 2026) say columnstore indexes, memory-optimized tables, temporal tables, sparse columns and column-level encryption are not supported, and neither is replication from databases with accelerated database recovery (ADR) turned on.
- Per the [source docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.html) (checked Oct 2026), changes to computed fields aren't replicated, truncate commands aren't captured, and renaming tables or columns with `sp_rename` isn't supported.
- If the database is set up for neither MS-Replication nor MS-CDC, [per AWS](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.html), tables without a primary key capture only INSERT and DELETE events; UPDATE and TRUNCATE events are ignored.
- The [source docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.html) say you may lose events if SQL Server archives them from the active transaction log to the backup log, or truncates them from it.

#### 10. Google Cloud Datastream: best for Google Cloud teams that want BigQuery or Cloud Storage

**At a glance**

- Reads SQL Server through: change tables or transaction logs, your choice per stream
- Lands data in: BigQuery, Cloud Storage, and [Apache Iceberg tables in BigQuery](https://docs.cloud.google.com/datastream/docs/destination-blmt), with the data in your own buckets
- Price: not covered here

[Datastream's SQL Server page](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) lists self-managed servers (Enterprise 2008 and later, Standard 2016 Service Pack 1 and later), Amazon RDS, Cloud SQL and Azure SQL Database. For Cloud SQL, Express is not supported (checked Oct 2026).

**What's good**

- Datastream [documents two methods per stream](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) (checked Oct 2026). Change tables have fewer limits and no risk that log truncation fails a stream for good, at lower throughput, while the transaction logs method is faster and needs fewer resources.
- The [docs](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) (checked Oct 2026) say the change tables method supports replication of encrypted tables, which the transaction logs method does not (it can't handle Transparent Data Encryption).
- With the `enable_ddl_support_for_ct` label, Datastream [checks](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) `cdc.ddl_history` every five minutes and, when a column is added, creates a new capture instance, reads the old one up to the change, then reads the new one. You still delete the original instance afterwards, since SQL Server allows two per table.
- Datastream [replicates user-defined data types](https://docs.cloud.google.com/datastream/docs/sources-sqlserver), but stores the base data type they derive from in the destination.

**Where it falls short**

- The transaction logs method doesn't support Transparent Data Encryption or column-level encryption (that data becomes `NULL`), and doesn't replicate columns added after a stream is created ([docs](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) (checked Oct 2026)).
- [Streams are limited](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) to 10,000 tables, and a table with more than 500 million rows can't be backfilled unless it has a unique index with no nullable columns, all included in the stream (checked Oct 2026).
- Its [Iceberg tables in BigQuery](https://docs.cloud.google.com/datastream/docs/destination-blmt) are append-only, and the page does not mention Amazon S3.
- `SQL_VARIANT`, `HIERARCHYID`, `GEOMETRY` and `GEOGRAPHY` columns aren't replicated ([docs](https://docs.cloud.google.com/datastream/docs/sources-sqlserver)).
- Databases with delayed durability or accelerated database recovery (ADR) enabled aren't supported, and neither is Windows Active Directory authentication ([docs](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) (checked Oct 2026)).
- With the change tables method, dropping a column replaces its data with `NULL`, and renaming columns isn't supported when CDC is enabled ([docs](https://docs.cloud.google.com/datastream/docs/sources-sqlserver) (checked Oct 2026)).

#### 11. Microsoft Fabric mirroring: best for teams whose target is Microsoft Fabric

**At a glance**

- Reads SQL Server through: CDC (SQL Server 2016 to 2022) or change feed (2025)
- Lands data in: Microsoft Fabric OneLake
- Price: replication compute is [free, per Microsoft](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) (checked Oct 2026); queries use Fabric capacity, so check what that costs you

Fabric mirroring copies a SQL Server database into Fabric. Data lands in OneLake as Delta tables, which Microsoft says now include [virtual Iceberg metadata](https://learn.microsoft.com/en-us/fabric/onelake/onelake-iceberg-tables). Microsoft's [limits page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server-limitations) says mirroring of SQL Server 2016 to 2022 requires CDC, while [SQL Server 2025 uses a different change feed](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) (checked Oct 2026).

**What's good**

- [Microsoft's docs](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) say that for SQL Server 2016 to 2022 it reuses CDC if it's already on, or can set it up.
- The [mirroring page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) lists SQL Server on Windows (Standard, Enterprise and Developer), Linux from 2017 CU18, and instances hosted on-premises, on an Azure VM or on non-Azure clouds for 2016 to 2022 (checked Oct 2026).
- Each mirrored database gets an autogenerated SQL analytics endpoint, a read-only copy you can query with T-SQL ([docs](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server)).
- To mirror a server behind a firewall, the [docs](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) say to set up an on-premises data gateway or a virtual network data gateway.
- If CDC isn't on, the [limits page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server-limitations) (checked Oct 2026) says the tutorial makes `fabric_login` a temporary member of the sysadmin server role to configure it.

**Where it falls short**

- Microsoft says you can't mirror a SQL Server 2025 database that has CDC enabled ([limits page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server-limitations) (checked Oct 2026)). SQL Server 2025 mirroring also [needs Azure Arc](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) and isn't supported on Linux or on an Azure VM.
- A schema change breaks mirroring on 2016 to 2022 until you re-enable CDC for the table, and it restarts a full snapshot on 2025 ([limits page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server-limitations) (checked Oct 2026)).
- Per the [limits page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server-limitations) (checked Oct 2026), mirroring works only on a primary database of an availability group, doesn't support a failover cluster instance, and can't mirror a database already mirrored in another Fabric workspace.
- You can mirror up to 1,000 tables, and the [limits page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server-limitations) says tables above that are not replicated (checked Oct 2026).
- On the [limits page](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server-limitations), clustered columnstore indexes aren't supported, tables using temporal history, Always Encrypted, in-memory, graph or external features can't be mirrored, and LOB columns over 1 MB are truncated to 1 MB (checked Oct 2026).
- Active transactions hold log truncation until the mirror catches up, and [Microsoft says](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server) to monitor the source transaction log so it doesn't fill.

## What actually breaks SQL Server CDC

![Native SQL Server CDC flows from an Agent job to change tables to your tool, and failures break it](/img/blog/2026/10/sql-server-cdc-tools-how-it-breaks.webp)

The diagram shows the three failures that stop a pipeline outright. A fourth, large columns, corrupts data quietly.

**The Agent stops.** [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) both capture methods need SQL Server Agent running. No Agent, no changes.

**The tool is down longer than retention.** The default is three days, which sounds fine until a long weekend. [Fivetran's docs](https://fivetran.com/docs/connectors/databases/sql-server) recommend seven days and, for change tracking, say it triggers a re-sync of a table when changes were deleted before it could process them. [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) a request for a range outside the valid window fails or can miss data.

**A column is added.** [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) new columns are ignored unless you create a second capture instance. A dropped column gets `NULL` (no value). [Microsoft's `sp_cdc_enable_table` page](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sys-sp-cdc-enable-table-transact-sql) (checked Oct 2026) says a source table can have at most two capture instances.

**Large columns come through empty.** [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/system-tables/cdc-capture-instance-ct-transact-sql) `varchar(max)`, `nvarchar(max)` and `varbinary(max)` columns are NULL on update rows unless the column changed in that update. Columns of type `text`, `image` and `ntext` are NULL on delete and update rows. A loader that treats NULL as "set to empty" will overwrite good data.

### A schema change, step by step

Microsoft's fix for a new column is a second capture instance, with a new name, that has the new shape.

```sql
EXEC sys.sp_cdc_enable_table @source_schema = 'dbo', @source_name = 'my_table',
  @role_name = 'my_role', @capture_instance = 'dbo_my_table_v2';
```

**Tools that overlap instances.** Estuary ([docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/)) and OLake Go ([guide](/docs/connectors/mssql/)) say they detect the second instance and switch when both are valid. Wait for your tool to confirm the switch before you delete the old instance.

**Tools that expect one instance.** Fivetran only supports tables with a single capture instance, so its [setup guide](https://fivetran.com/docs/connectors/databases/sql-server/setup-guide) (checked Oct 2026) tells you to create the new instance and delete the old one. Its [connector page](https://fivetran.com/docs/connectors/databases/sql-server) adds in its feature table that CDC tracks schema changes by re-syncing the modified table, unless you grant extra permissions.

### A check to run before every restart

[Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server) the query functions fail if your range is outside the valid window, so compare your tool's saved position with the oldest and newest positions SQL Server still holds.

```sql
SELECT sys.fn_cdc_get_min_lsn('dbo_my_table') AS oldest_lsn,
       sys.fn_cdc_get_max_lsn()               AS newest_lsn;
```

Debezium keeps its position as an LSN in its [offsets](https://debezium.io/documentation/reference/stable/connectors/sqlserver.html). If your saved position is older than `oldest_lsn`, cleanup has already removed changes you never read.

## A worked selection case

The case below is invented to show the method, and we did not run the other tools.

Suppose a SQL Server 2022 Standard edition server has 300 tables. Twenty have no primary key, two have a clustered columnstore index, and the target is Apache Iceberg on Amazon S3. Schemas change about monthly.

| Requirement | Fits | Does not fit, and why |
| --- | --- | --- |
| Twenty tables without a key | Estuary CDC ([docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/)), AWS DMS (MS-CDC) ([docs](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Source.SQLServer.CDC.html)), Fivetran CDC ([docs](https://fivetran.com/docs/connectors/databases/sql-server)) | Airbyte CDC copies those tables by full refresh only ([docs](https://docs.airbyte.com/integrations/sources/mssql)); Fivetran change tracking skips them ([docs](https://fivetran.com/docs/connectors/databases/sql-server)) |
| Two columnstore tables | Fivetran Teleport Sync, which [its docs](https://fivetran.com/docs/connectors/databases/sql-server) point to when CDC can't be enabled | CDC tools for those two tables, since [Microsoft says](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/change-data-capture-and-other-sql-server-features) (checked Oct 2026) CDC can't be enabled on a clustered columnstore index |
| Iceberg on S3 | Fivetran [Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service), Airbyte [S3 Data Lake](https://docs.airbyte.com/integrations/destinations/s3-data-lake), <img src="/img/logo/olake-blue.svg" alt="" height="20" style={{verticalAlign: 'middle', marginRight: '6px'}} />OLake Go | Datastream (Iceberg tables in BigQuery, [docs](https://docs.cloud.google.com/datastream/docs/destination-blmt)), Striim (Google Cloud Storage or Amazon S3 Tables, not plain S3, per its [Iceberg Writer](https://www.striim.com/docs/en/iceberg-writer.html) and [S3 Tables Writer](https://www.striim.com/docs/en/s3-tables-writer.html) docs), Fabric mirroring (lands in OneLake, [docs](https://learn.microsoft.com/en-us/fabric/mirroring/sql-server)), AWS DMS (its [target list](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Introduction.Targets.html) does not name Iceberg) |
| Monthly schema changes | Estuary and <img src="/img/logo/olake-blue.svg" alt="" height="20" style={{verticalAlign: 'middle', marginRight: '6px'}} />OLake Go (switch to a second instance) | Fivetran needs a new capture instance each time ([setup guide](https://fivetran.com/docs/connectors/databases/sql-server/setup-guide) (checked Oct 2026)) |

No single tool covers every row, so each path needs a compromise.

Airbyte can do CDC for tables with keys and full refresh for the rest. OLake Go covers the ordinary tables with CDC, and its [guide](/docs/connectors/mssql/) describes full refresh chunking for tables without a primary key.

## So which tool should you pick?

If two rows fit, shortlist both and test them.

| Your job | Look at |
| --- | --- |
| Kafka is already your hub | Debezium |
| A vendor runs loads to a warehouse | Fivetran or Estuary |
| Self-run loads on a schedule | Airbyte |
| Lower load on a busy source ([Striim's claim](https://www.striim.com/docs/en/sql-server-cdc.html)) | Striim with MSJet |
| Data goes to AWS stores, Google Cloud, or Fabric | AWS DMS, Datastream, or Fabric mirroring |
| You want to choose between change tables and log reading | Datastream or Qlik Replicate |
| Self-hosted Iceberg or Parquet files | <img src="/img/logo/olake-blue.svg" alt="" height="20" style={{verticalAlign: 'middle', marginRight: '6px'}} />OLake Go |
| CDC is not allowed on the server | Fivetran Teleport Sync, or Estuary's batch connector ([its docs](https://docs.estuary.dev/reference/Connectors/capture-connectors/SQLServer/) say it polls) |
