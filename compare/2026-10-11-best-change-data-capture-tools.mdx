<TLDR title='Key takeaways'>

Short version: there is no single best change data capture (CDC) tool, because these tools do different jobs. Debezium and Flink CDC suit teams that already run their own streaming systems.

Fivetran, Estuary, Airbyte and Artie suit teams that would rather have a vendor run the pipeline. Striim, Qlik Replicate and GoldenGate fit big Oracle estates, and AWS Database Migration Service (DMS) and Datastream fit teams that live on one cloud. Where your data has to land, say Apache Iceberg tables, cuts the list down fast.

- **CDC is not one thing.** Log-based tools read the database's change log. Query-based tools just ask, on a schedule, what changed, and that matters most for deletes and source load.
- **Where the data lands decides your shortlist.** Only some tools write Apache Iceberg, and the [AWS DMS target list](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Introduction.Targets.html) does not include it.

</TLDR>

We checked prices in September and October 2026 against vendor pages.


## Log-based or query-based? Start here

Change data capture sends only a database's inserts, updates and deletes to another system, instead of copying everything again.

[Confluent describes log-based CDC](https://www.confluent.io/learn/change-data-capture/) as reading the database's transaction log, the file where the database writes down every change in order. Query-based CDC, also called timestamp-based, works differently. It runs a query on a schedule, and it needs a column that records when each row changed.

Here's the catch with timestamp-based CDC. Confluent says it can only handle soft deletes (rows marked as deleted, not removed), and it adds load because rows must be scanned. Log-based CDC isn't free either, since [the Debezium FAQ says running a connector can add load to the source database](https://debezium.io/documentation/faq/).

![Log-based CDC reads the change log and sees deletes; query-based CDC polls on a schedule and can miss them](/img/blog/2026/10/best-change-data-capture-tools-log-vs-query.webp)

Confluent also lists trigger-based CDC, where a database trigger (a stored procedure that runs on every insert, update or delete) copies each change into a shadow table. It catches deletes, but Confluent says it hurts source performance and changes the source schema.

| Method | Sees deletes | Source load | Needs |
| --- | --- | --- | --- |
| Log-based | Yes | Low, though not zero | Access to the transaction log |
| Query-based (timestamp) | Soft deletes only | Rows are scanned on each run | A reliable changed-at column |
| Trigger-based | Yes | Extra writes on every change | Triggers and a shadow table in the source |

*Method facts: [Confluent's change data capture guide](https://www.confluent.io/learn/change-data-capture/) and the [Debezium FAQ](https://debezium.io/documentation/faq/), October 2026.*

## How we picked

We included maintained tools that read changes from at least one database and publish documentation we could open. We took the facts from the vendor's own pages and did not run these tools. This is a reading of documents, not a lab test, so any speed, uptime or ease claim below is the vendor's own.

Where we found a named, dated user comment we could link, the entry has a "What users say" line, quoted word for word. Those are single opinions, and we flag any that are old.

We left out the broad extract, transform, load (ETL) suites where CDC is just one feature among many (Hevo, Matillion, Skyvia and Integrate.io). We grouped the tools by how you run them, and the order inside a group is *not* a ranking.

## The 12 best change data capture tools, one by one

### Run it yourself

#### 1. Debezium: best for teams that already run Kafka

![Debezium home page showing its headline and main navigation](/img/blog/2026/10/landing-debezium.webp)

*Debezium home page, October 2026.*

**At a glance**

- Method: Log-based
- Databases: MongoDB, MariaDB, MySQL, PostgreSQL, SQL Server, Oracle, Db2, Cassandra ([connector list](https://debezium.io/documentation/reference/stable/connectors/index.html))
- Price: Free licence, you pay for infrastructure and staff

Debezium is an open-source tool for log-based CDC. It runs inside Kafka Connect, or as Debezium Server, which [the docs say needs no Apache Kafka](https://debezium.io/documentation/reference/stable/operations/debezium-server.html).

**What's good**

- Eight database connectors aren't marked incubating, and Oracle is one of them.
- Its docs describe [Debezium Server](https://debezium.io/documentation/reference/stable/operations/debezium-server.html) as a ready-to-use application that streams change events to messaging and storage systems without requiring Apache Kafka. The sink list includes Kinesis, Pub/Sub, Pulsar, Redis, RabbitMQ and Event Hubs besides Iceberg.
- Per the same docs, the Iceberg sink supports upsert and append modes, creates the destination tables on first startup when event and key schema information is enabled, and adds new columns when `allow-field-addition` is on (the default is true).
- The [Debezium FAQ](https://debezium.io/documentation/faq/) says all events within a topic are totally ordered, and that even if events are duplicated during failures, the end result after applying all of them stays the same.
- The [PostgreSQL docs](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) say that if the connector stops for any reason, it continues reading the WAL where it last left off after a restart.

**Where it falls short**

- You run it, all of it. The Apache Iceberg sink [lives in a separate community repository](https://debezium.io/documentation/reference/stable/operations/debezium-server.html), and each Debezium Server instance runs one connector.
- In the Iceberg sink, upsert is off by default, so the default is append-only. With upsert on, `upsert-keep-deletes` defaults to true, so deleted rows are kept and marked `__deleted=true` ([Debezium Server docs](https://debezium.io/documentation/reference/stable/operations/debezium-server.html)).
- Upsert keeps the record with the highest value in a dedup column (`__source_ts_ns` by default). The Debezium Server docs do not say what happens when two records share the same value.
- The PostgreSQL `pgoutput` plug-in does not capture values for generated columns, so those columns are missing from the connector's output ([PostgreSQL docs](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)).
- Delivery is at least once: in abnormal situations, such as recovering from a fault, the PostgreSQL connector might emit duplicate change events (same docs).

**What users say:** A commenter in the 2021 thread ["Postgres, Kafka, and a mysterious 100 GB"](https://news.ycombinator.com/item?id=29462140) said Debezium "requires a lot of babysitting."

#### 2. Apache Flink CDC: best for teams that already run Flink

![Apache Flink CDC home page showing its headline and main navigation](/img/blog/2026/10/landing-flink-cdc.webp)

*Apache Flink CDC home page, October 2026.*

**At a glance**

- Method: Log-based, with Debezium as the engine for some sources
- Price: Free licence, you pay for the Flink cluster

With Flink CDC you write a pipeline in YAML, and it generates and submits the Flink job for you. In version 3.6.x the [YAML sources](https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/pipeline-connectors/overview/) are MySQL, PostgreSQL and Oracle. SQL Server, MongoDB and Db2 are listed only under its separate Flink sources.

**What's good**

- The [Iceberg pipeline sink](https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/pipeline-connectors/iceberg/) creates tables and syncs schema changes such as new columns, with catalogs of type hadoop, hive, glue or a custom class.
- Its [connector overview](https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/pipeline-connectors/overview/) lists ten pipeline sinks for version 3.6.x: StarRocks, Doris, Paimon, Kafka, Elasticsearch, OceanBase, MaxCompute, Iceberg, Fluss and Hudi. The same YAML pipeline format covers all of them.
- The overview lists Iceberg versions 1.6, 1.7, 1.8, 1.9 and 1.10 for the Iceberg sink.
- The sink's `partition.key` option takes partition transforms per table: truncate, hour, day, month, year and bucket ([Iceberg sink docs](https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/pipeline-connectors/iceberg/)).
- Per the same page, the sink supports both batch and streaming data synchronization.

**Where it falls short**

- [The Iceberg sink](https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/pipeline-connectors/iceberg/) needs a primary key (a column that uniquely identifies each row) on every source table, and its docs say exactly-once is not supported. It uses at-least-once writes plus the key.
- Depending on the catalog type, the sink docs say you may need to add extra JARs by hand and pass them with the `--jar` argument of the Flink CDC command line.
- Each Flink CDC release pairs with specific Flink versions. Version 3.6.x supports Flink 1.20.* and 2.2.*, and 3.5.x supports 1.19.* and 1.20.* ([overview](https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/pipeline-connectors/overview/)).
- The version table shows YAML sources arriving over time: PostgreSQL first appears in the 3.5.x row and Oracle in the 3.6.x row, and the Iceberg sink first appears in the 3.4.x row.

#### 3. OLake Go: best for database changes into Iceberg on your own storage

<img src="/img/logo/olake-blue-with-text.svg" alt="OLake" height="32" style={{display: 'block', margin: '2px 0 14px'}} />

![OLake home page showing its headline and main navigation](/img/blog/2026/10/landing-olake.webp)

*OLake home page, October 2026.*

**At a glance**

- Method: Log-based CDC for four databases
- Price: Free licence (Apache 2.0), you pay for infrastructure

You run it with Docker Compose ([OLake UI install](/docs/install/olake-ui/)), the Docker command line ([Docker CLI](/docs/install/docker-cli/)) or Helm on Kubernetes ([Kubernetes install](/docs/install/kubernetes/)).

It reads PostgreSQL logical replication, the MySQL binlog, MongoDB change streams and SQL Server's native CDC, and writes Apache Iceberg tables. Deleted rows are marked with equality deletes (a delete by key value) or positional deletes (a delete by file position), both Iceberg version 2 delete formats. Since [v0.11.0](/docs/release/ingestion/v0.11.0/) it can also use deletion vectors, an Iceberg version 3 delete format (see the [terminology page](/docs/understanding/terminologies/olake/)).

Docs: [PostgreSQL](/docs/connectors/postgres/), [MySQL](/docs/connectors/mysql/), [MongoDB](/docs/connectors/mongodb/), [SQL Server](/docs/connectors/mssql/).

**What's good**

- It is open source under Apache 2.0 ([GitHub](https://github.com/datazip-inc/olake)), and one tool does the first snapshot and then the change capture, with no per-row fee.
- It supports eleven Iceberg catalog types ([compatibility page](/docs/understanding/compatibility-catalogs/)), including Glue, Hive, Unity and Representational State Transfer (REST) catalogs ([REST catalog page](/docs/writers/iceberg/catalog/rest/)).
- Kafka and S3 work as sources too ([docs](/docs/)), and OLake Fusion, a companion product, handles Iceberg compaction and table maintenance ([Fusion docs](/docs/fusion/compaction/types-of-compaction/)).
- Full Refresh + CDC, Full Refresh + Incremental and strict CDC syncs are stateful and resumable: after a crash, a network failure or a manual pause, a sync resumes from its last checkpoint instead of starting over. The Iceberg writer also uses a two-phase commit that tracks per-chunk commit status, so syncs avoid inconsistencies and duplicate writes ([OLake Go overview](/docs/)).
- Large tables are read in parallel chunks during the first snapshot, and each job sets its own maximum number of connections to the source database ([OLake Go overview](/docs/)).
- New source columns are added to the Iceberg schema automatically, and widening type changes such as INT to LONG, FLOAT to DOUBLE and wider DECIMAL precision are handled ([schema evolution docs](/docs/features/schema/)).

**Good to know**

- Change capture covers PostgreSQL, MySQL, MongoDB and SQL Server, and [Oracle](/docs/connectors/oracle/), [Db2](/docs/connectors/db2/) and S3 sources load by full refresh or incremental.
- Output is Iceberg and Parquet on storage you choose, and Snowflake, BigQuery and Redshift can query the Iceberg tables it writes (see the [compatibility page](/docs/understanding/compatibility-engines/)).

**Bottom line:** Pick OLake Go when you run PostgreSQL, MySQL, MongoDB or SQL Server and want database changes in Iceberg tables on storage you run. For Oracle change capture, look at Debezium, Qlik Replicate or Oracle GoldenGate above.

### Managed or vendor-run

#### 4. Estuary: best for one managed platform for streaming and batch

![Estuary Flow home page showing its headline and main navigation](/img/blog/2026/10/landing-estuary.webp)

*Estuary Flow home page, October 2026.*

**At a glance**

- Method: Log-based
- Price: $0.50 per GB moved, plus $100 a month for each of the first 6 connector instances and $50 for extra ones; free tier of 10 GB a month and 2 instances ([Estuary pricing page](https://estuary.dev/pricing/), October 2026)

Its [pricing page](https://estuary.dev/pricing/) lists PostgreSQL, MySQL, MongoDB, Oracle and SQL Server among the major databases it supports.

**What's good**

- Its pricing page says it unifies real-time streaming and batch movement in one system.
- The pricing FAQ says Estuary offers "200+ source and destination connectors" across databases, cloud storage, APIs, SaaS apps and streaming platforms ([pricing page](https://estuary.dev/pricing/)).
- Per the same FAQ, a new pipeline runs a historical backfill and then switches to real-time CDC, and the backfill can be disabled or scoped.
- Adding a new target means paying only for that target and the data sent to it, with no need to re-extract from each source (pricing FAQ).
- Its [Iceberg connector docs](https://docs.estuary.dev/reference/Connectors/materialization-connectors/apache-iceberg/) say AWS Glue catalogs work through the Glue Iceberg REST endpoint, and that with Glue you can configure table optimizers for compaction, snapshot retention and orphan file deletion.

**Where it falls short**

- The [Iceberg connector](https://docs.estuary.dev/reference/Connectors/materialization-connectors/apache-iceberg/) needs an Iceberg REST catalog (a catalog with a standard web API) on Amazon S3, an AWS EMR Serverless Spark application and an S3 staging bucket (a holding folder for files in transit). Catalogs on GCP or Azure are planned, not supported.
- Each source and destination is a billed instance ([pricing](https://estuary.dev/pricing/)), so the bill grows as your pipelines do.
- In the Iceberg connector docs, array and object fields are written as string columns, and the docs say nested types are not currently supported.
- Compaction through the Glue optimizer settings is off by default (Enable Compaction defaults to false), and Hard Delete is disabled by default, so rows deleted in the source are soft-deleted in Iceberg.
- A "Beta" label sits in the docs section on REST catalogs other than AWS Glue.
- Private and bring-your-own-cloud deployments need an annual plan and add fees based on the cloud infrastructure required, and no figure is published ([pricing docs](https://docs.estuary.dev/getting-started/pricing/)).

#### 5. Airbyte: best for scheduled syncs and a long connector list

![Airbyte home page showing its headline and main navigation](/img/blog/2026/10/landing-airbyte.webp)

*Airbyte home page, October 2026.*

**At a glance**

- Method: Log-based CDC on scheduled syncs
- Price: Core free; Cloud Standard $20 a month with 5 credits and $5 per extra credit, with database data at 4 credits per GB ([Airbyte pricing page](https://airbyte.com/pricing) and [credit docs](https://docs.airbyte.com/platform/cloud/managing-airbyte-cloud/manage-credits), October 2026)

[Airbyte's CDC docs](https://docs.airbyte.com/platform/understanding-airbyte/cdc) say syncs are scheduled, and CDC sources aren't treated as infinite streaming sources. So don't expect a live stream. Cloud Standard syncs at most hourly, and Plus syncs every 15 minutes ([Cloud limits](https://docs.airbyte.com/platform/cloud/managing-airbyte-cloud/understand-airbyte-cloud-limits)).

**What's good**

- Its [pricing page](https://airbyte.com/pricing) lists 700+ connectors, and the [S3 Iceberg destination](https://docs.airbyte.com/integrations/destinations/s3-data-lake) supports REST, Glue, Nessie and Polaris catalogs.
- The S3 Iceberg destination offers Full Refresh Overwrite, Append and Overwrite + Deduped, plus Incremental Append and Append + Deduped. Its docs say dedup is merge-on-read: primary keys become Iceberg identifier columns, and an upsert is an equality delete on the key followed by an insert.
- The pricing page's comparison matrix lists a maximum sync frequency of 5 minutes on Pro and Enterprise Flex, against 15 minutes on Plus and 1 hour on Standard.
- Its [licence FAQ](https://docs.airbyte.com/platform/developer-guides/licenses/license-faq) says anyone can use Airbyte free of charge and run it at scale on their own infrastructure, under the Elastic License 2.0.
- On Cloud, the [credit docs](https://docs.airbyte.com/platform/cloud/managing-airbyte-cloud/manage-credits) say that if you run out of credits, syncs continue and you are billed in arrears. A trial lasts 14 days or 400 trial credits, whichever comes first.

**Where it falls short**

- The [CDC docs](https://docs.airbyte.com/platform/understanding-airbyte/cdc) list some limits. Views aren't supported, TRUNCATE and ALTER changes aren't picked up from the logs, and new tables need a refresh.
- Per the same page, CDC incremental is supported only for tables with primary keys for most sources, and the first CDC sync takes a snapshot with a SELECT statement, which the docs call effectively a Full Refresh.
- In the S3 Iceberg destination, objects and unions are written as string columns of serialized JSON ([destination docs](https://docs.airbyte.com/integrations/destinations/s3-data-lake)).
- Two cautions in the same docs: if compaction runs at the same time as a truncate refresh sync, it deletes files from the current generation and causes data loss, and changes made to the main branch outside Airbyte after a sync begins are lost.
- The [Cloud limits page](https://docs.airbyte.com/platform/cloud/managing-airbyte-cloud/understand-airbyte-cloud-limits) caps Standard organizations at 1 workspace and a connection at 1,000 streams. Plus has SSO but no SCIM or role-based access control.
- Pro and Enterprise Flex use capacity-based pricing, and the [pricing page](https://airbyte.com/pricing) publishes no price for them.

#### 6. Fivetran: best for hands-off, vendor-run replication

![Fivetran home page showing its headline and main navigation](/img/blog/2026/10/landing-fivetran.webp)

*Fivetran home page, October 2026.*

**At a glance**

- Method: Native logs plus proprietary methods
- Price: Monthly Active Rows (MAR) per connection; [free up to 500,000 MAR](https://fivetran.com/docs/core-concepts/usage-based-pricing/billing-and-plans); a [$5 base charge per connection on paid plans](https://fivetran.com/docs/core-concepts/usage-based-pricing/pricing-updates/2026-pricing-updates) from January 2026; paid per-MAR rates in its [Service Consumption Table](https://www.fivetran.com/legal/service-consumption-table) (Standard first tier $495 per million MAR, version 10, effective February 1, 2026)

Fivetran counts Monthly Active Rows (MAR), meaning the rows changed in a month, per connection.

Its database connectors use each source's own CDC feature (MySQL and MariaDB binlog, SQL Server CDC and Change Tracking, MongoDB change streams, PostgreSQL logical replication) or a proprietary method ([database connector docs](https://fivetran.com/docs/connectors/databases)). Its proprietary Teleport Sync can force a full table re-sync if large parts of a table change.

**What's good**

- It runs the pipeline for you, with hundreds of connectors.
- [Managed Data Lake Service](https://fivetran.com/docs/destinations/managed-data-lake-service) writes Iceberg to S3, Azure Data Lake Storage and Google Cloud Storage, and Fivetran says it handles the table maintenance (we did not test that).
- Per its [database connector docs](https://fivetran.com/docs/connectors/databases), database connectors sync new and modified data every 15 minutes by default, apply changes to the destination in batches with a merge (upsert and insert), and most initial syncs finish within a day.
- For the Iceberg service, Fivetran says snapshots older than the retention period are deleted once a day (the last 2 snapshots are always kept), and orphan files are moved to an `orphans` folder on the second and fourth Saturdays of each month ([docs](https://fivetran.com/docs/destinations/managed-data-lake-service)). We did not test this.
- A row is counted once per month even if it syncs several times, and a row deleted twice in a month is counted once ([pricing update](https://fivetran.com/docs/core-concepts/usage-based-pricing/pricing-updates/2026-pricing-updates)).

**Where it falls short**

- The Iceberg service does not support position deletes ([docs](https://fivetran.com/docs/destinations/managed-data-lake-service)), and deleted rows count as paid MAR from January 2026 ([pricing update](https://fivetran.com/docs/core-concepts/usage-based-pricing/pricing-updates/2026-pricing-updates)).
- The [billing docs](https://fivetran.com/docs/core-concepts/usage-based-pricing/billing-and-plans) set a $5 minimum charge per connection on monthly pay-as-you-go (for usage between 1 and 1 million MAR) and a $12,000 minimum on annual contracts.
- Per the same page, Oracle, Oracle RAC, Oracle RDS, SAP ERP on HANA and Db2 for LUW (Beta) database sources can be synced only on the Enterprise or Business Critical plans.
- Expired change logs require a full source re-sync, and schema changes in the source are the most common trigger of a full table re-sync ([database connector docs](https://fivetran.com/docs/connectors/databases)).
- On AWS, the Iceberg service does not support the S3 Glacier Flexible Retrieval, Glacier Deep Archive and Intelligent-Tiering archive tiers, and AWS Glue Catalog supports only one table per schema and table name combination in a Region ([docs](https://fivetran.com/docs/destinations/managed-data-lake-service)).
- Iceberg does not allow columns named `_deleted`, `_file`, `_partition`, `_pos`, `_spec_id`, `file_path`, `pos` or `row`, so Fivetran prefixes such names with a hash symbol (#) (same docs).

**What users say:** In a Hacker News thread about Fivetran and dbt Labs [agreeing to merge](https://news.ycombinator.com/item?id=45573187) (October 2025), one commenter wrote "Fivetran is convenient but absurdly expensive."

![Artie home page showing its headline and main navigation](/img/blog/2026/10/landing-artie.webp)

## Open source or managed: what's the real cost?

Three of the twelve tools are open source under Apache 2.0. Airbyte's [Elastic License 2.0](https://docs.airbyte.com/platform/developer-guides/licenses/license-faq) and Estuary's [Business Source License 1.1](https://raw.githubusercontent.com/estuary/flow/master/LICENSE-BSL) are source-available licences. Airbyte's bars providing the software to others as a managed service, and Estuary's bars using it for a "Data Processing Service", and its text says it is not an Open Source license.

A free licence is not a free pipeline. Debezium's Kafka mode needs a Kafka cluster, Flink CDC needs a Flink cluster, and someone has to be on call. Managed tools swap that work for a meter: Fivetran counts rows, Estuary gigabytes and instances, Airbyte credits and Datastream processed bytes.

Here is the maths on Estuary's Cloud plan: 50 GB a month through one capture and one destination is 2 connector instances. [Estuary's docs](https://docs.estuary.dev/getting-started/pricing/) bill data "into and out of Estuary", so 50 GB is counted twice. That is 100 GB x $0.50 = $50 for data, plus $200 for instances, so $250 a month (our arithmetic from the Estuary pricing page and docs, October 2026).

## What to check before you commit

These seven checks come from failure modes the vendors' own docs describe.

**1. Exact database and version support.** [Qlik's docs](https://help.qlik.com/en-US/replicate/May2026/Content/Global_Common/Content/SharedReplicateHDD/Oracle/OracleDB_source_limitations.htm) say Oracle 21c cannot use LogMiner, only Qlik's own log reader. Artie lists Oracle and SQL Server log replication on [Enterprise only](https://www.artie.com/pricing).

**2. The initial snapshot.** Most setups copy the existing rows first, then switch to changes. [Debezium's PostgreSQL docs](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) say that if the connector stops during a snapshot it starts a new one on restart, and [Fivetran needs a full re-sync](https://fivetran.com/docs/connectors/databases) when you change database providers.

**3. Delete handling.** Timestamp-based CDC sees only soft deletes. Even log-based CDC has gaps: for MySQL, [the Debezium FAQ](https://debezium.io/documentation/faq/) says deletes caused by cascade delete rules are not in the binlog.

**4. Schema changes.** Airbyte's [Iceberg connector](https://docs.airbyte.com/integrations/destinations/s3-data-lake) never rewrites data files, so it handles only some changes. Striim's [Iceberg Writer](https://www.striim.com/docs/en/iceberg-writer.html) writes time types as strings.

**5. Latency.** Ask what delay you'll really see.

**6. Ordering and "at least once".** [Debezium's docs](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) say it delivers at least once, so duplicates can appear after a failure, though [events within a topic stay in order](https://debezium.io/documentation/faq/). Flink CDC's [Iceberg sink](https://nightlies.apache.org/flink/flink-cdc-docs-stable/docs/connectors/pipeline-connectors/iceberg/) and Striim's Iceberg Writer are also at least once, so use primary keys and upserts instead of blind appends.

**7. What vendors say about delay.**

| Tool | What its own pages say about delay |
| --- | --- |
| Artie | "Sub-minute latency, exactly-once delivery" on its [pricing page](https://www.artie.com/pricing) |
| Estuary | "Millisecond latency or batch, no extra charge" on its Cloud plan ([pricing page](https://estuary.dev/pricing/)) |
| Airbyte | Syncs are scheduled; Standard runs at most hourly and Plus every 15 minutes ([limits](https://docs.airbyte.com/platform/cloud/managing-airbyte-cloud/understand-airbyte-cloud-limits)) |

These are vendor claims, not our tests. AWS says DMS CDC has no latency guarantee.

One more for PostgreSQL. [Debezium's docs](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) warn that WAL (write-ahead log) disk space can spike when a quiet captured database shares a server with a busy one. The replication slot (PostgreSQL's log bookmark for the tool) can't move, and the fix is a heartbeat setting.

### How to run a two-week trial

Use the same test for every finalist. It is a checklist we suggest, not a result we measured.

- Seed rows 1, 2 and 3. Insert row 4, update row 2 twice and delete row 3.
- Add a column, then widen a number column from 32 to 64 bits.
- Stop the tool mid-run, then restart it. Every key should appear once.
- Expected result: rows 1, 2 (with its second update) and 4, no row 3, no duplicates. Append-only outputs, such as Datastream's, show every change as its own record.
- Read the bill after a week of real change volume.
