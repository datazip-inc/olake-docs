<TLDR title='Key takeaways'>

"Data quality tool" means three different jobs.

If you want rules you write and run in a pipeline, start free with Great Expectations, Soda Core, dbt tests or Deequ. If you want something to watch production tables for surprises, look at Elementary (free if you use dbt) or quote-based platforms such as Monte Carlo and Anomalo. For profiling, cleansing and governance in an enterprise suite, look at Informatica Data Quality and Ataccama ONE (a data quality platform).

Most paid platforms don't publish a price. Ask for a written quote and a trial before you get attached.

- **Free options exist.** Great Expectations Core, Deequ and Elementary's open-source tool use the Apache 2.0 licence, each per its own GitHub repository (we link the Great Expectations licence file). Soda Core uses the Elastic License 2.0, not Apache or MIT, so read it before you build on it.
- **Fit beats features.** dbt tests and Elementary's open-source tool only help if you already use dbt. Deequ needs Apache Spark (a big-data engine), so no Spark, no Deequ.

</TLDR>

IBM (International Business Machines) defines data quality as how well a dataset meets criteria for accuracy, completeness, validity, consistency, uniqueness, timeliness and fitness for purpose, according to IBM's data quality topic page. A data quality tool checks those things for you, so a wrong number gets caught before it reaches a report. Last reviewed October 2026.

## What a data quality tool actually does

The simplest check is a rule, such as every order having a unique ID. dbt's documentation on data tests uses that very example, where the `order_id` column in the `orders` model should be unique.

Rules catch the problems you thought of. Observability tools go after the ones you didn't. They record facts about each table, such as how many rows arrived and how fresh the data is, and flag anything that breaks the usual pattern.

![Testing tools run rules you write; observability tools learn what is normal and alert on drift](/img/blog/2026/10/best-data-quality-tools-two-jobs.webp)

The tool turns each rule into a query that hunts for bad rows, and you get pass or fail.

![A dbt test passes when its query returns zero rows and fails when any bad rows come back](/img/blog/2026/10/best-data-quality-tools-test-flow.webp)

*Original diagram based on dbt's data test documentation, October 2026.*

Cleansing is the third job: finding duplicate records, fixing formats and matching names, which the big enterprise suites handle. Data catalogs (a searchable list of your data) are now adding quality checks too.

## How we picked

Each tool had to check data quality as a main job, publish documentation or a pricing page we could read, and still be maintained. Vendor facts come from each vendor's own pages, read in October 2026. We did not run the other tools.

Tools whose pages we didn't read, and data quality features inside warehouses, are left out.

Within each group the order is not a ranking. We use no vendor testimonials and no comments from people who sell a rival tool.

## The 9 data quality tools, one by one

### 1. Great Expectations: rules written in Python

![Great Expectations home page showing its headline and main navigation](/img/blog/2026/10/landing-great-expectations.webp)

*Great Expectations home page, October 2026.*

**At a glance:** A Python library for data tests. Its paid cloud service is no longer publicly available.

Great Expectations (GX) is built around the Expectation, which its docs describe as a verifiable assertion about data (the GX overview page). You connect to data, write Expectations, group them into suites and run them. Its docs mention SQL tables and Spark dataframes (tables held in Python memory) as data to validate.

GX Core is free under the Apache 2.0 licence. On 6 May 2026 Great Expectations posted [an update](https://greatexpectations.io/blog/an-update-from-great-expectations/) saying "GX Cloud will no longer be publicly available beginning June 1."

The same post says "Fivetran will become the new steward of the Great Expectations open source community and the GX Core project." Under the planned transition, it adds, GX Core will continue as an open source, community-driven project.

**Where it fits**

- Rules live in code, so you can review and version them like anything else you write.
- It can validate SQL tables and Spark dataframes, so one tool can check several kinds of data.
- In production, a Checkpoint runs your validations, and Actions can send the results to email, Slack or Microsoft Teams, per the GX Core overview.
- It writes Data Docs, human-readable pages that host your Expectation Suites and Validation Results (GX Core overview).
- One Expectation Suite can be applied to different Batches, so the same checks can cover several tables or time slices (GX Core overview).

**Where it falls short**

- GX Cloud is no longer publicly available from 1 June 2026, per GX's own May 2026 post, so GX Core is the way in.
- Stewardship of GX Core moves to Fivetran under the planned transition (same post).
- You write the rules yourself. It checks data against them, and that's all. It does not move, store or catalog data.
- GX Core is a Python library, so someone has to write Python to set up the connections, Expectations and runs (GX Core overview).
- The docs' scheduled-testing example has an orchestrator trigger the run, so plan to bring your own scheduler (GX Core overview).

**Pick something else if** you want the tool to learn normal patterns for you. Elementary or Monte Carlo is the better place to look.

### 2. Soda: data contracts and a free hosted tier

![Soda home page showing its headline and main navigation](/img/blog/2026/10/landing-soda.webp)

*Soda home page, October 2026.*

**At a glance:** A data quality platform whose engine, Soda Core, runs checks written in YAML (a simple text format).

On its GitHub page, Soda describes Soda Core as a data quality and data contract verification engine.

A data contract is a written agreement about what a dataset must look like, including its columns, types and value ranges. Soda's docs split the work into testing during development and observability in production.

Soda shows its prices openly. The [pricing page](https://www.soda.io/pricing) lists a Free plan at $0 a month, a Team plan at $750 a month, and Enterprise at custom pricing.

Free includes some Soda Processing Units (SPUs). Team adds unlimited users, catalog integrations and pay-as-you-go extra units, as the screenshot shows. The catch: the price of one SPU is not shown.

![Soda pricing page: Free at 0 dollars a month, Team at 750 dollars a month, Enterprise custom](/img/blog/2026/10/best-data-quality-tools--soda-pricing-plans.webp)

*Soda pricing page, October 2026.*

**Where it fits**

- A published price for the paid Team plan. Several vendors in this category show none.
- Soda Core supports many sources, including PostgreSQL, Snowflake, BigQuery, Databricks and DuckDB, per its GitHub page.
- The Free plan at $0 includes pipeline testing, metrics observability and alerting integrations, with no credit card required (pricing page).
- You can run it three ways: Soda Core in your pipelines, a Soda-hosted Runner, or a Self-hosted Runner in your own Kubernetes environment, where the docs say data stays within your network (Soda docs).
- Its docs list Airflow, Dagster, Prefect and Azure Data Factory for orchestration, and Slack, Microsoft Teams, Jira, PagerDuty, ServiceNow and Opsgenie for alerts and tickets (Soda docs).

**Where it falls short**

- Soda's docs say Soda Core has no observability features. Those come from the hosted product.
- Its licence file is the [Elastic License 2.0](https://raw.githubusercontent.com/sodadata/soda-core/main/LICENSE), not Apache or MIT. The docs call Soda Core open source, but have a lawyer read the licence before you build a product on it.
- Features such as SSO (single sign-on), audit logs and private deployment appear under Enterprise on the live page.
- The hosted and self-hosted Runners cannot scan in-memory sources such as Spark or DataFrames. Soda Core is the option for those (Soda docs).
- The Self-hosted Runner needs Kubernetes expertise, per the same docs page.
- Soda Core `v4` renamed its packages (for example `soda-postgres`), and legacy `v3` packages are named `soda-core-{data source}`, so check which version a guide or install command targets (GitHub).

**Pick something else if** you only need tests and already use dbt. dbt's free open-source distribution already includes its built-in tests.

### 3. dbt tests: data already transformed with dbt

![dbt home page showing its headline and main navigation](/img/blog/2026/10/landing-dbt.webp)

*dbt home page, October 2026.*

**At a glance:** Tests built into dbt, a tool that transforms warehouse data with SQL (Structured Query Language).

dbt's docs describe data tests as assertions you make about your models and other resources. Each test is a query that returns the bad rows, and the test passes when zero rows come back. dbt ships four generic tests: `unique`, `not_null`, `accepted_values` and `relationships`.

dbt Core is free under Apache 2.0. The [pricing page](https://www.getdbt.com/pricing) lists a free Developer plan (1 seat, `3,000` successful models built a month) and a Starter plan at $100 per user a month.

Fivetran announced in a press release the completion of its merger with dbt Labs on June 1, 2026.

dbt's docs show an `orders` example: a short block of YAML covers the order ID, the status values and the link to customers, and the `dbt test` command runs it all. The screenshot is the docs' plain-English translation of that YAML.

![dbt docs translating four orders tests into plain English and saying a test passes on zero returned rows](/img/blog/2026/10/best-data-quality-tools--dbt-data-tests-plain-english.webp)

*dbt data tests documentation, October 2026.*

**Where it fits**

- No new tool to learn if you already use dbt.
- Four common checks come built in, and you can write your own in SQL.
- Newer unit tests check your SQL logic on small made-up inputs before a model is built, from dbt version `1.8`.
- Singular tests are plain SQL: you write the exact query that returns the failing records (dbt data tests docs).
- Open-source packages such as `dbt-utils` and `dbt-expectations` add more generic tests (dbt data tests docs).
- The `error_if` and `warn_if` configs set custom failure thresholds for a test (dbt data tests docs).

**Where it falls short**

- Ordinary data tests only run after a model is built, according to dbt's own unit test docs.
- It only tests what dbt manages. Data that never passes through dbt is invisible to it.
- Its tests return failing rows and pass on zero rows; the docs we read do not describe cleansing or learned alerts.
- Unit tests work on SQL models only, per the dbt unit test docs.
- On paid plans, models that build successfully are counted even if the run later fails: a job of 100 models that fails after 51 counts 51 ([dbt billing docs](https://docs.getdbt.com/docs/platform/billing/how-pricing-works)).

**Pick something else if** you don't use dbt. Great Expectations or Soda Core work without it.

Starter lists five developer seats and `15,000` successful models built a month, so the "per user" price looks aimed at a small team. This is our read.

![dbt pricing page: Developer free, Starter 100 dollars per user a month, Enterprise and Enterprise plus custom](/img/blog/2026/10/best-data-quality-tools--dbt-pricing-plans-quality.webp)

### 4. Elementary: adding alerts to a dbt project

![Elementary home page showing its headline and main navigation](/img/blog/2026/10/landing-elementary.webp)

*Elementary home page, October 2026.*

**At a glance:** An open-source command line tool and dbt package that turn your dbt test results into a report and alerts.

Elementary's GitHub page calls its tool the open-source CLI for dbt-native data observability. The Elementary dbt package collects results and feeds a report and alerts to Slack and Microsoft Teams. Anomaly detection tests are added as normal dbt tests.

The open-source tool uses Apache 2.0. Elementary's open-source docs list 14 supported dbt adapters, including Snowflake, BigQuery, Redshift, Databricks and PostgreSQL.

**Where it fits**

- Free to start, and the setup lives right in your dbt code.
- A 30-day free trial of the paid Elementary Cloud is listed on its [pricing page](https://www.elementary-data.com/pricing).
- Elementary says Cloud "can't access your data". That is the vendor's claim, and we did not test it.
- Alerts can go to Slack and Microsoft Teams, with custom channels and tagging of owners (GitHub).
- The CLI can send alerts and self-host the observability report, a view of your dbt runs and all dbt test results (OSS docs).
- Cloud's Scale plan lists anomaly detection, column-level lineage, incident management and an MCP server (pricing page).

**Where it falls short**

- The docs say the open-source tool "covers a single dbt project". Teams with several projects are pointed to Cloud.
- Cloud plans (Scale, Enterprise and Unlimited) all say "Talk to us" instead of a price.
- The open-source tool depends on dbt. Elementary's docs say Cloud can connect to a warehouse without dbt, which helps if you're not a dbt shop.
- SSO and RBAC are listed under Enterprise, not Scale (pricing page).
- The AI Layer add-on has its own credit-based pricing, also marked "Talk to us" (pricing page).
- The open-source CLI reads the results that the Elementary dbt package collects in your warehouse, so you install both the package and the CLI (GitHub).

**Pick something else if** your data isn't in dbt. Soda Core and Great Expectations don't need it.

Elementary says its pricing is based on seats and environments. Scale lists up to 10 editor seats and `1K` tables, and Enterprise lists up to 20 editor seats, 40 viewer seats and `3K` tables, with no dollar prices. The cost of an extra `1K` tables is not shown.

### 5. Deequ: very large data on Apache Spark

![Deequ home page showing its headline and main navigation](/img/blog/2026/10/landing-deequ.webp)

*Deequ home page, October 2026.*

**At a glance:** A free library from AWS (Amazon Web Services) Labs that runs "unit tests for data" on Spark.

The Deequ repository on GitHub describes a library built on Apache Spark, written in Scala, with a Python wrapper called PyDeequ. Its repository lists data profiling, anomaly detection over time and automatic constraint suggestion, and its rule language includes completeness and uniqueness checks.

Deequ uses Apache 2.0, and its latest release on GitHub, `2.1.0`, came out on 2026-09-16.

**Where it fits**

- Free, and built on Spark, an engine made for large datasets.
- It can suggest checks from the data, which helps when you have no idea where to start.
- A declarative rule language called DQDL is supported.
- It is designed for very large datasets: the README says "think billions of rows".
- It works on anything you can fit into a Spark dataframe, including CSV files, database tables, logs and flattened JSON (README).
- Computed metrics can be stored and queried with a `MetricsRepository`, and updated incrementally as data grows or partitions change (README).

**Where it falls short**

- You need a Spark setup and a matching Java version. Release `2.1.0` and later need Java `11`, and each release targets specific Spark versions, so check before you install.
- The repository says row-level checks in DQDL mode work only for certain rule types, and dataset-level rules such as `RowCount` and `Mean` are marked as skipped.
- It's a library from AWS Labs, not an AWS managed service.
- The Deequ `2.x` table lists Spark `3.1` through `3.5`, and Spark `3.0` and earlier need a Deequ `1.x` release (README).
- It is a Scala library, and Python use goes through PyDeequ, a separate Python interface (README).

**Pick something else if** you have no Spark. Soda Core and Great Expectations are Python-based and do not need Spark.

### 6. OpenMetadata: quality tests inside a free catalog

![OpenMetadata home page showing its headline and main navigation](/img/blog/2026/10/landing-openmetadata.webp)

*OpenMetadata home page, October 2026.*

**At a glance:** An open-source data catalog with data quality tests built in.

Per its docs, you can run tests at the table and column level, write no-code test cases from the screen and use a built-in profiler. Alerts fire when a test fails. Lineage (where data came from) and governance are covered too, all under the Apache 2.0 licence.

**Where it fits**

- One free tool for the catalog, the tests and the alerts, with no licence fee.
- No-code tests let analysts add checks without writing any Python.
- Its GitHub README says it has 130+ connectors.
- The docs say quality tests are supported for all of its supported database connectors, with alerts, a health dashboard and a resolution workflow for failures (docs).
- Tests can be set up in the UI or in a YAML config file, and you can write your own tests and test suites (docs).

**Where it falls short**

- You run and upgrade it yourself unless you use a managed offering. The docs' production options are Kubernetes, cloud-managed services or bare metal (docs).
- Collate, which sells managed OpenMetadata, posted about a free managed tier in June 2024 with a waitlist (Collate's blog post). We did not confirm it is open today.
- It's a full catalog with lineage and governance as well as tests.
- Quality is one feature among several in its docs. A team that only wants tests may not need all of it.
- Its connectors page marks each connector `PROD` or `BETA`, and says a `BETA` connector may have limitations or missing features.

**Pick something else if** you only need pipeline tests. Great Expectations or dbt tests are lighter to carry.

## Your first week with a free tool

1. **Pick the five columns your reports lean on most.** Think order IDs, dates and amounts.
2. **Add `unique` and `not_null` to every ID.** One duplicated or empty ID can quietly double-count an order.
3. **Add `accepted_values` to status columns.** A new, misspelled status then fails a test instead of silently vanishing from a chart.
4. **Add `relationships` between tables.** It catches an order that points to a customer who doesn't exist.
5. **Send failures to one chat channel.** A test nobody sees is just a file.

Run it for a week before you shop for anything bigger. The failing tests show which tables deserve a monitoring tool.

## Questions to ask a paid vendor

Get the answers in writing.

- What is one credit, unit or table worth in dollars on my tier?
- What counts toward usage: tables, monitors, rows scanned or users?
- Is there a trial or proof of concept on my own data?
- Which of my sources and warehouse are supported today, not on the roadmap?
- What happens to unused units at the end of the period?
- Can I export my rules and results if I leave?

## Where data quality fits in the pipeline

Quality checks sit after data has been loaded, and sometimes after it's been transformed. The tools here don't copy data between systems; if your tables come from database replication, checks such as row counts compare a source against its copy.

## Where OLake fits

[OLake Go](/docs/) is an open-source extract-and-load tool with no transformation step. It copies databases such as Postgres, MySQL, MongoDB and SQL Server into Apache Iceberg tables, using [any of the catalogs our docs list](/docs/understanding/compatibility-catalogs/). Once the copy lands, those Iceberg tables are where a quality tool can run its checks, such as a row count against the source. OLake Go writes Iceberg or Parquet, so the checks come from the tools above.
