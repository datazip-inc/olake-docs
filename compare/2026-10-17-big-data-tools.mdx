<TLDR title='Key takeaways'>

There is no single best big data tool. Big data work has four jobs, and most tools only do one of them. Hadoop (HDFS), Amazon S3, Cassandra and MongoDB store data, Kafka moves streams, Spark and Flink process data, and Trino, BigQuery, Snowflake and Databricks answer queries.

Pick one tool per job, or one cloud platform that bundles several. Then check how each one bills before you commit.

A small team that only needs reports can start with S3 files and one managed warehouse. Jump to [which tool for which situation](#which-tool-for-which-situation) for a quick pick.

- **Big data tools aren't rivals.** A storage tool, a streaming tool and a query tool sit side by side in one stack, so one ranked list of all three misleads you.
- **The open-source projects here are still shipping.** Hadoop `3.5.0` came out April 2, 2026, Kafka `4.3.1` on June 25, Flink `2.3.0` on June 25, Spark `4.2.0` on July 14 and Trino `483` on July 17. Yes, Hadoop is still maintained.
- **Kafka no longer needs ZooKeeper.** [Kafka `4.0` removed it](https://kafka.apache.org/42/getting-started/upgrade/), so any list that names ZooKeeper as a requirement is out of date.
- **Cloud bills follow different meters.** BigQuery bills by data scanned, Snowflake by credits and Databricks by DBUs. So you can't line the dollar figures up side by side.
- **Free software still costs money to run.** Hadoop, Spark, Flink, Kafka, Cassandra and Trino cost nothing to download. Self-hosting moves the bill to servers and the person who gets paged at 2 a.m.

</TLDR>

We checked prices and release dates on October 8, 2026 against each vendor's or project's own pages. Plans change often, so double-check the vendor's page before you decide.

## So what does "big data" mean?

AWS's ["What is big data?"](https://aws.amazon.com/what-is/big-data/) page describes big data as data management problems, caused by growing volume, velocity and variety of data, that traditional databases cannot solve. Volume means terabytes to petabytes, velocity means how fast data arrives and answers are needed, and variety means many sources and formats.

A "big data tool" is any software that helps with one of those problems. That's a very wide net, so one ranked list would mix wildly different products. Here, we sort them by the job each one does.

![Big data tools do different jobs, such as storing, moving, processing and querying, so most lists compare tools that are not rivals](/img/blog/2026/10/big-data-tools-layers.webp)

The four jobs, in plain words:

- **Store:** keep the data, either in files or in a database built to spread across many machines.
- **Move:** carry data between systems, often as a stream of events (see [what a data pipeline is](/learn/what-is-a-data-pipeline/)).
- **Process:** clean, join and calculate over the data, in batches or as it arrives.
- **Query:** let people ask questions in SQL (the standard database query language) and get answers fast.

## Storage tools: where your data lives

### 1. Apache Hadoop: best for storing and batch processing huge files on your own servers

**At a glance**
- Price: Free under [Apache 2.0](https://raw.githubusercontent.com/apache/hadoop/trunk/LICENSE.txt) (checked Oct 2026); you pay for servers and staff
- Latest: Hadoop `3.5.0`, April 2, 2026, the first stable release of the Hadoop `3.5` line ([Hadoop site](https://hadoop.apache.org/))

Hadoop is really four parts in a trench coat. The first, Hadoop Common, holds shared utilities, and HDFS (the Hadoop Distributed File System) stores files across many machines. YARN (the job scheduler) shares cluster resources, and MapReduce is a system for parallel processing.

If a list calls Hadoop outdated, check its date. We found no primary source that says so, and the project shipped `3.4.3` on February 24, 2026 and `3.5.0` on April 2, 2026 ([Hadoop releases](https://hadoop.apache.org/releases.html)).

**What's good**

- It's free, and you control the machines and the data.
- The [Hadoop site](https://hadoop.apache.org/) says the library is designed to scale from single servers to thousands of machines, each offering local computation and storage.
- The same [site](https://hadoop.apache.org/) says it handles failures at the application layer instead of relying on hardware for high availability, so a cluster of machines that may fail can still serve data.
- Per the [HDFS design page](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html) (checked Oct 2026), the blocks of a file are replicated for fault tolerance, and block size and replication factor can be set per file. A typical block is `128 MB`.
- It keeps shipping. The [Hadoop site](https://hadoop.apache.org/) (checked Oct 2026) says release `3.5.0` (April 2, 2026) holds 485 bug fixes, improvements and enhancements since `3.4`.

**Where it falls short**

- The [HDFS design page](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html) (checked Oct 2026) says a typical file is gigabytes to terabytes and that the emphasis is on high throughput of data access rather than low latency of data access. It adds that HDFS is designed more for batch processing than for interactive use.
- The same [HDFS design page](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html) (checked Oct 2026) says files are write-once (appends and truncates aside) and have strictly one writer at any time, so it is not a place for many writers to edit one file.
- The [HDFS design page](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html) (checked Oct 2026) says a cluster has a single NameNode that manages the file system namespace. [Uber's engineering blog](https://www.uber.com/us/en/blog/uber-big-data-platform/) on its big data platform says HDFS is bottlenecked by NameNode capacity, a limit that usually occurs when data grows beyond ten petabytes and becomes a real issue beyond 50 to 100 petabytes.
- The `3.4.3` release does not include the `bundle.jar` with the AWS SDK that the `s3a` connector (the part that reads S3) needs. The [Hadoop site](https://hadoop.apache.org/) (checked Oct 2026) tells you to download it from Maven Central yourself.

**What users say:** [PeerSpot](https://www.peerspot.com/products/apache-hadoop-reviews) reviewers say, in a March 2025 review, "It scaled well" and, in a December 2023 review, "You have to create and maintain servers on your own, which can be hectic."

**Better choice if** you run your own cluster and your jobs are large batch jobs. If people want quick, interactive answers, look elsewhere.

### 2. Amazon S3: best for file storage with no cluster to run

**At a glance**
- Price: in US East (N. Virginia), S3 Standard storage is $0.023 per GB a month for the first 50 TB, $0.022 for the next 450 TB and $0.021 over 500 TB, per the [AWS S3 price list for US East](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/us-east-1/index.json) (checked Oct 2026)

S3 is AWS object storage, so you pay for the objects you store, at a rate that depends on object size, time stored and storage class.

The same [price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/us-east-1/index.json) has lower rates for other storage classes, for example $0.0125 per GB for S3 Standard Infrequent Access (checked Oct 2026).

**What's good**

- You pay for what you store, and AWS runs the machines. No cluster to babysit.
- AWS's [storage classes page](https://aws.amazon.com/s3/storage-classes/) (checked Oct 2026) says S3 is designed to exceed 99.999999999% (11 nines) data durability. That is a design target, not a guarantee.
- The [S3 user guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html) says S3 gives strong read-after-write consistency for `PUT` and `DELETE` requests in all AWS Regions, and that updates to a single key are atomic.
- The S3 user guide's [upload page](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html) (checked Oct 2026) says one object can be up to `50 TB` when you upload it in parts with the multipart upload API.
- For Iceberg tables, AWS's [S3 pricing page](https://aws.amazon.com/s3/pricing/) says S3 Tables bills on storage, requests and a monitoring fee per object stored in table buckets. That page's worked example is a daily ETL job updating an Apache Iceberg table in a table bucket (checked Oct 2026).

**Where it falls short**

- It stores objects and does not process or query them.
- Requests are billed by type and quantity. S3 Standard `PUT`, `COPY`, `POST` and `LIST` requests are $0.005 per 1,000 and `GET` requests are $0.0004 per 1,000 on the [US East price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/us-east-1/index.json) (checked Oct 2026).
- AWS's [S3 pricing page](https://aws.amazon.com/s3/pricing/) says you pay for all bandwidth into and out of S3, except data coming in from the internet and the first 100 GB a month going out to the internet (counted across AWS services and Regions, China and GovCloud excluded) (checked Oct 2026).
- The same [user guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html) (checked Oct 2026) says there is no way to make atomic updates across keys, so a change that touches several objects is not all-or-nothing.
- The [upload page](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html) (checked Oct 2026) says a single `PUT` uploads up to `5 GB`, and the S3 console tops out at `160 GB` per file.
- Rates depend on region and storage class, and the [pricing page](https://aws.amazon.com/s3/pricing/) examples each name a Region (checked Oct 2026). Check the Region before you budget.

**What users say:** In an April 2026 [Hacker News thread on S3 versus Cloudflare R2](https://news.ycombinator.com/item?id=47700966), one commenter put it this way: "S3 if you're already in the AWS ecosystem. R2 if egress costs are killing you." (Egress just means data transfer out.)

**Better choice if** you want storage you don't operate yourself. HDFS is better if you must keep everything on your own hardware.

### 3. Apache Cassandra: best as an always-on database for application data

**At a glance**
- Price: Free under [Apache 2.0](https://github.com/apache/cassandra/blob/trunk/LICENSE.txt) (checked Oct 2026); you pay for servers and staff
- Latest: Cassandra `5.0.9`, August 7, 2026; the `4.1` line is maintained until the `7.0` release ([Cassandra downloads page](https://cassandra.apache.org/_/download.html))

Cassandra is an open-source NoSQL distributed database. NoSQL loosely means a database outside the classic relational model.

**What's good**

- The [project](https://cassandra.apache.org/) describes itself as built for scalability and high availability, with data spread across many machines. That is the project's own claim.
- Its [architecture docs](https://cassandra.apache.org/doc/5.0/cassandra/architecture/dynamo.html) describe multi-master replication with tunable consistency. Consistency levels run from `ONE` (a single replica must respond) through `QUORUM` (a majority) to `ALL`.
- You choose how many copies to keep. With a replication factor (RF) of `3`, the [architecture docs](https://cassandra.apache.org/doc/5.0/cassandra/architecture/dynamo.html) (checked Oct 2026) say data is written to three distinct replicas.
- The [download page](https://cassandra.apache.org/_/download.html) (checked Oct 2026) lists `5.0` as the latest GA line (`5.0.9`, August 7, 2026), maintained until the `8.0` release. The `4.1` line (`4.1.12`) is maintained until `7.0`.

**Where it falls short**

- Its change data capture (CDC) feature, which copies changes out, [rejects writes to a flagged table](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/cdc.html) (checked Oct 2026) once the CDC log reaches its configured size. So whatever reads that log has to keep draining it, or writes stop. The docs say not to enable CDC without a consumption process in place.
- The [Cassandra data modeling docs](https://cassandra.apache.org/doc/5.0/cassandra/developing/data-modeling/intro.html) (checked Oct 2026) say joins are not supported, so all required fields must sit in a single table. Because each query is backed by a table, data is duplicated across tables (denormalization).
- The [same page](https://cassandra.apache.org/doc/5.0/cassandra/developing/data-modeling/intro.html) (checked Oct 2026) gives a general guideline of under `100,000` values and under `100MB` of disk space per partition, though it says requirements vary by application.
- Concurrent updates to a key are settled by last-write-wins. The [architecture docs](https://cassandra.apache.org/doc/5.0/cassandra/architecture/dynamo.html) (checked Oct 2026) say every mutation is timestamped, deletes included, and the latest version is the winning value.

**What users say:** In an August 2026 [Hacker News thread](https://news.ycombinator.com/item?id=49393923) about ACID (safe, all-or-nothing updates) in Cassandra 6, one commenter said it has "demonstrably better cost and availability" than anything else they tried. Their condition: "as long as you have a competent team".

**Better choice if** you need a database that keeps taking writes across many machines. It is not a reporting tool.

### 4. MongoDB: best for JSON-shaped application data

**At a glance**
- Price: Not covered here. The licence file for the server code in MongoDB's GitHub repository is the Server Side Public License (SSPL), which is not an Apache licence: [MongoDB licence file](https://github.com/mongodb/mongo/blob/master/LICENSE-Community.txt) (checked Oct 2026)

MongoDB stores data as flexible, JSON-like documents. Think of a document as one record, like a row, except it can hold nested fields.

**What's good**

- Its [change streams](https://www.mongodb.com/docs/manual/changeStreams/) let applications follow data changes in real time without tailing the oplog, the database's own change log, by hand.
- Applications can subscribe to all data changes on a single collection, a database or an entire deployment.
- Change streams are resumable. You pass a resume token to `resumeAfter` or `startAfter` when you open the cursor, and the `_id` field of each change event acts as that token.
- Change streams only notify on changes that have persisted to a majority of the data-bearing members in the replica set.
- By default an update event carries only the changed fields (the delta). A stream can be configured to return the most current majority-committed version of the updated document.

**Where it falls short**

- The [change streams docs](https://www.mongodb.com/docs/manual/changeStreams/) (checked Oct 2026) say change streams are restricted to database events. The same page says Atlas Stream Processing has extended functionality.
- The same [change streams page](https://www.mongodb.com/docs/manual/changeStreams/) (checked Oct 2026) lists replica sets and sharded clusters, and says they must use the WiredTiger storage engine and replica set protocol version `1`.
- Per the [change streams docs](https://www.mongodb.com/docs/manual/changeStreams/) (checked Oct 2026), time series collections do not support change streams, because they use an optimized storage format instead of tracking changes at the document level.
- Per the [change streams docs](https://www.mongodb.com/docs/manual/changeStreams/) (checked Oct 2026), resuming needs enough oplog history to find the token. Also, `resumeAfter` cannot resume after an `invalidate` event such as a collection drop or rename, although `startAfter` can start a new stream.
- By default MongoDB sets no minimum oplog retention period and truncates the oldest entries to hold the configured size. The [MongoDB oplog docs](https://www.mongodb.com/docs/manual/core/replica-set-oplog/) (checked Oct 2026) put the WiredTiger default at 5% of free disk space, with a `990 MB` minimum and a `50 GB` maximum.

**What users say:** [PeerSpot](https://www.peerspot.com/products/mongodb-atlas-reviews) reviews cover MongoDB Atlas, the managed service. One says "MongoDB Atlas is our primary database, and we prefer this because of the reliability of MongoDB Atlas". Another (November 2025) says "I would say pricing is an area where MongoDB Atlas could improve".

**Better choice if** your data is naturally nested, such as product catalogs or user profiles. For reports across many tables, a warehouse is the better home.

## Moving and processing: Kafka, Spark and Flink

### 5. Apache Kafka: best for sharing one stream of events between many systems

**At a glance**
- Price: Free under [Apache 2.0](https://github.com/apache/kafka/blob/trunk/LICENSE) (checked Oct 2026); the [Kafka intro](https://kafka.apache.org/intro) says fully managed services are offered by a variety of vendors
- Latest: Kafka `4.3.1`, June 25, 2026 ([Kafka downloads page](https://kafka.apache.org/community/downloads/))

Kafka is an event streaming platform. Programs publish events to it, it stores them durably, and other programs read them back. It's a broker, which means a middle layer between the programs that write events and the ones that read them.

One stale claim is worth fixing. Kafka's [upgrade notes](https://kafka.apache.org/42/getting-started/upgrade/) say "Apache Kafka 4.0 only supports KRaft mode - ZooKeeper mode has been removed", so lists that name ZooKeeper as a Kafka requirement are out of date.

**What's good**

- Many programs can read the same stream without ever knowing about each other.
- The [Kafka intro](https://kafka.apache.org/intro) says events in a topic can be read as often as needed, because they are not deleted after consumption. Retention is a per-topic setting, and a consumer reads a partition's events in the order they were written.
- Copies are built in. The [intro](https://kafka.apache.org/intro) (checked Oct 2026) calls a replication factor of `3` a common production setting, and says a topic can be replicated even across geo-regions or datacenters.
- Kafka Connect imports and exports data as event streams, and the [intro](https://kafka.apache.org/intro) says the community already provides hundreds of ready-to-use connectors.
- Per Kafka's [design docs](https://kafka.apache.org/42/design/design/), Kafka supports exactly-once delivery in Kafka Streams. The transactional producer plus a read-committed consumer can provide it when you read, process and write data on Kafka topics.

**Where it falls short**

- The [Kafka intro](https://kafka.apache.org/intro) (checked Oct 2026) describes Kafka Connect, not the brokers, as the part that imports data from existing systems such as relational databases. For tools that capture database changes, see our [change data capture comparison](/compare/best-change-data-capture-tools/).
- The [design docs](https://kafka.apache.org/42/design/design/) (checked Oct 2026) say Kafka guarantees at-least-once delivery by default. At-most-once means disabling producer retries and committing offsets before processing.
- For exactly-once into outside systems, the same [design page](https://kafka.apache.org/42/design/design/) (checked Oct 2026) notes that many output systems will not support a two-phase commit. The workaround is to store the consumer's offset in the same place as its output.
- Check Kafka's [broker defaults](https://kafka.apache.org/42/configuration/broker-configs/) (checked Oct 2026): automatically created topics get a replication factor of `1`, and the largest record batch allowed is `1048588` bytes (`message.max.bytes`), about `1 MB`.
- The [Kafka downloads page](https://kafka.apache.org/community/downloads/) (checked Oct 2026) says Kafka `4.3.1` fixed a critical Kafka Streams RocksDB native memory leak along with about 15 other issues. The project aims for 3 releases a year, one every 4 months.

**What users say:** A July 2025 [Hacker News thread about Ursa](https://news.ycombinator.com/item?id=44747082), a Kafka alternative, has a commenter calling Kafka "one of the pieces of software that has been rock solid for me". In the October 2025 [Hacker News thread "Kafka is Fast"](https://news.ycombinator.com/item?id=45748198), another says "Managed hosting is expensive to operate and self-managing kafka is a job in of itself."

**Better choice if** several systems must publish and read the same events. If hourly data is fine, a scheduled copy job is simpler.

### 6. Apache Spark: best for large batch jobs and mixed workloads on one engine

**At a glance**
- Price: Free under [Apache 2.0](https://github.com/apache/spark) (checked Oct 2026); you pay for servers and staff
- Latest: Spark `4.2.0`, July 14, 2026; also `4.1.3` and `4.0.4` on July 15 and `3.5.9` on July 16 ([Spark news page](https://spark.apache.org/news/))

Spark is a distributed engine for data engineering, data science and machine learning. It runs on one machine or on a cluster.

**What's good**

- Spark's [docs](https://spark.apache.org/docs/latest/) list batch work, SQL and machine learning on one engine, so there may be fewer tools to learn.
- Spark's [streaming docs](https://spark.apache.org/docs/latest/streaming/index.html) say micro-batch processing, the default for Structured Streaming, achieves end-to-end latencies as low as 100 milliseconds with exactly-once fault-tolerance guarantees.
- The [Structured Streaming guide](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html) (checked Oct 2026) lists three types of time windows: tumbling (fixed), sliding and session. Since Spark `4.0` it encourages the `transformWithState` operator for complex stateful applications.
- Feature releases arrive steadily: `4.0.0` on May 23, 2025, `4.1.0` on December 16, 2025 and `4.2.0` on July 14, 2026, per the [Spark news page](https://spark.apache.org/news/) (checked Oct 2026).

**Where it falls short**

- The [Spark news page](https://spark.apache.org/news/) (checked Oct 2026) lists releases in July 2026 for four lines (`4.2`, `4.1`, `4.0` and `3.5`). Check which line your connectors and cloud service support before you upgrade.
- The [Spark downloads page](https://spark.apache.org/downloads.html) (checked Oct 2026) says Spark `4` is pre-built with Scala `2.13` and support for Scala `2.12` has been officially dropped. Check your Scala version before moving to Spark `4`.
- The [Structured Streaming guide](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html) (checked Oct 2026) says streaming Datasets do not support `limit` or taking the first N rows, or `distinct` operations. Sorting works only after an aggregation in `Complete` output mode.
- Late data needs care. In the [guide's](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html) (checked Oct 2026) 2-hour watermark example, the guarantee is strict in only one direction: data delayed by more than 2 hours is not guaranteed to be dropped, and may or may not get aggregated.
- For stream-stream joins, the [guide](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html) (checked Oct 2026) says you have to define extra join conditions so that indefinitely old inputs cannot match future inputs. Without them the state grows without bound.

**What users say:** [PeerSpot](https://www.peerspot.com/products/apache-spark-reviews) reviewers say "As it uses in-memory data processing, Spark is very fast" and also "Apache Spark is very difficult to use. It would require a data engineer."

**Better choice if** you have large batch jobs, or you want SQL and machine learning in one place. For stateful streams that need low delay, look at Flink.

### 7. Apache Flink: best for stateful, low-delay stream processing

**At a glance**
- Price: Free under [Apache 2.0](https://github.com/apache/flink) (checked Oct 2026); you pay for servers and staff
- Latest: Flink `2.3.0`, June 25, 2026; `1.20.5` is the long-term support line, dated June 3, 2026 ([Flink downloads page](https://flink.apache.org/downloads/))

Flink describes itself as a distributed engine for stateful computations over unbounded and bounded data streams. "Stateful" means it remembers earlier events, such as a running total, while new ones arrive.

**What's good**

- The [project's own site](https://flink.apache.org/) lists low latency and high throughput among its features.
- Flink's [Kafka connector docs](https://nightlies.apache.org/flink/flink-docs-stable/docs/connectors/datastream/kafka/) say Flink reads from and writes to Kafka topics with exactly-once guarantees.
- Big state is allowed. The Flink [state backends docs](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/state_backends/) say that with `EmbeddedRocksDBStateBackend` the state you can keep is limited only by disk space, and that it is currently the only backend with incremental checkpoints.
- There is a long-term support line. The Flink site labels the `1.20` line as LTS, and the [downloads page](https://flink.apache.org/downloads/) (checked Oct 2026) dates `1.20.5` as June 3, 2026, while `2.3.0` (June 25, 2026) is the latest stable release and `2.2.1` came out May 15, 2026.

**Where it falls short**

- The [downloads page](https://flink.apache.org/downloads/) (checked Oct 2026) says the community supports the current and previous minor release with bugfixes, so you upgrade on the project's schedule.
- The [Kafka connector docs](https://nightlies.apache.org/flink/flink-docs-stable/docs/connectors/datastream/kafka/) (checked Oct 2026) say there is no connector (yet) available for Flink version `2.3`, and that Flink's streaming connectors are not part of the binary distribution.
- The default in-memory option has a ceiling. The [state backends docs](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/state_backends/) (checked Oct 2026) say `HashMapStateBackend` is very fast, but its state size is limited by the available memory within the cluster.
- The disk-based option is slower. The same [page](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/state_backends/) (checked Oct 2026) says RocksDB access leads to average performance about an order of magnitude slower than the memory state backends.
- The newer `ForStStateBackend` is, per the [docs](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/state_backends/) (checked Oct 2026), still experimental and not fully available for production.

**What users say:** [PeerSpot](https://www.peerspot.com/products/apache-flink-reviews) reviews of Apache Flink include "Apache Flink makes it easy to write on-the-fly transformations on streaming data". Another reviewer says "We also need to simplify operational procedures, such as developing tools and tuning Flink clusters, as these processes can be quite complex."

**Better choice if** results must update within moments of an event. If batches every few minutes are enough, Spark is simpler.

## Query tools and cloud platforms: answers, on demand

### 8. Trino: best for asking SQL questions across data that lives in many places

**At a glance**
- Price: Free under [Apache 2.0](https://github.com/trinodb/trino/blob/master/LICENSE) (checked Oct 2026); you pay for servers and staff
- Latest: Trino `483`, July 17, 2026 ([Trino release index](https://trino.io/docs/current/release.html))

Trino is a distributed SQL query engine. It reads data where it already sits, in files or other databases, and doesn't keep the data itself.

**What's good**

- Per its docs, one SQL query can reach several systems. The [use cases page](https://trino.io/docs/current/overview/use-cases.html) says Trino can be, and has been, extended to traditional relational databases and sources such as Cassandra.
- The same [use cases page](https://trino.io/docs/current/overview/use-cases.html) says it was designed as an alternative to tools that query HDFS with pipelines of MapReduce jobs, such as Hive or Pig, though it is not limited to HDFS.
- It was designed for data warehousing and analytics, meaning aggregating large amounts of data and producing reports.
- Its [Iceberg connector](https://trino.io/docs/current/connector/iceberg.html) (checked Oct 2026) supports Iceberg table spec versions `1` and `2` and data files in Parquet, ORC or Avro. Catalogs can be a Hive metastore, AWS Glue, JDBC, REST, Nessie or Snowflake.
- The same [connector](https://trino.io/docs/current/connector/iceberg.html) supports `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` and `MERGE` statements on Iceberg tables.

**Where it falls short**

- The [use cases page](https://trino.io/docs/current/overview/use-cases.html) (checked Oct 2026) says Trino "is not a general-purpose relational database" and "was not designed to handle Online Transaction Processing (OLTP)", meaning many small app-style reads and writes.
- Per the [Iceberg connector docs](https://trino.io/docs/current/connector/iceberg.html) (checked Oct 2026), support for Iceberg format version `3` is experimental, and row-level updates, deletes and `OPTIMIZE` are not supported on version `3` tables.
- Writing to encrypted Iceberg tables is not supported, per the [Iceberg connector docs](https://trino.io/docs/current/connector/iceberg.html) (checked Oct 2026).
- The `table_changes` function, which reads row-level changes between two versions of an Iceberg table, does not support tables with delete files, per the [Iceberg connector docs](https://trino.io/docs/current/connector/iceberg.html) (checked Oct 2026).

**What users say:** A Hacker News commenter in the May 2025 [thread "Databricks acquires Neon"](https://news.ycombinator.com/item?id=43982947), who used Trino through AWS Athena, wrote "I really can't speak highly enough of Trino". A September 2025 [GitHub issue](https://github.com/trinodb/trino/issues/26563) on the Trino project reports that queries on Iceberg tables were "taking more than 1 minutes and up to 10 minutes to complete the planning stage".

**Better choice if** your data is already in files and you want SQL over it without loading it elsewhere. A managed warehouse is better if you'd rather not run servers.

### 9. Google BigQuery: best for a serverless warehouse on Google Cloud

**At a glance**
- Price: On-demand queries bill per TiB scanned, and "the first 1 TiB of query data processed per month is free", per [BigQuery pricing](https://cloud.google.com/bigquery/pricing) (checked Oct 2026)

BigQuery is a managed, serverless data warehouse. Serverless means Google runs the machines, so there is no cluster to run.

It also sells reserved capacity under three editions: Standard, Enterprise and Enterprise Plus. The [pricing page](https://cloud.google.com/bigquery/pricing) says on-demand queries generally get up to `2,000` concurrent slots, shared among all queries in a project. It also says the older flat-rate model is no longer offered as of July 5, 2023, so older cost guides may be out of date (checked Oct 2026).

**What's good**

- Google runs the servers, and the free monthly tier covers the first 1 TiB of queries.
- Standard edition slots need no commitment. The [pricing page](https://cloud.google.com/bigquery/pricing) default column lists $0.04 per slot-hour (Enterprise is $0.06), billed per second with a 1-minute minimum. The rendered table does not state its region (checked Oct 2026).
- You can check cost before you pay. Google's [cost best practices docs](https://docs.cloud.google.com/bigquery/docs/best-practices-costs) say a dry run estimates the bytes a query will read, and with a `maximum bytes billed` setting a query over the limit fails without a charge.
- Storage gets cheaper on its own. A table or partition not modified for 90 consecutive days drops to long-term storage, which cuts its price by approximately 50%, and the first 10 GiB of storage each month is free, per the [pricing page](https://cloud.google.com/bigquery/pricing) (checked Oct 2026).
- Enterprise and Enterprise Plus can take a 1-year commitment at a 20% discount or a 3-year commitment at 40%, per Google's [editions page](https://cloud.google.com/bigquery/docs/editions-intro) (checked Oct 2026).

**Where it falls short**

- The on-demand bill follows how much data each query scans, so a query that reads a huge table in full costs real money. We found no self-hosted option in [Google's docs](https://cloud.google.com/bigquery/docs/introduction) (checked Oct 2026).
- A `LIMIT` clause does not cut the bill. The [pricing page](https://cloud.google.com/bigquery/pricing) says you are charged for the data processed in the columns you select even with an explicit `LIMIT`, and the [cost best practices](https://docs.cloud.google.com/bigquery/docs/best-practices-costs) add that on non-clustered tables a `LIMIT` won't reduce compute costs (checked Oct 2026).
- On-demand charges are rounded up to the nearest MB, with a minimum of `10 MB` processed per table a query references and per query, per the [pricing page](https://cloud.google.com/bigquery/pricing) (checked Oct 2026).
- The [editions page](https://cloud.google.com/bigquery/docs/editions-intro) shows the Standard edition has no access to capacity commitments, fine-grained security controls (column-level access, row-level security, data masking), BigQuery ML or VPC Service Controls (checked Oct 2026).
- Capacity (slot) pricing does not apply to streaming inserts or to using the BigQuery Storage API, per the [pricing page](https://cloud.google.com/bigquery/pricing) (checked Oct 2026).

The [pricing page's](https://cloud.google.com/bigquery/pricing) table lists $6.25 per TiB on demand and states no region (checked Oct 2026). At that rate, scanning 10 TiB in a month bills 9 TiB after the free first TiB, so 9 x $6.25 = $56.25. Scanning 100 TiB bills 99 x $6.25 = $618.75.

The bill follows what queries read, not how long anything runs, and the [pricing page's](https://cloud.google.com/bigquery/pricing) own advice is to use partitioning and clustering to read less.

**What users say:** A respondent to the [BARC panel survey](https://barc.com/review/google-bigquery/) (April 2025) wrote "I love using it as a product, but it can get pricey if you handle large datasets."

**Better choice if** you already live in Google Cloud and want no cluster to manage.

### 10. Snowflake: best for a managed warehouse with published per-credit prices

**At a glance**
- Price: $2.00 per credit on Standard, $3.00 on Enterprise and $4.00 on Business Critical, on demand, AWS US East, per the [Snowflake Service Consumption Table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf), effective October 15, 2026 (checked Oct 2026)

In Snowflake, a warehouse is a block of compute, and it uses credits at an hourly rate. For Standard warehouses: Extra Small uses 1, Small 2, Medium 4 and Large 8, according to the [Service Consumption Table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf) (checked Oct 2026). On-demand storage on AWS US East is $23.00 per terabyte per month, per the same [table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf) (checked Oct 2026).

From those published rates: a Medium warehouse (4 credits an hour) running 2 hours a day for 30 days uses 240 credits, or $480 on Standard at $2.00 a credit.

That is compute only. Storage and other charges are extra.

**What's good**

- Prices per credit, by edition and region, are published in one [table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf) (checked Oct 2026). So you can work out compute cost in advance.
- Per Snowflake's [compute cost docs](https://docs.snowflake.com/en/user-guide/cost-understanding-compute), credits are billed per second with a 60-second minimum, and a suspended warehouse does not use any credits.
- Sizes double in cost at each step. The same [table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf) lists Standard warehouses at 1 credit an hour for Extra Small, then 2, 4, 8, 16, 32, 64, 128, 256 and 512 for the 6XL size (checked Oct 2026).
- Ingestion has published rates too. The [table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf) lists Snowpipe at 0.0037 credits per GB, and Snowpipe Streaming (high-performance architecture) at 0.0037 credits per uncompressed GB (checked Oct 2026).
- Snowflake's [Time Travel docs](https://docs.snowflake.com/en/user-guide/data-time-travel) (checked Oct 2026) say a 1-day (24-hour) retention period is automatic for all accounts. On Enterprise Edition and higher, permanent tables can be set from 0 up to 90 days.

**Where it falls short**

- Credit prices vary by region. For example, AWS EU Frankfurt is $2.60 on Standard and $3.90 on Enterprise on the same [table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf) (checked Oct 2026).
- A Time Travel period longer than 1 day requires Enterprise Edition or higher, and the [docs](https://docs.snowflake.com/en/user-guide/data-time-travel) (checked Oct 2026) say extended retention needs extra storage that shows up in your monthly storage charges.
- Cloud services usage is charged only when daily cloud services consumption exceeds 10% of the daily usage of virtual warehouses, per the [compute cost docs](https://docs.snowflake.com/en/user-guide/cost-understanding-compute) (checked Oct 2026). So an account that leans on cloud services can see a charge beyond warehouse hours.
- Gen 2 warehouses list more credits per hour than the standard-warehouse [table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf). It shows Extra Small at 1.35 on AWS and 1.25 on Azure, against 1 for a standard Extra Small (checked Oct 2026).
- Ingestion charges depend on file type. A footnote on the [table](https://www.snowflake.com/legal-files/CreditConsumptionTable.pdf) says text files such as CSV, XML and JSON are charged at uncompressed size, while binary files such as Parquet, Avro and ORC are charged at their observed size regardless of compression (checked Oct 2026).

**Better choice if** you want one managed warehouse and can estimate your hours of compute. If you're fully on Google Cloud, BigQuery is simpler.

### 11. Databricks: best for teams that want managed Spark-style jobs and SQL in one paid platform

**At a glance**
- Price: On AWS, US East, Premium plan: SQL Serverless $0.70, SQL Pro $0.55 and SQL Classic $0.22 per Databricks Unit (DBU), per [Databricks SQL pricing](https://www.databricks.com/product/pricing/databricks-sql) (checked Oct 2026)

Databricks meters compute in DBUs, its own unit. The [warehouse types doc](https://docs.databricks.com/aws/en/compute/sql-warehouse/warehouse-types) says Classic and Pro warehouses keep their compute layer in your own cloud account. On the [pricing page](https://www.databricks.com/product/pricing/databricks-sql), the SQL Serverless price includes cloud instance cost (checked Oct 2026).

**What's good**

- SQL warehouses and jobs are both priced in DBUs on Databricks' [pricing pages](https://www.databricks.com/product/pricing), so one unit covers both (checked Oct 2026).
- Serverless SQL warehouses start quickly. The [SQL warehouse types doc](https://docs.databricks.com/aws/en/compute/sql-warehouse/warehouse-types) puts startup typically between 2 and 6 seconds.
- Its [Iceberg docs](https://docs.databricks.com/aws/en/iceberg/) (checked Oct 2026) say Databricks supports Iceberg tables that use Parquet and versions `1`, `2` and `3` of the Iceberg specification. They can be managed by Unity Catalog or by foreign catalogs such as AWS Glue, Hive metastore or Snowflake Horizon Catalog.
- The same [page](https://docs.databricks.com/aws/en/iceberg/) says managed Iceberg tables can also be created from outside engines that support the Iceberg REST Catalog API, such as Apache Spark, Flink, Trino or Kafka.

**Where it falls short**

- You can't total a monthly bill from the page alone. DBUs per hour for each warehouse size weren't on the [pricing pages](https://www.databricks.com/product/pricing/databricks-sql) we read (checked Oct 2026), so use the vendor's calculator.
- Pro and Classic warehouses are slower to start. The [warehouse types doc](https://docs.databricks.com/aws/en/compute/sql-warehouse/warehouse-types) (checked Oct 2026) says each takes several minutes, typically about 4, and a Classic warehouse's compute layer lives in your own AWS account.
- Plan names shift by cloud. The [SQL pricing page](https://www.databricks.com/product/pricing/databricks-sql) notes that the Premium tier on Azure Databricks corresponds to the Enterprise tier on AWS and GCP, so check the tier before comparing numbers (checked Oct 2026).
- Iceberg has conditions. The [Iceberg docs](https://docs.databricks.com/aws/en/iceberg/) (checked Oct 2026) say foreign Iceberg tables are read-only in Databricks, branching and tagging are not supported, and the [external access page](https://docs.databricks.com/aws/en/external-access/iceberg) says external Iceberg engines can't read views.
- Managed Iceberg tables can only be created if predictive optimization is enabled for table maintenance, and the [docs](https://docs.databricks.com/aws/en/iceberg/) (checked Oct 2026) ask for Databricks Runtime `16.4` LTS or above.

**Better choice if** you want managed jobs and SQL together. If SQL reports are most of your work, compare it with Snowflake, whose pricing table lists credit rates by warehouse size.

## Other names you'll meet

You'll bump into a few more names. Apache HBase and Apache Storm are open-source projects for random-access storage and real-time streams. ClickHouse is a column database for analytics, and Apache Airflow schedules the steps of a pipeline.

Open table formats such as Apache Iceberg, Delta Lake and Apache Hudi sit between files and query engines. Several engines can read the same tables. For those lake layers in more depth, see our [best data lake tools](/compare/best-data-lake-tools/) comparison.

## How to choose: four questions

1. **Is the work batch or real time?** Big batch jobs point to Spark or Hadoop. If results must update within moments of an event, think Kafka with Flink.
2. **Do you want to run servers?** Hadoop, Cassandra, Kafka, Spark, Flink and Trino are free to download but need staff to run. S3, BigQuery, Snowflake and Databricks are run for you, and you pay by meter.
3. **Which cloud are you on?** BigQuery runs on Google Cloud and S3 on AWS. Snowflake and Databricks publish prices by cloud and region, so the same workload can cost different amounts in different places.
4. **Can you estimate the meter?** If you know your hours of compute, credits and DBUs are predictable. If you know the bytes your queries read, the per-TiB model is easier to forecast.

If you can't answer question 4 yet, start on a free tier or a small open-source setup, and don't sign a commitment on a rate you can't turn into a monthly figure.

## Which tool for which situation?

| If you need to... | Start with | Why | Watch out for |
| --- | --- | --- | --- |
| Keep files on your own hardware | Hadoop (HDFS) | You control the machines | Built for large batch files, not quick answers |
| Store files without running servers | Amazon S3 | AWS runs it | Requests and transfer bill separately |
| Run an always-on app database | Cassandra or MongoDB | Built for application data | CDC log limit (Cassandra); change streams limits (MongoDB) |
| Share one event stream | Kafka | Many readers, one stream | Database import goes through Kafka Connect |
| Crunch large batches | Spark | One engine for SQL and machine learning | Releases on four lines in July 2026 |
| React to events in moments | Flink | Stateful stream processing | Upgrade on its support schedule |
| Query files in place | Trino | No loading step | Not for app-style reads and writes |
| Run a managed warehouse | BigQuery, Snowflake or Databricks | No cluster to run | Three different bill meters |
| Copy database tables into Iceberg or Parquet | <img src="/img/logo/olake-blue.svg" alt="" height="20" style={{verticalAlign: 'middle', marginRight: '6px'}} />OLake Go | Open source loader you run yourself | Pair it with a catalog and a query engine |

Most real stacks mix three or four of these. Think files in S3 or HDFS, a stream in Kafka, processing in Spark or Flink, and a query tool on top.

The tools above store, process and query data that already sits somewhere. Getting database data into a lake in the first place is a separate job, and it is the one OLake Go handles. It is our open-source tool, licensed Apache 2.0 ([OLake on GitHub](https://github.com/datazip-inc/olake)).

## Conclusion

Big data tools work as a kit. Figure out whether your problem is storing, moving, processing or querying, then pick one tool for that job, or one platform that bundles several. Read the bill meter as closely as the feature list.
