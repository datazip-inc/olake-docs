## Common Challenges Using Debezium and Kafka Connect for CDC

![Debezium + Kafka architecture: MySQL/MongoDB/Postgres CDC to Kafka, routed to sinks, with setup cost and de-duplication warning](/img/blog/cover/issues-debezium-kafka-cover.webp)

Debezium is an open source change data capture (CDC) project: its connectors read a database's transaction log and turn each committed row change into an event. The [Debezium architecture page](https://debezium.io/documentation/reference/3.7/architecture.html) describes the usual deployment in one line: "Most commonly, you deploy Debezium by means of Apache Kafka Connect." This page lists the problems that setup runs into, with the exact messages each one prints from Debezium 0.9 to 3.7, and a fix that works on Debezium itself.

Where a runbook on this site reproduces a problem in a lab, the section gives the short version and links to the runbook for the full fix. The runbooks quote what their labs captured, with the versions and the date of each run.

**Disclosure.** [OLake Go](/docs/) is an open source alternative to Debezium for loading database changes into Apache Iceberg, and its Iceberg writer began as a fork of [debezium-server-iceberg](https://github.com/memiiso/debezium-server-iceberg), the community Iceberg sink for Debezium Server ([writer source](https://github.com/datazip-inc/olake-go/blob/master/destination/iceberg/olake-iceberg-java-writer/README.md)). None of the fixes on this page needs OLake Go. OLake is not affiliated with the Commonhaus Foundation, which holds the Debezium marks ([trademark policy](https://www.commonhaus.org/policies/trademark-policy/)).

<TLDR title='Key takeaways'>

- `An exception occurred in the change event producer. This connector will be stopped.` is a wrapper. The cause is the last `Caused by:` line in the failed task's `trace`, which the Kafka Connect status call returns.
- Several limits in older guides have moved: Kafka 4.0 runs without ZooKeeper, Debezium 3.3 added exactly-once delivery on Kafka Connect 3.3 or later, and Debezium 3.5 can split one table across snapshot threads.
- The data losses reproduced in the labs behind this page came from a purged binary log, an invalidated replication slot and `errors.tolerance=all` without a dead letter queue. When Kafka itself is down, the Debezium documentation says the connector pauses and resumes where it left off.

</TLDR>

## Debezium, Kafka Connect and Debezium Server {/* #debezium-kafka-connect-and-debezium-server */}

Kafka Connect is the framework, and Debezium supplies source connectors that run inside it. The architecture page calls Kafka Connect "a framework and runtime" for source connectors "such as Debezium that send records into Kafka" and for sink connectors "that propagate records from Kafka topics to other systems". Debezium and Kafka Connect are therefore not alternatives to each other: a Debezium connector is a Kafka Connect plug-in.

Debezium also runs without Kafka Connect. [Debezium Server](https://debezium.io/documentation/reference/3.7/operations/debezium-server.html) is a standalone application whose documentation says it "runs on the Quarkus framework", and it sends events to targets such as Amazon Kinesis, Google Cloud Pub/Sub or Apache Pulsar. The Debezium Engine embeds the same connectors as a library inside a Java application ([architecture](https://debezium.io/documentation/reference/3.7/architecture.html)).

The layers matter when you read an error, because Kafka Connect, Debezium and the database each print their own messages:

| Printed by | Example | Explained in |
| --- | --- | --- |
| Kafka Connect | `Task threw an uncaught and unrecoverable exception. Task is being killed and will not recover until manually restarted` | [Task failed, will not recover](/docs/runbooks/kafka-connect/task-failed-will-not-recover/) |
| Kafka Connect | `Failed to find any class that implements Connector and which name matches ...` | [Connector class not found](/docs/runbooks/kafka-connect/connector-class-not-found/) |
| Debezium | `An exception occurred in the change event producer. This connector will be stopped.` | [The decoder below](#change-event-producer) |
| Debezium | `The db history topic is missing.` | [Section 13](#schema-history-topic) |
| The database, through Debezium | `logical decoding requires wal_level >= logical` | [Section 17](#logical-replication) |

## Decode "An exception occurred in the change event producer" {/* #change-event-producer */}

Debezium wraps many different failures in one line:

```text
org.apache.kafka.connect.errors.ConnectException: An exception occurred in the change event producer. This connector will be stopped.
```

It names no cause. Debezium reads the database log on its own thread, the change event producer, and passes events to Kafka Connect through a queue. When that thread fails, Debezium logs `Producer failure` and the next call from Kafka Connect gets this exception with the real error attached ([`ErrorHandler`](https://github.com/debezium/debezium/blob/v3.7.1.Final/debezium-connector-common/src/main/java/io/debezium/pipeline/ErrorHandler.java) and [`ChangeEventQueue`](https://github.com/debezium/debezium/blob/v3.7.1.Final/debezium-connector-common/src/main/java/io/debezium/connector/base/ChangeEventQueue.java) at 3.7.1).

In the worker log the failure arrives as a short sequence. These lines are from Debezium 3.7.1 on Kafka Connect 4.3.1, in the lab behind the [schema history runbook](/docs/runbooks/debezium/schema-history-topic-missing/), with the timestamps removed and the stored offset shortened:

```text
ERROR  MySQL||binlog  Error during binlog processing. Last offset stored = {...}, binlog reader near position = mysql-bin.000003/686   [io.debezium.connector.binlog.BinlogStreamingChangeEventSource]
ERROR  MySQL||binlog  Producer failure   [io.debezium.pipeline.ErrorHandler]
ERROR  MySQL||lifecycle  WorkerSourceTask{id=inventory-connector-0} Task threw an uncaught and unrecoverable exception. Task is being killed and will not recover until manually restarted   [org.apache.kafka.connect.runtime.WorkerTask]
```

The last line is Kafka Connect's own wrapper, so a Debezium failure is wrapped twice.

### Read the cause from the task status {/* #read-the-cause */}

The connector keeps reporting `RUNNING` and its task goes to `FAILED`. The task's `trace` field holds the whole chain of exceptions, and this command prints it without the stack frames:

```bash
curl -s localhost:8083/connectors/<name>/status | jq -r '.tasks[].trace // empty' | grep -vE '^[[:space:]]+(at |\.\.\. )'
```

For the run above it printed:

```text
org.apache.kafka.connect.errors.ConnectException: An exception occurred in the change event producer. This connector will be stopped.
Caused by: io.debezium.DebeziumException: Error processing binlog event
Caused by: io.debezium.DebeziumException: Error processing row in customers, internal schema size 5, but row size 4 , restart connector with schema recovery mode.
```

Read it from the bottom. The last `Caused by:` line is the cause: the connector's stored table structure had five columns and the binlog row had four, because a column was added while the connector was down ([section 13](#schema-history-topic)).

Failures at start-up skip the wrapper. When the same lab deleted the schema history topic, the trace began directly with `io.debezium.DebeziumException: The db history topic is missing.`, because the task failed while it was starting.

### When the connector restarts itself {/* #retriable */}

A retriable error does not fail the task. In the lab behind the [binlog runbook](/docs/runbooks/mysql/binlog-retention-error-1236/), Debezium 3.0.8 on Kafka Connect 3.9.0 lost its binlog position, kept the task `RUNNING` and repeated these lines about every 15 seconds:

```text
WARN   MySQL|dbserver1|binlog  Retry 1 of unlimited retries will be attempted   [io.debezium.pipeline.ErrorHandler]
WARN   ||  Going to restart connector after 10 sec. after a retriable exception   [io.debezium.connector.common.BaseSourceTask]
```

Kafka Connect logs the exception as `failed to poll records from SourceTask. Will retry operation.` ([`AbstractWorkerSourceTask.java` at 4.3.1](https://github.com/apache/kafka/blob/4.3.1/connect/runtime/src/main/java/org/apache/kafka/connect/runtime/AbstractWorkerSourceTask.java)), so an alert on `FAILED` tasks never fires. When `errors.max.retries` runs out, Debezium logs `The maximum number of <n> retries has been attempted` and raises the `... This connector will be stopped.` version ([`ErrorHandler.java` at 3.7.1](https://github.com/debezium/debezium/blob/v3.7.1.Final/debezium-connector-common/src/main/java/io/debezium/pipeline/ErrorHandler.java)).

## 1. Complex setup and maintenance {/* #setup */}

A Debezium pipeline on Kafka has four moving parts: Kafka brokers, Kafka Connect workers, the Debezium plug-ins installed on those workers, and sink connectors that take the events further. Each has its own configuration, versions and failure modes.

### Kafka no longer needs ZooKeeper

ZooKeeper is not part of a current Kafka cluster. Kafka 3.5 marked it deprecated ([3.5.0 announcement](https://kafka.apache.org/blog/2023/06/15/apache-kafka-3.5.0-release-announcement/)), and the [4.0.0 announcement](https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/) calls 4.0 "the first major release to operate entirely without Apache ZooKeeper".

Kafka now runs in KRaft (Kafka Raft) mode, in which a few servers act as controllers and hold the cluster metadata. The [operations guide](https://kafka.apache.org/43/operations/kraft/#controllers) says "A Kafka admin will typically select 3 or 5 servers for this role" and that combined mode, where one server is both broker and controller, "is not recommended in critical deployment environments". The Debezium labs behind the runbooks on this page ran one Kafka 4.3.1 server in KRaft mode, as broker and controller at once.

### Versions that work together

Debezium publishes what each release series is tested against. For 3.7 the [release page](https://debezium.io/releases/3.7/) lists Java "17+ for connectors" and Kafka Connect "3.1 and later". A plug-in built for a newer Java fails quietly: in a lab, a Kafka Connect 3.2.0 worker on Java 11 did not load the Debezium 3.7.1 PostgreSQL plug-in and logged no warning ([connector class not found, cause 6](/docs/runbooks/kafka-connect/connector-class-not-found/#cause-6-the-plug-in-needs-a-newer-java)).

### Failed to find any class that implements Connector

When a worker has not loaded a plug-in, creating the connector fails with `Failed to find any class that implements Connector and which name matches io.debezium.connector.postgresql.PostgresConnector, available connectors are: ...`. Ask the worker what it loaded with `curl -s localhost:8083/connector-plugins`: if the class is missing, the jars are not where `plugin.path` looks, or the worker was not restarted after the install. The [runbook](/docs/runbooks/kafka-connect/connector-class-not-found/) reproduces seven causes on Kafka Connect 3.2.0 and 4.3.1, starting with `plugin.path` pointing at the folder of jars instead of its parent.

### A connector configuration for Debezium 2.4 and later

Configurations copied from posts written for Debezium 1.x use property names that later versions removed. This MongoDB example uses the names in the 3.7 documentation, where `mongodb.connection.string` "replaces the mongodb.hosts property that was available in previous versions of the MongoDB connector" ([MongoDB connector](https://debezium.io/documentation/reference/3.7/connectors/mongodb.html#mongodb-property-mongodb-connection-string)). It was written from that documentation and was not run in a lab.

```json
{
  "name": "mongodb-connector",
  "config": {
    "connector.class": "io.debezium.connector.mongodb.MongoDbConnector",
    "mongodb.connection.string": "mongodb://localhost:27017/?replicaSet=rs0",
    "mongodb.user": "debezium",
    "mongodb.password": "dbz",
    "topic.prefix": "dbserver1",
    "database.include.list": "mydb",
    "collection.include.list": "mydb.my_collection"
  }
}
```

These renames break configurations written for older versions:

| Old name | New name | Version |
| --- | --- | --- |
| `mongodb.hosts` | `mongodb.connection.string` | New name from 2.0, old name removed in 2.4 |
| `mongodb.name` | `topic.prefix` | 2.0 |
| `database.server.name` | `topic.prefix` | 2.0 |
| `database.history.kafka.topic` | `schema.history.internal.kafka.topic` | 2.0 |
| `table.whitelist`, `database.whitelist` and their siblings | `table.include.list` and its siblings | 1.3, old names removed in 2.0 |
| `snapshot.mode=schema_only` (MySQL) or `never` (PostgreSQL) | `snapshot.mode=no_data` | 2.6, old values removed in 3.3 |
| `snapshot.mode=schema_only_recovery` | `snapshot.mode=recovery` | 2.6 |
| `toasted.value.placeholder` | `unavailable.value.placeholder` | Old name deprecated in 1.9, removed in 2.0 |

Sources: Debezium source at the tags for `CommonConnectorConfig.java` [1.9.7](https://github.com/debezium/debezium/blob/v1.9.7.Final/debezium-core/src/main/java/io/debezium/config/CommonConnectorConfig.java) and [2.0.0](https://github.com/debezium/debezium/blob/v2.0.0.Final/debezium-core/src/main/java/io/debezium/config/CommonConnectorConfig.java), `MongoDbConnectorConfig.java` [2.3.0](https://github.com/debezium/debezium/blob/v2.3.0.Final/debezium-connector-mongodb/src/main/java/io/debezium/connector/mongodb/MongoDbConnectorConfig.java) and [2.4.0](https://github.com/debezium/debezium/blob/v2.4.0.Final/debezium-connector-mongodb/src/main/java/io/debezium/connector/mongodb/MongoDbConnectorConfig.java), and `PostgresConnectorConfig.java` [1.9.7](https://github.com/debezium/debezium/blob/v1.9.7.Final/debezium-connector-postgres/src/main/java/io/debezium/connector/postgresql/PostgresConnectorConfig.java); the [2.0 release notes](https://debezium.io/releases/2.0/release-notes); and the version tables in the [schema history](/docs/runbooks/debezium/schema-history-topic-missing/#the-same-failure-across-versions) and [captures nothing](/docs/runbooks/debezium/connector-running-captures-nothing/#names-and-messages-by-debezium-version) runbooks.

For a full walk-through, see [MongoDB CDC with Debezium and Kafka](/blog/mongodb-cdc-using-debezium-and-kafka/).

### Single message transforms are plug-ins too

Kafka Connect transformations change records on their way through, and the [Kafka documentation](https://kafka.apache.org/43/kafka-connect/user-guide/#transformations) describes them as "lightweight message-at-a-time modifications". A custom single message transform (SMT) is a Java class, and a worker finds it the same way it finds a connector, so it has to be on `plugin.path` on every worker ([runbook](/docs/runbooks/kafka-connect/connector-class-not-found/#a-converter-that-is-not-installed)). What one record at a time cannot do is in [section 8](#transformations).

:::note[How OLake Go handles this]

OLake Go runs each source as its own Docker image, such as `olakego/source-mysql` in the [MySQL connector's check command](/docs/connectors/mysql/#3-check-source-connection), not as a plug-in on a Kafka Connect worker. The PostgreSQL connector page adds that it "can be used within the OLake UI or run locally via Docker for open-source workflows" ([PostgreSQL connector](/docs/connectors/postgres/)).

:::

## 2. High operational overhead {/* #operations */}

A running pipeline means watching the database, Kafka and Kafka Connect. On top of the metrics that Kafka and Kafka Connect expose, the Debezium MySQL connector provides "three types of metrics", for snapshots, streaming and schema history, over Java Management Extensions (JMX) ([monitoring](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-monitoring)).

Two streaming metrics show where lag builds up. `MilliSecondsBehindSource` is the time between a change's timestamp in the database and the connector processing it, and `QueueRemainingCapacity` is the free room in the queue between the connector and Kafka Connect ([streaming metrics](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-streaming-metrics)).

Alert on the task state, not on the connector state. In every run behind the [task failure runbook](/docs/runbooks/kafka-connect/task-failed-will-not-recover/), the connector kept reporting `RUNNING` over a `FAILED` task, and Kafka Connect did not restart the task on its own. The restart calls, which differ by Kafka Connect version, are in [that runbook](/docs/runbooks/kafka-connect/task-failed-will-not-recover/#fix-1-restart-when-the-cause-is-gone).

Adding brokers does not move data by itself. The [operations guide](https://kafka.apache.org/43/operations/basic-kafka-operations/#expanding-your-cluster) says new servers "will not automatically be assigned any data partitions", so existing partitions stay where they are until you move them with `bin/kafka-reassign-partitions.sh`.

## 3. Slow initial snapshot {/* #snapshot */}

By default the initial snapshot reads one table at a time with one thread: `snapshot.max.threads` defaults to `1` ([MySQL](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-property-snapshot-max-threads), [PostgreSQL](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-snapshot-max-threads)). If it is interrupted, the [MySQL documentation](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-snapshots) says "the process restarts after the connector restarts", so a long snapshot that fails near the end starts over.

How far one snapshot can be split depends on the version. The setting has existed since 1.4 ([`CommonConnectorConfig.java` at 1.4.0](https://github.com/debezium/debezium/blob/v1.4.0.Final/debezium-core/src/main/java/io/debezium/config/CommonConnectorConfig.java)), and up to 3.4 each thread reads a whole table, so several tables run at once and one large table still runs alone. From 3.5 a value above `1` also splits each table "into chunks based on primary key ranges"; the 3.7 documentation calls this "an incubating feature", and tables without a primary key or with snapshot select overrides "fall back to single-threaded snapshotting" ([MySQL](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-property-snapshot-max-threads); [`CommonConnectorConfig.java` at 3.5.0](https://github.com/debezium/debezium/blob/v3.5.0.Final/debezium-connector-common/src/main/java/io/debezium/config/CommonConnectorConfig.java)).

Incremental snapshots, added in 1.6 (DBZ-3473 in the [1.6 release notes](https://debezium.io/releases/1.6/release-notes)), read a table in chunks of `incremental.snapshot.chunk.size` rows, 1024 by default, while streaming goes on. The MySQL documentation says "neither operation blocks the other", and an interrupted incremental snapshot "begins at the point where it stopped, rather than recapturing the table from the beginning" ([incremental snapshots](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#debezium-mysql-incremental-snapshots)). You start one with a signal, which is also how a table added to a running connector gets its existing rows.

Locks are a separate question from speed. The MySQL connector's default, `snapshot.locking.mode=minimal`, holds the global read lock "for only the initial phase of the snapshot during which it reads the database schemas and other metadata", while `extended` "Blocks all write operations for the duration of the snapshot" ([MySQL](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-property-snapshot-locking-mode)). The PostgreSQL connector's default in 3.7 is `none`, under which "The connector avoids locks entirely" ([PostgreSQL](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-snapshot-locking-mode)).

One way around a long snapshot is to copy the history with a separate bulk job, for example in Apache Spark, and let Debezium stream only new changes with `snapshot.mode=no_data` (`schema_only` or `never` before 2.6). The bulk copy and the stream then overlap, and the two have to be merged by key into one table.

:::note[How OLake Go handles this]

OLake Go's PostgreSQL connector "offers features like parallel chunking, checkpointing, and automatic resume for failed full loads" ([PostgreSQL connector](/docs/connectors/postgres/)). Its [MySQL](/docs/connectors/mysql/), [MongoDB](/docs/connectors/mongodb/) and [SQL Server](/docs/connectors/mssql/) pages describe the same.

:::

## 4. Schema changes and DDL {/* #schema-changes */}

How a schema change reaches the change stream depends on the database. The MySQL connector reads DDL statements from the binary log and keeps them in its schema history topic. The PostgreSQL connector cannot, because "Logical decoding does not support DDL changes" and so "the connector is unable to report DDL change events back to consumers" ([PostgreSQL limitations](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-limitations)).

### DDL statement couldn't be parsed {/* #ddl-parse-error */}

When the MySQL connector meets a statement its parser cannot read, the task stops with:

```text
io.debezium.text.ParsingException: DDL statement couldn't be parsed. Please open a Jira issue with the statement '...'
```

From Debezium 3.5 the second sentence reads `Please open a GitHub issue at https://github.com/debezium/dbz/issues with the statement '...'` ([`ParsingErrorListener.java` at 3.4.0](https://github.com/debezium/debezium/blob/v3.4.0.Final/debezium-ddl-parser/src/main/java/io/debezium/antlr/ParsingErrorListener.java) and [3.5.0](https://github.com/debezium/debezium/blob/v3.5.0.Final/debezium-ddl-parser/src/main/java/io/debezium/antlr/ParsingErrorListener.java)). On Azure Database for MySQL 5.7 the connector stopped this way on `FLUSH FIREWALL_RULES`: [DBZ-3925](https://redhat.atlassian.net/browse/DBZ-3925) was reported on 1.6.1.Final in August 2021 and fixed in 2.4.0.Alpha1. A [2017 Stack Overflow question](https://stackoverflow.com/questions/46663900) shows the same failure on DDL for stored procedures.

The setting that skips such statements is `schema.history.internal.skip.unparseable.ddl`, called `database.history.skip.unparseable.ddl` before 2.0, and it defaults to `false`. Its description warns that "If skipping is enabled then Debezium can miss metadata changes" ([`SchemaHistory.java` at 3.7.1](https://github.com/debezium/debezium/blob/v3.7.1.Final/debezium-connector-common/src/main/java/io/debezium/relational/history/SchemaHistory.java); [MySQL property](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-property-database-history-skip-unparseable-ddl)), so use it to get past one known statement and then set it back.

### Primary key changes

Changing a primary key has two effects. An `UPDATE` that changes a key value arrives as two events: "the connector sends a DELETE event record for the old key and a CREATE event record for the new (updated) key" ([PostgreSQL primary key updates](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-primary-key-updates)). Changing the key definition itself opens a short window on PostgreSQL, because the connector takes the key columns from Java Database Connectivity (JDBC) metadata and not from the change stream.

The documentation describes the window: "there is a tiny period of time when the primary key information from JDBC is not synchronized with the change event that the logical decoding plug-in generates". Its procedure for a key change ([streaming changes](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-streaming-changes)) is:

1. Put the database or an application into a read-only mode.
2. Let Debezium process all remaining events.
3. Stop Debezium.
4. Update the primary key definition in the relevant table.
5. Put the database or the application into read/write mode.
6. Restart Debezium.

### A new column with a default value

Adding a column on PostgreSQL writes no row changes. The [ALTER TABLE notes](https://www.postgresql.org/docs/current/sql-altertable.html#SQL-ALTERTABLE-NOTES) explain that with a non-volatile default, "the default value is evaluated at the time of the statement and the result stored in the table's metadata", so existing rows are not touched and Debezium has nothing to send. The new column shows up in the change stream with the next insert, update or delete on that table, and a backfill written as `UPDATE` statements arrives as ordinary updates.

On the Debezium mailing list in June 2021, the answer to this question was: "for Postgres, we don't support schema history and so all that gets captured are your typical data change events, i.e. insert / update / delete" ([thread](https://groups.google.com/g/debezium/c/B0S6F_VHCHo)). PostgreSQL's own [restrictions page](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) says the same of logical replication: "The database schema and DDL commands are not replicated."

Whether a sink accepts the new field depends on its own schema evolution settings. For Iceberg tables, the errors that Spark, PyIceberg and Trino print are in [Iceberg schema evolution errors](/docs/runbooks/iceberg/schema-evolution-errors/).

### JSON events and schemas.enable

With Kafka's JSON (JavaScript Object Notation) converter, every event carries its schema next to its payload. The Debezium frequently asked questions (FAQ) page says each event must be "completely self-describing" and that "events represented in JSON are indeed verbose and large" ([FAQ](https://debezium.io/documentation/faq/#why-are-events-so-large)).

The converter settings are `key.converter.schemas.enable` and `value.converter.schemas.enable`, without a final `d`, and `schemas.enable` defaults to `true` ([`JsonConverterConfig.java` at 4.3.1](https://github.com/apache/kafka/blob/4.3.1/connect/json/src/main/java/org/apache/kafka/connect/json/JsonConverterConfig.java)). Setting them to `false` drops the schema from each event, so a consumer needs it from elsewhere. The FAQ's suggestion is a schema registry, where "actual change events only contain the id of the corresponding schema in the registry".

A sink that expects schemas and reads events written without them stops with this message, which is the same at the Kafka [0.10.2.2](https://github.com/apache/kafka/blob/0.10.2.2/connect/json/src/main/java/org/apache/kafka/connect/json/JsonConverter.java) and [4.3.1](https://github.com/apache/kafka/blob/4.3.1/connect/json/src/main/java/org/apache/kafka/connect/json/JsonConverter.java) tags:

```text
JsonConverter with schemas.enable requires "schema" and "payload" fields and may not contain additional fields. If you are trying to deserialize plain JSON data, set schemas.enable=false in your converter configuration.
```

### Schema changes during an incremental snapshot

The PostgreSQL documentation is direct: "The Debezium connector for PostgreSQL does not support schema changes while an incremental snapshot is running." For a change made after the signal and before the snapshot starts, it says to set the pass-through option `database.autosave` to `conservative` ([PostgreSQL incremental snapshots](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-incremental-snapshots)).

The MySQL connector has `incremental.snapshot.allow.schema.changes`, default `false`, which re-reads the current chunk when it detects a schema change; the documentation adds that "Changes to a primary key are not supported" ([MySQL](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-property-incremental-snapshot-allow-schema-changes)). The MongoDB documentation sets a condition on keys, "Incremental snapshots require that the primary key for each table is stably ordered", and advises a key type other than String ([MongoDB](https://debezium.io/documentation/reference/3.7/connectors/mongodb.html#debezium-mongodb-incremental-snapshots)).

### Snapshot mode names

`snapshot.mode` values were renamed in 2.6 and the old ones removed in 3.3: `schema_only` and `never` became `no_data`, and `schema_only_recovery` became `recovery`. Debezium 3.7.1 rejects the old names with `The 'snapshot.mode' value is invalid: Value must be one of ...`, and 1.9.7 rejects the new ones the same way ([runbook](/docs/runbooks/debezium/connector-running-captures-nothing/#the-old-value-on-a-new-version)).

:::note[How OLake Go handles this]

Instead of a schema history topic, OLake Go's MySQL connector recommends `binlog_row_metadata=FULL` "so the binlog carries column metadata. Otherwise OLake reads it from information_schema, which can mis-map columns if a table is altered while a sync is catching up" ([MySQL connector](/docs/connectors/mysql/#3-check-source-connection)). A table changed after CDC started, or incomplete binlog metadata, gives [`Column Count Mismatch: Expected X, Got Y`](/docs/connectors/mysql/#3-column-count-mismatch-expected-x-got-y).

:::

## 5. At-least-once delivery, exactly-once and failover {/* #delivery */}

Debezium's default guarantee is at least once. Its [exactly-once page](https://debezium.io/documentation/reference/3.7/configuration/eos.html) says: "This means that no changes are missed; however, in some cases, a record may be delivered more than once." The [FAQ](https://debezium.io/documentation/faq/#what_happens_when_debezium_stops_or_crashes) explains one case: after a worker crash, the restarted connectors "will begin recording events from the database starting at the position/offset last recorded by the connector before it crashed", and consumers see some events twice.

### Exactly-once delivery from Debezium 3.3

Exactly-once delivery arrived in Debezium 3.3 (DBZ-9177 in the [3.3 release notes](https://debezium.io/releases/3.3/release-notes)) for the MariaDB, MongoDB, MySQL, Oracle, PostgreSQL and SQL Server connectors, and only on Kafka Connect. It needs Kafka Connect 3.3.0 or later in distributed mode, `exactly.once.source.support=enabled` on every worker and `exactly.once.support=required` on the connector ([exactly-once page](https://debezium.io/documentation/reference/3.7/configuration/eos.html)).

It covers what Kafka Connect writes to Kafka, so consumers have to read with `isolation.level=read_committed`; the default, `read_uncommitted`, "will return all messages, even transactional messages which have been aborted" ([consumer configs](https://kafka.apache.org/43/configuration/consumer-configs/#consumerconfigs_isolation.level)). Debezium's page also notes that "it remains unclear whether the implementation is fully correct or if there are edge cases where exactly-once semantics might be violated".

A new snapshot is a different matter. After the binlog runbook's `when_needed` recovery, every row arrived again as a read event, so consumers still have to treat a repeated key as an update ([runbook](/docs/runbooks/mysql/binlog-retention-error-1236/#fix-2-let-debezium-take-a-new-snapshot)).

Incremental snapshots handle their own overlap with the stream: the watermarking strategy exists "to deduplicate events that might be captured by an incremental snapshot and then recaptured after streaming resumes" ([`incremental.snapshot.watermarking.strategy`](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-incremental-snapshot-watermarking-strategy)).

### When the database fails over

PostgreSQL 17 added "the failover of logical slots" ([17.0 release notes](https://www.postgresql.org/docs/release/17.0/)), and Debezium's PostgreSQL connector creates such slots with `slot.failover=true` from 3.0.5 ([`PostgresConnectorConfig.java` at 3.0.4](https://github.com/debezium/debezium/blob/v3.0.4.Final/debezium-connector-postgres/src/main/java/io/debezium/connector/postgresql/PostgresConnectorConfig.java) and [3.0.5](https://github.com/debezium/debezium/blob/v3.0.5.Final/debezium-connector-postgres/src/main/java/io/debezium/connector/postgresql/PostgresConnectorConfig.java)). The Debezium documentation says these slots "enable Debezium to continue reading changes from a new primary server after a failover event, without losing events", and they also need `synchronized_standby_slots` set on the primary ([failover slots](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#enabling-postgresql-failover-slots)).

On PostgreSQL 16 and earlier the connector does not create a failover slot, and whether a slot survives a failover depends on the platform. Azure Database for PostgreSQL, for one, says that on those versions with high availability "logical replication slots aren't preserved during failover events", and points to the PG Failover Slots extension ([Azure limitations](https://learn.microsoft.com/en-us/azure/postgresql/configure-maintain/concepts-logical#limitations)).

### When a Kafka Connect worker fails

When a worker leaves the group, Kafka Connect waits up to `scheduled.rebalance.max.delay.ms`, 5 minutes by default, before it reassigns that worker's connectors and tasks, which "remain unassigned" in the meantime ([Kafka Connect configs](https://kafka.apache.org/43/configuration/kafka-connect-configs/#connectconfigs_scheduled.rebalance.max.delay.ms)). After a crash, the restarted connectors resume from the last recorded offset, which is the duplicate case quoted above.

## 6. Getting changes into a lake or warehouse {/* #sinks */}

Debezium's source connectors stop at Kafka topics, and a sink connector or a consumer takes the events further. Depending on the sink, the [architecture page](https://debezium.io/documentation/reference/3.7/architecture.html) says "you might need to configure the Debezium new record state extraction transformation", which reduces each change event to the row's new state.

Three ready-made routes now exist. Debezium has shipped a JDBC sink connector since 2.2 (DBZ-3647 in the [2.2 release notes](https://debezium.io/releases/2.2/release-notes)), and Debezium Server lists an Apache Iceberg sink that "is a community-maintained, open-source project" kept in a [separate repository](https://github.com/memiiso/debezium-server-iceberg) ([Debezium Server](https://debezium.io/documentation/reference/3.7/operations/debezium-server.html#debezium-server-apache-iceberg-sink-configuration)). Apache Iceberg has shipped its own Kafka Connect sink since [1.5.0](https://iceberg.apache.org/releases/#150-release), with an experimental `DebeziumTransform` for Debezium events ([Iceberg Kafka Connect](https://iceberg.apache.org/docs/latest/kafka-connect/)).

The Iceberg sink's documented features include table creation, schema evolution and exactly-once delivery, but not updates in place. Its tracker says the first version left out the delta writer needed "for features like change data capture and upsert mode", and that issue has been open since August 2024 ([apache/iceberg#10842](https://github.com/apache/iceberg/issues/10842), checked Nov 2026). Until it lands, a current-state table needs a merge job after the sink.

Iceberg-side failures are in the [Iceberg runbooks](/docs/runbooks/iceberg/): schema evolution errors, compaction that rewrites nothing, and Spark sessions that cannot find Iceberg.

:::note[How OLake Go handles this]

OLake Go replicates PostgreSQL, MySQL, MongoDB, Oracle, SQL Server, IBM Db2, Kafka and S3 into Apache Iceberg or Parquet ([supported sources](/docs/connectors/overview/)) with its own writer, the one named in the disclosure at the top of this page. A job writes to the Iceberg or Parquet destination set in its [destination configuration](/docs/core/configs/writer/).

:::

## 7. Kafka dependency and resource consumption {/* #kafka-cost */}

Running Debezium on Kafka Connect means running Kafka: brokers, KRaft controllers, Kafka Connect workers and storage for each topic's retention. [Debezium Server and the Debezium Engine](#debezium-kafka-connect-and-debezium-server) avoid that when the events can go somewhere other than Kafka.

Kafka's own guidance sizes brokers by workload, not by a fixed figure. The [hardware page](https://kafka.apache.org/43/operations/hardware-and-os/) suggests estimating memory as `write_throughput*30` to buffer 30 seconds of writes and says "In general disk throughput is the performance bottleneck, and more disks is better", and the [Java page](https://kafka.apache.org/43/operations/java-version/) shows `-Xmx6g -Xms6g` among "Typical arguments for running Kafka".

As an illustration, three brokers on `m5.2xlarge` and three KRaft controllers on `m5.large`, at on-demand Linux prices in US East (N. Virginia), cost:

| Role | Instance | Price per hour | Three instances for a 730-hour month |
| --- | --- | --- | --- |
| Broker | `m5.2xlarge` | $0.384 | $840.96 |
| Controller | `m5.large` | $0.096 | $210.24 |
| Total | | | $1,051.20 |

Sources: [Amazon Elastic Compute Cloud (EC2) on-demand pricing](https://aws.amazon.com/ec2/pricing/on-demand/) (checked Nov 2026).

Storage, data transfer and the Kafka Connect workers come on top, and the instance types are an example, not a sizing recommendation. Combined mode would drop the three controllers, and the Kafka documentation does not recommend it for critical deployments ([KRaft](https://kafka.apache.org/43/operations/kraft/#controllers)).

## 8. Limited transformation capabilities {/* #transformations */}

Kafka Connect transformations work on one record at a time, which is what "message-at-a-time" means in the [Kafka documentation](https://kafka.apache.org/43/kafka-connect/user-guide/#transformations). Debezium adds its own, such as the new record state extraction that flattens events, and Kafka includes others, such as `Cast` and `RegexRouter`.

A join, an aggregation or anything else that needs state across records is outside what a single message transform can do, so it runs downstream in Kafka Streams, Apache Flink or Apache Spark. Joining change events from two tables into one denormalized table is one example.

## 9. Data loss scenarios {/* #data-loss */}

A Kafka outage pauses the pipeline instead of dropping events. The PostgreSQL connector documentation says that while the brokers are unavailable, "the connector tasks pause until a connection can be re-established, at which point the connectors resume exactly where they left off" ([Kafka becomes unavailable](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-kafka-becomes-unavailable)).

The losses reproduced in the labs behind the runbooks came from other places:

- **A purged binary log.** A MySQL connector was stopped while its binlog file expired, and `snapshot.mode=when_needed` took a new snapshot; the order deleted during the outage never produced a delete event ([binlog runbook](/docs/runbooks/mysql/binlog-retention-error-1236/#fix-2-let-debezium-take-a-new-snapshot)).
- **An invalidated replication slot.** With `max_slot_wal_keep_size` set, PostgreSQL removed write-ahead log (WAL) that the slot still needed, and every reader of the slot then needed a new snapshot ([slot runbook](/docs/runbooks/postgres/replication-slot-filling-disk/#what-an-invalidated-slot-costs)).
- **SQL Server clean-up.** A reader whose saved position fell below the change table's minimum log sequence number (LSN) after the clean-up job ran lost a change for good ([SQL Server runbook](/docs/runbooks/sql-server/enable-cdc-change-tables-empty/#the-range-moves-when-clean-up-runs)).
- **`errors.tolerance=all` on its own.** A sink with that setting and no dead letter queue skipped a bad record that was then gone, with no line in the worker log ([task failure runbook](/docs/runbooks/kafka-connect/task-failed-will-not-recover/#do-not-tolerate-without-a-trace)).

Each of these is visible on the source side before it happens: the WAL each slot retains, the oldest binlog file against the connector's position, and the size of the dead letter queue. The runbooks give the query or command for each.

## 10. Scalability, backpressure and performance settings {/* #performance */}

Debezium reads the log into a queue, and Kafka Connect takes events from it in batches. When the queue is full the connector stops reading, which the documentation describes as backpressure "in cases where the connector ingests messages faster than it can write them to Kafka, or when Kafka becomes unavailable" ([`max.queue.size`](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-max-queue-size)). The backlog then waits in the database log, which on PostgreSQL means WAL held by the replication slot ([section 15](#replication-slot)).

These settings size that path. The defaults are from the 3.7 PostgreSQL connector documentation:

| Setting | Default | What it controls |
| --- | --- | --- |
| `max.batch.size` | 2048 | Events in each batch the connector processes |
| `max.queue.size` | 8192 | Events the queue holds; keep it larger than `max.batch.size` |
| `max.queue.size.in.bytes` | 0, no byte limit | The queue's size in bytes |
| `poll.interval.ms` | 500 | Wait for new events in each poll, capped at 5000 |
| `snapshot.fetch.size` | 10240 | Rows per batch while a snapshot reads a table |
| `incremental.snapshot.chunk.size` | 1024 | Rows per incremental snapshot chunk |
| `snapshot.max.threads` | 1 | Snapshot threads, see [section 3](#snapshot) |

Sources: [Debezium PostgreSQL connector properties](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-max-batch-size) (checked Nov 2026).

Read the metrics from [section 2](#operations) before changing them. A `QueueRemainingCapacity` near zero suggests the Kafka side is the slower one, while a growing `MilliSecondsBehindSource` with room in the queue suggests the connector is not reading the database log fast enough.

On Debezium 1.x with PostgreSQL, the [`wal2json`](https://github.com/eulerto/wal2json) plug-in was an option. Debezium 2.0 removed it, and the [2.0 release notes](https://debezium.io/releases/2.0/release-notes) say "pgoutput decoding plug-in is recommended as the replacement". The `plugin.name` default is still `decoderbufs` in 3.7 ([`plugin.name`](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-plugin-name)).

## 11. Source data types on PostgreSQL {/* #data-types */}

The PostgreSQL connector maps several types to plain strings, so the consumer has to parse them. These mappings are from the [3.7 type tables](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-basic-types):

| PostgreSQL type | Debezium schema | What arrives |
| --- | --- | --- |
| `INT4RANGE`, `INT8RANGE`, `NUMRANGE`, `TSRANGE`, `TSTZRANGE`, `DATERANGE` | `STRING` | The range as text |
| `ENUM` | `STRING`, named `io.debezium.data.Enum` | The value as text; the schema's `allowed` parameter lists the allowed values |
| `INTERVAL` | `INT64` (`io.debezium.time.MicroDuration`) by default | "The approximate number of microseconds", or a string such as `P1Y2M3DT4H5M6.78S` with `interval.handling.mode=string` |
| `POINT` | `STRUCT` (`io.debezium.data.geometry.Point`) | Two `FLOAT64` fields, `x` and `y` |
| Domain types | The type they are based on | Built "based on the full type hierarchy" ([domain types](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-domain-types)) |
| A type the connector does not know | Nothing | Left out with a warning, unless `include.unknown.datatypes=true` ([property](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-include-unknown-datatypes)) |

## 12. TOAST columns and `__debezium_unavailable_value` {/* #toast */}

PostgreSQL stores large values out of line with The Oversized-Attribute Storage Technique (TOAST). The [Debezium documentation](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-toasted-values) states the consequence: "Values that were stored by using the TOAST mechanism and that have not been changed are not included in the message", unless they are part of the table's replica identity.

Debezium puts a placeholder in their place. With the default replica identity, an update to a user's email leaves a large `TEXT` column such as `biography` unchanged, and the `after` part of the event looks like this:

```json
{ "after": { "id": 1004, "first_name": "Dana", "last_name": "Kretchmar", "email": "annek@noanswer.org", "biography": "__debezium_unavailable_value" } }
```

The value comes from `unavailable.value.placeholder`, default `__debezium_unavailable_value` ([property](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-unavailable-value-placeholder)). Before 2.0 it was `toasted.value.placeholder`, with the same default; 1.9 marks that name deprecated and 2.0 removed it ([`PostgresConnectorConfig.java` at 1.2.0](https://github.com/debezium/debezium/blob/v1.2.0.Final/debezium-connector-postgres/src/main/java/io/debezium/connector/postgresql/PostgresConnectorConfig.java) and [1.9.7](https://github.com/debezium/debezium/blob/v1.9.7.Final/debezium-connector-postgres/src/main/java/io/debezium/connector/postgresql/PostgresConnectorConfig.java)).

The placeholder stands for what PostgreSQL itself sends. In the [logical replication lab](/docs/runbooks/postgres/enable-logical-replication/#6-give-every-table-a-replica-identity), an update that did not touch a 32,000-character column arrived from the `test_decoding` plug-in as `body[text]:unchanged-toast-datum`, on all eight PostgreSQL versions run.

There are three ways out, each with a cost:

- `ALTER TABLE ... REPLICA IDENTITY FULL` makes PostgreSQL log the whole old row on every update and delete. The PostgreSQL manual says "replica identity FULL should only be used as a fallback if no other solution is possible" ([publication](https://www.postgresql.org/docs/current/logical-replication-publication.html)).
- From Debezium 2.5, the [reselect columns post processor](https://debezium.io/documentation/reference/3.7/post-processors/reselect-columns.html) queries the source again for columns that carry the placeholder and "fetches their current state" ([class added at 2.5.0](https://github.com/debezium/debezium/blob/v2.5.0.Final/debezium-core/src/main/java/io/debezium/processors/reselect/ReselectColumnsPostProcessor.java)). If the row changed again since, that is a newer value than the change being processed, which is why the connector does not read it by default: the PostgreSQL connector documentation says doing so "would potentially lead to race conditions".
- The consumer can keep the column's previous value whenever the placeholder arrives, which works once it has seen the row.

:::note[How OLake Go handles this]

OLake Go has the same limit. When an update leaves a TOAST column unchanged, "OLake Go writes `__olake_unavailable_value__` for that column"; its **Preserve TOAST Values** option, which can only be set when the source is created, reads the previous value from the Iceberg destination instead ([PostgreSQL connector](/docs/connectors/postgres/#toast-columns-preserve)).

:::

## 13. The db history topic is missing {/* #schema-history-topic */}

A Debezium MySQL connector stops at start-up with this message when its schema history topic is gone and its offsets are not:

```text
io.debezium.DebeziumException: The db history topic is missing. You may attempt to recover it by reconfiguring the connector to recovery.
```

Before 2.6 the sentence ends `... to SCHEMA_ONLY_RECOVERY`, and the topic property is `database.history.kafka.topic` before 2.0 and `schema.history.internal.kafka.topic` after. Versions 1.2 to 3.0 also have `The db history topic or its content is fully or partially missing.` for a topic that exists but lacks records ([runbook](/docs/runbooks/debezium/schema-history-topic-missing/)).

If no table changed structure since the connector last ran, `snapshot.mode=recovery` (`schema_only_recovery` before 2.6) rebuilt the topic in the lab and resumed from the stored offset on Debezium 1.9.7 and 3.7.1, with no rows read twice. After a column was added during the outage, recovery failed with the `internal schema size 5, but row size 4` error from the [decoder](#read-the-cause), and the fix was a new snapshot with the offsets cleared.

The same topic causes `Encountered change event for table inventory.orders whose schema isn't known to this connector` when a table is added to a connector that stores only the captured tables' DDL. The runbook has the documented fix and the topic settings that prevent both errors: one partition and no retention limit.

## 14. Connector is RUNNING but captures nothing {/* #running-captures-nothing */}

A connector and its task can both report `RUNNING` while no events arrive. A [Confluent forum thread from August 2024](https://forum.confluent.io/t/troubleshooting-debezium-connector-intermittent-failures/11300) describes it on Debezium 2.5.0 with Aurora MySQL, and a second user reported the same symptoms on Debezium 1.8 with Kafka 2.7 in November 2024.

The thread's restart call, `POST /connectors/<name>/restart` with no parameters, restarts the connector and leaves its tasks alone. In a lab on Kafka Connect 3.2.0 and 4.3.1 it answered with HTTP (Hypertext Transfer Protocol) status 204 and the task was not started again, while `POST /connectors/<name>/tasks/<id>/restart` restarts a task on every version ([runbook](/docs/runbooks/kafka-connect/task-failed-will-not-recover/#fix-1-restart-when-the-cause-is-gone)).

The [captures nothing runbook](/docs/runbooks/debezium/connector-running-captures-nothing/) reproduces five causes on MySQL and PostgreSQL, each with the command that proves it:

- an include list that matches no table, logged at start-up as `After applying the include/exclude list filters, no changes will be captured. Please check your configuration!`;
- a snapshot mode that reads no existing rows, `no_data` (`schema_only` or `never` before 2.6);
- topics that are never created, with `UNKNOWN_TOPIC_OR_PARTITION` warnings in the log;
- a PostgreSQL publication that lacks the table, which logs nothing;
- a connector with no task, such as the MySQL connector with `tasks.max=2`, which logged `java.lang.IllegalArgumentException: Only a single connector task may be started`.

Correcting the configuration does not replay what was skipped. On MySQL, the rows from before the fix arrived only after the offsets were removed and a new snapshot ran. Old filter names such as `table.whitelist` were ignored without a log line by Debezium 3.7.1, so the connector captured every table.

## 15. PostgreSQL replication slot is filling the disk {/* #replication-slot */}

A logical replication slot keeps all WAL after its `restart_lsn` until its consumer confirms, whether or not anything is connected. In the [runbook's lab](/docs/runbooks/postgres/replication-slot-filling-disk/), a slot that nobody read held 257 MB while `max_wal_size` was 64 MB, and on a 256 MB disk PostgreSQL 18.7 stopped with `PANIC:  could not write to file "pg_wal/xlogtemp.334": No space left on device`.

Find the slot that holds the space, then get its consumer reading again or drop the slot:

```sql
SELECT slot_name, active, restart_lsn, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots ORDER BY slot_name;
```

A slot in use cannot be dropped and answers `ERROR:  replication slot "cdc_slot" is active for PID 3314`. Stop the consumer first, then run `SELECT pg_drop_replication_slot('cdc_slot');`.

For Debezium, the PostgreSQL documentation describes a quiet captured database next to a busy one: "As WAL is shared by all databases, the amount used tends to grow until an event is emitted by the database for which Debezium is capturing changes" ([WAL disk space consumption](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-wal-disk-space)). The fix is a heartbeat: `heartbeat.interval.ms`, which defaults to `0`, with `heartbeat.action.query` writing to a table in the connector's publication. Debezium 3.4 added `lsn.flush.mode` ([3.4 release notes](https://debezium.io/releases/3.4/release-notes)), whose `connector_and_driver` value is meant "to prevent WAL growth on low-activity databases where monitored tables have infrequent changes" ([`lsn.flush.mode`](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-property-lsn-flush-mode)).

`max_slot_wal_keep_size` (PostgreSQL 13 and later) caps what a slot may hold, at the price of the slot. Once it is invalidated, a streaming reader gets `cannot read from logical replication slot "cdc_slot"` on 13 to 15, `can no longer get changes from replication slot "cdc_slot"` on 16 and 17, or `can no longer access replication slot "cdc_slot"` on 18, and has to start over from a new snapshot.

:::note[How OLake Go handles this]

OLake Go reads the same kind of slot, so it has the same limit. Its PostgreSQL connector uses a `pgoutput` slot that "retains WAL segments until read", and its documentation warns against sharing one slot or publication between jobs ([PostgreSQL connector](/docs/connectors/postgres/#configuration)).

:::

## 16. MySQL binlog purged: error 1236 {/* #binlog-1236 */}

MySQL removes binary log files when they expire or on `PURGE BINARY LOGS`, without checking whether a stopped reader still needs them. A Debezium connector whose position is gone reports it differently by version ([runbook](/docs/runbooks/mysql/binlog-retention-error-1236/)):

| Debezium | What the task does and says |
| --- | --- |
| 1.9 to 2.5 | `FAILED` at start: `The connector is trying to read binlog starting at ..., but this is no longer available on the server. Reconfigure the connector to use a snapshot when needed.` |
| 2.6 to 3.1 | Stays `RUNNING` and retries: `Could not find first log file name in binary log index file Error code: 1236; SQLSTATE: HY000.` |
| 3.2 and later | `FAILED` at start: `The connector is trying to read change stream starting at ..., but this is no longer available on the server. Reconfigure the connector to use a snapshot mode when needed.` |

A MySQL replica in the same position reports `Got fatal error 1236 from source when reading data from binary log: 'Could not find first log file name in binary log index file'` on 8.0.33 and later, `from master` on older versions, and its `Last_IO_Errno` was 13114 on 8.0.46 and 8.4.13.

The fix that worked on Debezium 1.9.7, 3.0.8 and 3.7.1 was `snapshot.mode=when_needed`: every row arrived again, and a delete made during the outage was lost. To prevent it, keep binary logs longer than the longest stop you plan for, with `binlog_expire_logs_seconds` on MySQL 8.0 and 8.4 (default 2592000, which is 30 days) or `expire_logs_days` on 5.7, and set `heartbeat.interval.ms` so a quiet connector's stored position keeps moving.

:::note[How OLake Go handles this]

OLake Go reads the same binary log and has the same limit. Its connection check includes an optional `binlog_retention` test with a recommended value of 7 days or more, and explains: "If a sync is paused longer than the retention window, the logs it needs are purged and a full resync is required" ([MySQL connector](/docs/connectors/mysql/#3-check-source-connection)).

:::

## 17. PostgreSQL logical replication prerequisites {/* #logical-replication */}

Debezium's PostgreSQL connector reads through logical decoding, and each missing prerequisite has its own error. The [runbook](/docs/runbooks/postgres/enable-logical-replication/) captured them on PostgreSQL 12 to 18 and the 19 release candidate:

| Missing | Message |
| --- | --- |
| `wal_level = logical` | `logical decoding requires wal_level >= logical` (12 to 16), `logical decoding requires "wal_level" >= "logical"` (17, 18). Changing it needs a restart |
| The `REPLICATION` attribute | `must be superuser or replication role to use replication slots` (12 to 15), `permission denied to use replication slots` (16 and later) |
| A free slot | `all replication slots are in use` |
| The publication | `publication "cdc_publication" does not exist` (12 to 17); 18 logs `skipped loading publication "cdc_publication"` instead |
| A replica identity | `cannot update table "events_nopk" because it does not have a replica identity and publishes updates`, raised in the application and not in Debezium |

The output plug-in is the one Debezium users meet by default: `plugin.name` defaults to `decoderbufs`, a separate package, while `pgoutput` ships with PostgreSQL 10 and later and needed nothing installed in the lab. On the minor releases of 13 August 2026 and later, a third-party plug-in also has to be listed in `output_plugin_libraries`, or the server answers `library "wal2json" may not be used as an output plugin` ([runbook, step 5](/docs/runbooks/postgres/enable-logical-replication/#5-choose-an-output-plugin)).

## 18. SQL Server change tables stay empty {/* #sql-server-cdc */}

Debezium's SQL Server connector reads the change tables that SQL Server's capture job fills, and that job runs under SQL Server Agent. With the Agent stopped, `sys.sp_cdc_enable_db` and `sys.sp_cdc_enable_table` still succeed, and the only hint is `SQLServerAgent is not currently running so it cannot be notified of this action.` ([runbook](/docs/runbooks/sql-server/enable-cdc-change-tables-empty/)).

Debezium logs `No maximum LSN recorded in the database; SQL Server Agent is not running` from 2.0, and `No maximum LSN recorded in the database; please ensure that the SQL Server Agent is running` in 1.9. A new column needs a second capture instance, and a table can have two at most.

Connections use Secure Sockets Layer (SSL) encryption by default: "By default, JDBC connections to Microsoft SQL Server use SSL encryption". Setting `driver.encrypt` to `false` turns that off for a server without SSL ([encrypting connections](https://debezium.io/documentation/reference/3.7/connectors/sqlserver.html#_encrypting_connections)).

## 19. Miscellaneous {/* #misc */}

### One task per connector

The MySQL and PostgreSQL connectors run a single task. The [MySQL documentation](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-property-tasks-max) says "Because the MySQL connector always uses a single task, changing the default value has no effect", yet in a lab `tasks.max=2` left the MySQL connector with no task at all ([runbook](/docs/runbooks/debezium/connector-running-captures-nothing/#tasksmax-above-1-on-the-mysql-connector)). The SQL Server connector is the exception: with several databases in `database.names`, `tasks.max` can go up to their number ([SQL Server](https://debezium.io/documentation/reference/3.7/connectors/sqlserver.html#sqlserver-property-tasks-max)).

### Active Directory and Microsoft Entra sign-in

The SQL Server connector documents directory sign-in through the Microsoft JDBC driver. `driver.authentication` takes values such as `ActiveDirectoryManagedIdentity`, with the note "Use this property to configure Microsoft Entra authentication when connecting to Azure SQL Database", and Kerberos is set up through pass-through properties ([`driver.authentication`](https://debezium.io/documentation/reference/3.7/connectors/sqlserver.html#sqlserver-property-driver-authentication)).

### Table names with dots in snapshot signals

In an incremental snapshot signal, a table name that contains a dot, a space or another non-alphanumeric character has to be quoted. The MySQL documentation's example for a table `My.Table` in the `db1` database is `"db1.\"My.Table\""` ([triggering an incremental snapshot](https://debezium.io/documentation/reference/3.7/connectors/mysql.html#mysql-triggering-an-incremental-snapshot)).

### Unbalanced load across tables

PostgreSQL hands committed transactions to the connector one at a time: "Concurrent transactions are decoded in commit order" ([output plug-in callbacks](https://www.postgresql.org/docs/current/logicaldecoding-output-plugin.html#LOGICALDECODING-OUTPUT-PLUGIN-CALLBACKS)). A large transaction on one table therefore delays changes to every table committed after it. Splitting tables across connectors gives each connector its own order, since "each connector requires a unique replication slot and publication" ([multiple connectors](https://debezium.io/documentation/reference/3.7/connectors/postgresql.html#postgresql-deploying-multiple-connectors)).
