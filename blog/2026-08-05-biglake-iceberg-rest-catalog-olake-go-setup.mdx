:::info[TL;DR]
Apache Iceberg 1.10 made BigQuery a native Iceberg catalog, so OLake Go can write Iceberg tables straight into Google BigLake and have BigQuery read them from the same catalog, no Pub/Sub bridge or synced copy. To set it up: create a BigLake catalog (single- or multi-bucket) on the GCP side, grant the service account its BigLake and Storage roles, then configure an OLake Go Iceberg destination with the REST catalog type set to Big Lake. [Skip to setup](#getting-biglake-ready).
:::

For most of Apache Iceberg's history, BigQuery could read Iceberg tables, but it could not own them. The tables themselves were still managed elsewhere, by a Hive Metastore, AWS Glue, or an outside REST catalog. BigQuery was a consumer, not the source of truth.


Apache Iceberg 1.10.0 changed that. Google contributed two things to the release. The first is a native BigQuery Metastore Catalog (`BigQueryMetastoreCatalog` and `BigQueryMetastoreClient`), merged through [PR #12808](https://github.com/apache/iceberg/pull/12808), which lets Spark, Flink, Trino, and any other Iceberg-aware engine use BigQuery's own metadata service as the catalog of record. The same catalog was added to the Iceberg Kafka Connect runtime bundle, so streaming pipelines get it too.

![BigLake Iceberg REST catalog architecture: OLake Go writing Iceberg data and metadata to Cloud Storage, registered in the BigLake catalog, and read by BigQuery and other engines](/img/blog/2026/5/bigquery-native-catalog.webp)

The second is `GoogleAuthManager`, which plugs Google credentials into the standard Iceberg REST catalog path. That second piece is what this post relies on. Google now recommends the BigLake Iceberg REST catalog endpoint for new setups and describes the BigQuery Metastore Catalog as the earlier integration, so the destination below points at the REST endpoint and authenticates through `GoogleAuthManager`.

## BigLake: A Governance Layer

BigLake is easiest to understand as a governance layer rather than a storage layer. A BigLake Iceberg table is a governed pointer to Iceberg data and metadata sitting in Cloud Storage, not a copy of it inside BigQuery. BigLake applies Google Cloud IAM controls to that data and exposes it through the Iceberg REST catalog, so compatible engines can access it directly.

One caveat worth knowing up front: row-level security and column masking are available on BigLake external tables generally, but Google documents fine-grained access control as unsupported for tables managed through the Iceberg REST catalog endpoint. Access control on those tables runs through IAM at the catalog, namespace, and table level instead.

Google also offers a separate BigLake managed table type, with its own compaction and full DML support, which this post does not use. Tables registered through the Iceberg REST catalog endpoint, the ones OLake Go writes to, cannot be created or modified with BigQuery DDL or DML, and writes come from the external engine instead. Worth knowing since Google's documentation covers both table types under the same product name.

The part that matters most here is the serverless metadata service sitting behind all of it, which Google now calls the Lakehouse runtime catalog. It is a shared runtime metadata layer for both BigQuery and open engines like Spark, so a table written from Spark can be read from BigQuery, and vice versa, without a separate metastore or a second copy of the schema. IAM policies on the catalog apply no matter which engine touched the table last. One copy of data, one schema, readable and writable from wherever a job happens to run.

## The Gap This Closes

BigQuery and external engines never shared the same Iceberg catalog, so connecting them meant working around that gap rather than through it.

A common setup: Spark writes Iceberg data to GCS using AWS Glue as the catalog, then BigQuery creates an external table pointing at that metadata file. Every data change means re-pointing BigQuery at the new metadata file, often through a Pub/Sub trigger watching the bucket.

With the BigQuery Metastore Catalog and the BigLake Iceberg REST catalog, BigQuery and the other query engines now read and write through the same catalog. No re-pointing step, no synced copy, one catalog every engine talks to directly.

The rest of this post covers what that looks like in practice:

- what to set up on the Google Cloud side before touching OLake Go
- how to configure OLake Go's BigLake destination, field by field
- what a passing connection test actually confirms, and what it does not
- how to confirm the tables landed, by querying them from BigQuery
- the failure modes worth knowing about, and how to tell them apart

## Getting BigLake Ready

Before touching OLake Go, the catalog needs to exist on the Google Cloud side.

**Project and API:** A Google Cloud project with billing enabled and the BigLake API turned on.

**Cloud Storage bucket:** A bucket to hold Iceberg table data and metadata.

**Create the catalog:** BigLake offers two catalog types, and OLake Go supports both. Pick the one that matches how you want the catalog scoped, then follow that tab through the rest of this post.

<Tabs>
<TabItem value="single" label="Single-bucket" default>

The catalog is tied to one bucket, and the catalog ID matches the bucket name.

```bash
gcloud biglake iceberg catalogs create BUCKET_NAME \
    --project PROJECT_ID \
    --catalog-type gcs-bucket \
    --credential-mode end-user
```

</TabItem>
<TabItem value="multi" label="Multi-bucket">

One catalog can span multiple buckets, with the catalog name independent of any single bucket. This is Google's general recommendation.

```bash
gcloud biglake iceberg catalogs create CATALOG_ID \
    --project PROJECT_ID \
    --catalog-type biglake \
    --default-location gs://BUCKET_NAME \
    --credential-mode end-user
```

</TabItem>
</Tabs>

**Grant roles.** The service account OLake Go uses needs these roles:

| Role | IAM ID | Scope | Purpose |
| --- | --- | --- | --- |
| BigLake Admin | `roles/biglake.admin` | Project | Catalog management and registering tables |
| BigLake Editor | `roles/biglake.editor` | Project | Writing table data |
| BigLake Viewer | `roles/biglake.viewer` | Project | Reading table data |
| Storage Object User | `roles/storage.objectUser` | Every bucket the catalog touches | Object-level read/write in Cloud Storage |

Google's [Lakehouse documentation](https://docs.cloud.google.com/lakehouse/docs/set-up-lakehouse-iceberg-rest-catalog) covers catalog creation and IAM setup in full. Once the catalog exists and the roles are granted, the rest happens on the OLake Go side.

## Configuring OLake Go To Write Into BigLake

BigLake catalog support ships in OLake Go 0.9.1 and above, so confirm the version before configuring the destination.

Set up the source as usual first (any of OLake Go's supported databases, Kafka, or S3 work here). Then, when configuring the destination, select the Iceberg writer and choose **Big Lake** from the Catalog Type dropdown. The form then shows the BigLake fields (REST Catalog URI, BigLake Catalog Path, GCP Service Account JSON, and so on).

BigLake only supports one authentication path: Google OAuth through a service account. There is no token or generic OAuth2 option here the way there is for other REST catalogs.

The fields that matter:

| Field | Value |
|-------|-------|
| `catalog_type` | `biglake` |
| `rest_catalog_url` | `https://biglake.googleapis.com/iceberg/v1/restcatalog` |
| `iceberg_s3_path` | The BigLake catalog path. |
| `rest_auth_type` | `org.apache.iceberg.gcp.auth.GoogleAuthManager` |
| `gcp_service_account_json` | The full JSON content of the service account key |
| `gcp_project_id` | Required for multi-bucket catalogs only. Identifies the GCP project for request routing and billing. |
| `catalog_name` | Defaults to `olake_iceberg` if left blank. Lowercase letters and underscores only. |
| `gcp_auth_scopes` | Defaults to `https://www.googleapis.com/auth/cloud-platform` |
| `arrow_writes` | Optional. Writes data and delete files via the Arrow-based writer. Defaults to `false`. |

`iceberg_s3_path` and the destination JSON both differ by catalog type:

<Tabs>
<TabItem value="single" label="Single-bucket" default>

`iceberg_s3_path` is `gs://<BUCKET_NAME>`. The catalog name is locked to that bucket's name, and `gcp_project_id` is not needed.

```json
{
  "type": "ICEBERG",
  "writer": {
    "catalog_type": "biglake",
    "rest_catalog_url": "https://biglake.googleapis.com/iceberg/v1/restcatalog",
    "catalog_name": "olake_iceberg",
    "iceberg_s3_path": "gs://<BUCKET_NAME>",
    "rest_auth_type": "org.apache.iceberg.gcp.auth.GoogleAuthManager",
    "gcp_service_account_json": "{ \"type\": \"service_account\", ... }",
    "arrow_writes": false
  }
}
```

</TabItem>
<TabItem value="multi" label="Multi-bucket">

`iceberg_s3_path` is `bl://projects/<PROJECT_ID>/catalogs/<CATALOG_ID>`, which keeps the catalog name independent of any single bucket. Multi-bucket also requires `gcp_project_id`.

```json
{
  "type": "ICEBERG",
  "writer": {
    "catalog_type": "biglake",
    "rest_catalog_url": "https://biglake.googleapis.com/iceberg/v1/restcatalog",
    "catalog_name": "olake_iceberg",
    "iceberg_s3_path": "bl://projects/<PROJECT_ID>/catalogs/<CATALOG_ID>",
    "rest_auth_type": "org.apache.iceberg.gcp.auth.GoogleAuthManager",
    "gcp_service_account_json": "{ \"type\": \"service_account\", ... }",
    "gcp_project_id": "<PROJECT_ID>",
    "arrow_writes": false
  }
}
```

</TabItem>
</Tabs>

## What Happens When You Test The Connection

Clicking Create on the destination does not run a sync. It checks two things: that OLake Go can reach the BigLake REST endpoint, and that the service account credentials in `gcp_service_account_json` are valid and scoped for it.

A successful test confirms the network path and the authentication are both sound. It does not confirm the service account can actually write to the specific catalog or bucket named in `iceberg_s3_path`, since that permission check happens on the first real write, not at connection time. So a passing test but a failing first sync usually means bucket-level permissions, not bad credentials.

From here, the flow is the same as any other OLake Go destination: configure the streams to sync, run discover, and start the job. Once a sync completes, the tables are queryable straight from BigQuery, since OLake Go registered them with the same catalog BigQuery reads from. Confirm it with a four-part identifier:

```sql
SELECT * FROM `PROJECT_ID.CATALOG_ID.NAMESPACE.TABLE_NAME` LIMIT 10;
```

Rows coming back means the catalog registration and the storage write both worked.

## Troubleshooting

Most setup issues fall into one of three categories.

**Authentication and permission errors:** The connection test passes, but a sync fails partway through, or write operations are rejected. This almost always means a missing storage role. Check Storage Object User on the buckets for the service account in `gcp_service_account_json`, then rule out BigLake Editor on the project. Re-check the roles against the prerequisites rather than assuming the credentials themselves are wrong.


**Connection test fails outright:** Before assuming a credentials problem, confirm the BigLake API is enabled on the project, and that the service account key in `gcp_service_account_json` is valid, complete JSON, not rotated or revoked since you pasted it. The REST endpoint is a public Google API, so reachability is rarely the issue. It usually turns out to be project configuration, not the network.

## Wrap-up

Native catalog support closes a real gap that used to require a Pub/Sub bridge and a second copy of the metadata. Setting OLake Go up to write directly into BigLake is just the usual source configuration plus a REST catalog destination pointed at Google's endpoint. The one prerequisite is the GCP-side setup: bucket, catalog, and service account roles in place first.

If something does not line up on the first attempt, the OLake Slack community is a fast way to get unblocked; most setup issues come down to a missing IAM role or a mismatched catalog path format, both of which are quick fixes once identified.

And once you're happy with your BigLake setup and ready to expand your pipeline to other sources or destinations, check out our [other connector guides here](https://olake.io/docs/connectors/).
