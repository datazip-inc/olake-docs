## OLake Go Architecture, How did we do it?

![Diagram showing database sync flow: snapshot/CDC extraction, chunking, transform, Amazon S3, and writing to lakehouse](/img/blog/cover/olake-architecture-cover.webp)

**Updated 27 November 2026** to match OLake Go v1.2.2.

When building [OLake Go](/), our goal was simple: *Fastest DB to Data LakeHouse (Apache Iceberg to start) data pipeline.*

Check out the GitHub repository for OLake Go - [https://github.com/datazip-inc/olake-go](https://github.com/datazip-inc/olake-go)

Over time, many of us who’ve worked with data pipelines have dealt with the toil of building one-off ETL scripts, battling performance bottlenecks, or worrying about vendor lock-in.

With OLake Go, we wanted a clean, open-source solution that solves these problems in a straightforward, high-performing manner.

In this blog, I'm going to walk you through the architecture of OLake Go: how we capture data from databases, Apache Kafka and Amazon S3, write it to object storage as Apache Iceberg tables or plain Parquet files, and handle everything from schema evolution to high-volume parallel loads.

## Architectural Overview

At a high level, OLake Go reads from eight source systems and writes directly to Apache Iceberg tables or plain Parquet files. The files can live on local disk, Amazon S3 (or an S3-compatible store), Google Cloud Storage (GCS) or Azure storage. Our architecture is built around these components:

**Components**

* **CLI (*Command Line Interface*) and [OLake UI](/docs/install/olake-ui)**, a web user interface (UI) that runs the same commands through Temporal
    
* **Framework (Core sync engine)**
    
* **Connectors (Drivers)**
    
* **Writers**
    
* **Testing Setup**
    
    * **Unit Testing**
        
    * **Integration Testing**
        
        * **Workflow testing**
            
        * **Time limit based testing to maintain the performance**
            
* **Monitoring & Alerting**
    

We wanted to keep these components as modular as possible so each one can excel at its responsibilities. Here’s a simplified conceptual diagram showing how data flows through OLake Go.

![Architecture of a data platform: UI, connectors and logic, Colake framework modules, writing to a lakehouse](/img/blog/2025/01/olake-architecture-1.webp)

Here’s how it all ties together:

1. **Initial Snapshot (full load)**: The driver splits each table or collection into chunks and reads them in parallel. Each chunk is a bounded query, such as a `ctid` range in PostgreSQL or an `_id` range in MongoDB.
    
2. **Change Data Capture (CDC)**: After completing the snapshot, OLake Go reads the source's change log for near real-time updates: MongoDB change streams (built on the oplog), the PostgreSQL write-ahead log (WAL), the MySQL binlog or SQL Server CDC tables. For any record changes that occurred during the snapshot process, CDC reflects those changes as well just as initial snapshot finishes and from then on it continues to capture any other changes that occur in your source database (depending on your scheduled time).
    
3. The users have an option to set the number of parallel running threads (`max_threads` in the source config) so you can decide what's the optimal configuration for you in terms of **speed vs load** on your source database.
    
4. **Transformation & Normalization**: With normalization on, top-level fields become columns and nested objects are stored as JSON (JavaScript Object Notation) strings. With it off, each record is stored as JSON in a single `data` column. Normalization is set per stream in `selected_streams.json`.
    
5. **Integrated Writes**: We write the transformed data into destinations with minimal overhead.
    
6. **Monitoring & Alerts**: Each sync reports its progress (records synced, speed, estimated time remaining) in a `stats.json` file. OLake UI sends webhook alerts to Slack, Microsoft Teams or any other webhook endpoint when a job fails.
    
7. **Logs:** View logs to exactly know what the processes are doing under the hood.
    
8. **Full refresh specific table** - so you can quickly update a particular high priority table you need to sync immediately.
    
9. **Testing support** - Built in testing framework for normal sync tests, connection check for different flavours of the source databases.
    

## Drivers (Connectors)

In OLake Go, each Driver (also called a Connector) embeds the logic necessary to interact with a particular source system. We started with MongoDB, and there are now eight drivers: PostgreSQL, MySQL, MongoDB, Oracle, SQL Server, IBM Db2, Apache Kafka and Amazon S3 ([all sources](/docs/connectors/overview)).

Each driver ships as its own Docker image, `olakego/source-<type>`, with its own dependencies. The Driver's job is to:

* **Perform Full Load**: Issue queries to fetch an entire table or collection efficiently. We divide it into multiple chunks and process them in parallel for faster replication. How a driver picks chunk boundaries depends on what the source exposes:
    
    * MongoDB: `splitVector` by default, `$bucketAuto` when `splitVector` is not allowed or the `_id` values are not all ObjectIDs, and an opt-in timestamp strategy.
        
    * PostgreSQL: `ctid` (physical row location) ranges, or ranges on a primary-key column you choose.
        
    * MySQL, SQL Server and Db2: primary-key ranges, with a fallback for tables that have no primary key.
        
    * Oracle: ROWID ranges.
        
    * S3: groups of files.
        
* **Manage CDC**: Read changes from the source's own log.
    
    * PostgreSQL: a logical replication slot with the `pgoutput` plugin.
        
    * MySQL and MariaDB: the binlog, with Global Transaction Identifier (GTID) checkpoints on MySQL since v1.1.2.
        
    * MongoDB: change streams, which read from the oplog.
        
    * SQL Server: CDC change tables.
        
    * Kafka: topics are read continuously through consumer groups, with JSON and Avro messages and an optional upsert mode.
        
    * We let the initial snapshot finish and then capture incremental changes so we never miss any updates that happen while the snapshot is in progress.
        
* **Run Incremental Syncs**: Read only the rows whose cursor column (for example `updated_at`) moved past the last saved value. Oracle and Db2 keep up this way after the full load, since they have no CDC in OLake Go today. S3 uses each file's last-modified time as the cursor.
    

If someone adds a new table or collection after months of running the pipeline, OLake Go runs a full load for that stream only. The saved CDC position of the existing streams is kept, so they are not loaded again.

For a closer look at how each driver chunks, see [What makes OLake Go fast](/blog/what-makes-olake-fast) and the [OLake Go architecture deep dive](/blog/olake-architecture-deep-dive).

## Destinations

Our Destinations are tightly integrated so data can flow directly from the Driver into the destination, eliminating unnecessary read-and-write cycles to local disk. Two Writers ship today:

* **Apache Iceberg**: tables on S3 or an S3-compatible store such as MinIO, on GCS, or on Azure Data Lake Storage. Tables are registered in AWS Glue, a REST catalog (Polaris, Lakekeeper, Nessie, Unity Catalog, BigLake, S3 Tables or Snowflake Horizon), Hive Metastore or a Java Database Connectivity (JDBC) catalog. See the [catalog setup docs](/docs/writers/iceberg/catalog/rest).
    
* **Parquet**: plain Parquet files on local disk, S3, GCS or Azure Blob Storage (Azure since v1.1.0), with [partitioning](/docs/writers/parquet/partitioning) by column values.
    

The Iceberg writer works in two parts. The Go process starts a Java sidecar that uses the Apache Iceberg Java library, and talks to it over gRPC, a remote procedure call framework. By default Go sends batches of records and the Java side writes the files.

With `arrow_writes` enabled in the destination config, Go builds the Parquet files itself with Apache Arrow and the Java side only registers them. Either way, each commit is one Iceberg transaction, so data files, delete files and metadata become visible together.

### Avoiding Bottlenecks with Integrated Destinations

By embedding Destinations inside each Driver, we cut down latencies significantly. Instead of collecting data in a queue or intermediary store, the Driver pushes records as soon as they’re extracted. This approach also avoids “blocking” reads while the Destinations are happening.

Each reader gets its own writer thread. The thread buffers records (10,000 by default, set with `--destination-buffer-size`) and hands a full buffer to a background flush while the reader keeps going.

## Core

The Core is the foundation on which OLake Go Drivers and Destinations rest. It gives us:

1. **CLI & Commands**: every source image exposes the same five commands.
    
    * `spec`: Returns a JSON Schema for the frontend to render form-based configurations.
        
    * `check`: Validates the source or destination config and tests the connection, including the CDC prerequisite checks (server settings and permissions) added in v0.12.0.
        
    * `discover`: Lists all streams and their schemas for a given source, and writes `available_streams.json` and `selected_streams.json`.
        
    * `sync`: Orchestrates the extract, and load (ETL) process.
        
    * `clear-destination`: Clears the destination data and resets the state for the selected streams.
        
    * Flags (full list in [Commands and Flags](/docs/community/commands-and-flags))
        
        1. `--config`, `--destination`, `--available-streams`, `--selected-streams` and `--state` → the JSON files that describe a sync
            
        2. `--destination-buffer-size` → records buffered per writer thread before a flush (default 10000)
            
        3. `--target-query-engines` → the query engines that will read the tables, which narrows the delete formats offered per stream (`--available-query-engines` lists them)
            
        4. `--discover-schema` → re-discovers the source schema during sync (opt-in since v0.10.1)
            
        5. `--max-discover-threads` → parallel threads for discovery (default 50)
            
        6. `--encryption-key`, `--destination-database-prefix`, `--timeout` and `--no-save` → config decryption, naming, timeouts and log files
            
    * Concurrency is not a flag. Set `max_threads` in the source config to control how many chunks or streams are read in parallel.
        
2. **State Management**: `state.json` stores what each run learned: the chunks still to read during a full load, the cursor value for incremental streams, and the CDC position (a PostgreSQL Log Sequence Number (LSN), a MySQL binlog position or GTID set, or a MongoDB resume token). A sync loads the file, does its work, writes it back and exits, so an interrupted full load or CDC run resumes from where it stopped.
    
3. **Configuration**: Connection details, credentials and `max_threads` live in `source.json`, the writer settings in `destination.json`, and per-stream choices (sync mode, partitioning, filters, normalization, delete format) in `selected_streams.json`.
    
4. **Logging & Monitoring**: Each sync writes a `stats.json` file that tracks:
    
    * How many writer threads are running.
        
    * The estimated remaining time.
        
    * Synced records, throughput, memory use and processor use.
        
    Logs are also saved to a file unless you pass `--no-save`.

## OLake UI and Temporal

The CLI runs one command and exits. [OLake UI](/docs/install/olake-ui) adds the always-on part: a web app where you create sources, destinations and jobs, set schedules and read logs. It does not reimplement the pipeline; it runs the same `check`, `discover` and `sync` commands for you.

Behind the UI, [Temporal](https://temporal.io/) orchestrates the jobs. The OLake UI backend starts a Temporal workflow for each operation, and a Temporal worker runs the matching `olakego/source-<type>` image as a Docker container (Docker Compose install) or a pod ([Kubernetes install with Helm](/docs/install/kubernetes)). PostgreSQL stores job data, configs, sync state and Temporal's workflow data.

The whole stack starts with one command:

```bash
curl -sSL https://raw.githubusercontent.com/datazip-inc/olake-ui/master/docker-compose-v1.yml | docker compose -f - up -d
```

### Handling Schema Evolution & Error Recovery

When working with a schema-less store like MongoDB, we often encounter evolving document structures. When a batch brings a new column or a wider type (for example `int` to `long`), the writer evolves the Iceberg table schema before it writes. By default `sync` skips schema discovery for faster runs, and `--discover-schema` (since v0.10.1) re-discovers the source schema and validates the configured streams on each sync.

Failed reads are retried a configurable number of times, and a failed run resumes from `state.json` on the next sync.

## OLake Go’s Role in a Lakehouse Ecosystem

We emphasised early on that we wanted to avoid vendor lock-in. Hence, OLake Go stores data in open formats, like `parquet`, using a table format like *Apache Iceberg*.

This opens up the possibility for various query engines, including *Spark*, *Trino*, *Flink* or Snowflake (see [query engine compatibility](/docs/understanding/compatibility-engines)). By decoupling how data is written and how it's consumed, we make sure you can leverage the best analytical tools without rewriting or re-ingesting the data.

**Key Benefits**:

* **Real-Time Replication**: Source change logs (the MongoDB oplog, the PostgreSQL WAL, the MySQL binlog) feed near real-time changes, ensuring the lakehouse is promptly updated.
    
* **Upserts with the right delete files (Apache Iceberg)**: CDC and incremental rows are upserted by default. OLake Go writes equality deletes, positional deletes (since v0.10.0) or deletion vectors (since v0.11.0), and since v0.11.0 it picks the format from the target query engines you set. See [delete format support by query engine](/docs/understanding/compatibility-engines#delete-format-support-by-query-engine).

## Key Architectural Highlights

1. **Native BSON Extraction**: For MongoDB, we pull data in its raw BSON form, decoding it on the ETL side. This approach maintains fidelity and boosts speed.
    
2. **Parallel Chunking**: Instead of serial reads, we split big collections into smaller virtual chunks to parallelize the process.
    
3. **CDC Cursor Preservation**: We never lose track of CDC offsets. Even if a large table or collection is added later, we run a full load for it alone and keep the saved log position of the others.
    
4. **Job Failure Alerts**: OLake UI sends a webhook alert when a job fails, so issues surface early instead of as silent failures ([alerts setup](/docs/getting-started/alerts-and-notifications)).
    
5. **Open Format for Freedom**: By embracing Parquet and Iceberg, we side-step vendor lock-in and enable multi-engine querying.
    
6. Both full snapshot and CDC are resumable as and when required by the customer.
    
7. Estimated time duration for the initial snapshot to be completed so you have a better insight on what’s going on inside the hood.
    

## Concluding Remarks

When this post first went out, we listed what we planned next. Here is where each item stands in OLake Go v1.2.2:

1. **Handle Nested JSON** flattening into separate tables or exploded columns: not available. Normalization flattens top-level fields, and nested objects are stored as JSON strings.
    
2. **Effortless deployment**: OLake Go ships as one Docker image per source, and OLake UI starts with one Docker Compose command. [Kubernetes with Helm](/docs/install/kubernetes) and [GitOps](/docs/install/gitops) installs are also available.
    
3. **Flexible BYOC** (Bring Your Own Cloud): OLake Go is self-hosted, so it runs in your own cloud account or on-premises.
    
4. **Security**: Config files can be encrypted and decrypted at run time with `--encryption-key`, which takes an AWS Key Management Service (KMS) key, a universally unique identifier (UUID) or a custom string.
    
5. **Transactional consistency**: Each Iceberg commit is a single transaction, so the data files, delete files and metadata of one commit become visible together.
    
6. **Resumable full loads**: shipped. Chunk progress is saved in `state.json`, so an interrupted full load continues with the chunks still pending.
    
7. **Kafka integration**: shipped as a [source](/docs/connectors/kafka), with consumer groups, JSON and Avro messages, and an upsert mode. Kafka is not a destination.
    
8. **Server and unified UI**: shipped as [OLake UI](/docs/install/olake-ui), with Temporal running the jobs.
    
9. **Horizontal scalability**: On Kubernetes, each sync runs in its own pod, and [JobID-based scheduling](/docs/install/kubernetes#jobid-based-scheduling) maps jobs to nodes with enough capacity.
    
10. **Lake-based optimization** and compaction: shipped as a separate product, [OLake Fusion](/docs/fusion/getting-started/overview), which schedules compaction for Iceberg tables.
    
11. **Multiple cloud support**: shipped. Iceberg and Parquet both write to GCS and Azure, and the catalogs include AWS Glue, Polaris, Lakekeeper, Nessie, Unity Catalog, BigLake, S3 Tables, Snowflake Horizon, Hive Metastore and JDBC.
