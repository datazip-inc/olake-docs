Unity Catalog exposes an Iceberg REST (representational state transfer) endpoint. OLake Go writes managed Iceberg tables through it, and Databricks governs them.

**Short answer.** To write Iceberg tables to Unity Catalog, create an OLake Go destination with `catalog_type: unity`, the workspace Iceberg REST endpoint, and OAuth2 machine-to-machine, OAuth2 user-to-machine, token federation or a personal access token. The metastore needs **external data access** turned on, and the writer needs the `EXTERNAL USE SCHEMA` privilege.

<TLDR title='Key takeaways'>

- OLake Go writes Unity Catalog managed Iceberg tables through the workspace Iceberg REST endpoint.
- [Databricks](/docs/integrations/databricks/) reads them natively, and Spark, DuckDB and Trino read them over REST.
- Eight guides ran end to end on Unity Catalog, for example [Postgres to Databricks](/docs/integrations/postgres-to-databricks/).

## How OLake Go writes to Unity Catalog

OLake Go uses **change data capture (CDC)** where the source has it. It commits Unity Catalog managed Iceberg tables. Databricks reads them natively, and Spark, DuckDB and Trino read them over REST.

The eight [Databricks](/docs/integrations/databricks/) guides ran end to end on Unity Catalog. The [Unity Catalog writer page](/docs/writers/iceberg/catalog/rest/?rest-catalog=unity) holds the destination reference.

## When to use it

- Databricks is the main reader and Unity Catalog governs your data.
- DuckDB or Spark should read the same tables.

## When not to use it

- The job needs equality or positional deletes. Databricks reads only deletion vectors on these tables.
- A Kafka topic must be upserted. OLake Go v1.1.0 upserts Kafka with positional deletes, so Kafka runs in Append mode on Unity.
