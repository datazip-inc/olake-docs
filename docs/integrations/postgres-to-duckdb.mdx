Postgres to DuckDB usually means `pg_dump`, a CSV or Parquet export, and a DuckDB file somebody rebuilds, or DuckDB's `postgres` extension hitting the live database. This guide takes a different route.

OLake Go reads the Postgres write-ahead log (WAL) and commits the changes as Apache Iceberg tables into an Apache Polaris catalog. DuckDB attaches that catalog and queries the tables in place.

Polaris is an open source Iceberg REST (Representational State Transfer) catalog you run yourself, with the files in your own bucket. Nothing else is in the path: no Kafka, no Debezium, no DuckDB file to copy around. ClickHouse and Trino read the same tables through the same endpoint.

<I.IntegrationByline />

<TLDR title='Key takeaways'>

- OLake Go replicates Postgres into Iceberg tables in Polaris: a full historical snapshot first, then change data capture (CDC) from the WAL, with no Kafka or Debezium in between.
- DuckDB attaches the whole Polaris catalog with one `ATTACH`, lists every table OLake Go committed, and sees every change the moment a sync commits. Every session reads the same tables, on a laptop or in a job.
- The same tables, written once by OLake Go, are also queryable from ClickHouse and Trino through the same catalog. In the run on this page all three engines returned identical rows.

</TLDR>

**The short answer.** To replicate Postgres to DuckDB with change data capture (CDC), run OLake Go with a Postgres replication slot as the source. Point it at an Apache Polaris catalog as the Iceberg destination. The first sync copies each table in full (the historical snapshot); every later sync replays inserts, updates and deletes from the WAL. DuckDB, ClickHouse and Trino then query the same Iceberg tables, with no second copy.

## How Postgres CDC reaches DuckDB here

```mermaid
%%{init: {"flowchart": {"nodeSpacing": 30, "rankSpacing": 40}}}%%
flowchart TB
  subgraph pg["Postgres"]
    T[(customers, orders)]
    WAL[write-ahead log, read through a replication slot]
    T ~~~ WAL
  end
  subgraph olake["OLake Go"]
    W[Iceberg writer]
  end
  subgraph pol["Apache Polaris"]
    H[REST catalog: table pointers, access control]
  end
  S[(S3 or MinIO bucket)]
  R[Query engines: DuckDB, ClickHouse, Trino]
  T -- "first sync (historical snapshot): parallel reads over table chunks" --> W
  WAL -- "later syncs: inserts, updates, deletes" --> W
  H -. "1. vended storage credentials" .-> W
  W -- "2. Parquet data files and positional delete files" --> S
  W -- "3. commit snapshot" --> H
  H -- "table metadata and vended credentials" --> R
  S -- "data and delete files" --> R
```

Two things happen in order, and OLake Go does both on its own. The first sync records the current WAL position through the replication slot. Then it reads each table in parallel chunks and writes Parquet data files: that is the historical load.

Every later sync opens the slot at the saved position and replays the inserts, updates and deletes since. Nothing written during the snapshot is lost, and there is no separate backfill job.

Each sync ends with one commit to Polaris. OLake Go asks Polaris for short-lived storage credentials, uploads the data and delete files, then posts the new snapshot to the catalog. DuckDB, ClickHouse and Trino see it on their next query; none of them keeps a copy.

One thing to keep an eye on: the replication slot pins WAL on the Postgres server until OLake Go has read it. A job that is paused for days makes the WAL grow by everything written since. Keep the job running on a schedule, and alert on `pg_replication_slots` lag if disk is tight.

## What you need

- **Postgres 12 or later** with `wal_level = logical` and a user that can read the WAL. The tables on this page ran on Postgres 16. Hosted Postgres on Amazon Relational Database Service (RDS), Aurora, Google Cloud SQL, Azure, Neon or Supabase works the same way; step 1 links the setup guides.
- **An Apache Polaris server and a bucket**, both reachable from OLake Go and from wherever DuckDB runs. The run on this page used Polaris 1.8.0 and MinIO in Docker; on AWS, use an S3 bucket and an IAM role instead.
- **DuckDB 1.4 or later** with the `iceberg` and `httpfs` extensions, which DuckDB installs on first use. The run on this page used DuckDB 1.5.5.
- **OLake UI** from the [Docker Compose install](/docs/install/olake-ui/). The run on this page used OLake Go v1.1.0.
- **Docker**, and about 40 minutes.

## Step 2: Set up the Polaris catalog

DuckDB reads Iceberg tables through a catalog. **Apache Polaris** is the one this page uses: an open source REST catalog that you run next to your bucket.

OLake Go writes into it, and DuckDB, ClickHouse and Trino read from it with the credentials Polaris hands out. The Iceberg files sit in your own S3 or MinIO bucket; Polaris holds only the pointers and the permissions.

## Step 7: Change rows in Postgres and sync again

To see the change path work, the run on this page made 12 changes in Postgres after the first sync:

```sql title="Changes made in Postgres between the two syncs"
INSERT INTO customers (name, email, city, tier) VALUES
  ('Maya Patel', 'maya@example.com', 'Pune', 'silver'),
  ('Lucas Silva', 'lucas@example.com', 'São Paulo', 'bronze');
INSERT INTO orders (customer_id, product, amount, status) VALUES
  (9, 'Laptop', 1299.00, 'placed'), (9, 'Mouse', 25.50, 'placed'),
  (10, 'Monitor', 349.99, 'placed'), (3, 'Keyboard', 89.00, 'placed'), (7, 'Webcam', 79.90, 'placed');
UPDATE customers SET tier = 'gold', updated_at = NOW()      WHERE name = 'Liam Carter';
UPDATE customers SET city = 'Abu Dhabi', updated_at = NOW() WHERE name = 'Zara Ali';
UPDATE orders    SET status = 'delivered', updated_at = NOW() WHERE id IN (1, 4, 7);
```

The second sync read **12 records (594 bytes)** from the slot and finished in **12 seconds** end to end. For `customers` that meant one new data file with 4 rows: 2 inserts plus the new versions of 2 updated rows.

One small positional delete file retires the 2 old versions. OLake Go's commit report in the sync log shows it directly: `addedDataFiles=1`, `addedRecords=4`, `addedPositionalDeleteFiles=1`, `addedPositionalDeletes=2`. The `orders` table has the same shape with 8 rows and 3 deletes.

<Figure src='/img/docs/integrations/postgres-to-duckdb/olake-sync-log-positional-delete-commit.webp' alt='OLake UI sync log filtered to the Iceberg commit report for orders, showing addedDataFiles 1, addedPositionalDeleteFiles 1, addedRecords 8, totalRecords 48 and addedPositionalDeletes 3' caption='The change-only sync in the OLake UI log: one data file and one positional delete file per table.' />

DuckDB shows the result on the next query, with no refresh. Liam Carter is `gold`, Zara Ali moved to Abu Dhabi, and the two new customers are there.

The two retired versions are gone, because DuckDB applies the positional deletes while reading. The `_op_type` column shows how each row arrived: `r` for the snapshot, `c` for the inserts and `u` for the updates.

**Schema changes.** When a column is added in Postgres, OLake Go adds it to the Iceberg table on the next sync. DuckDB shows it on the next `ATTACH`.

Widening changes (`int` to `bigint`, `real` to `double precision`) are applied. Narrowing or incompatible type changes fail the sync rather than corrupt the table. Full rules are on the [schema evolution page](/docs/features/schema/).

## Data types: Postgres to Iceberg to DuckDB

OLake Go maps Postgres types to Iceberg types, and DuckDB maps Iceberg types to its own. Most columns pass through unchanged; three groups are worth knowing about.

| Postgres | Iceberg (written by OLake Go) | DuckDB shows | Notes |
| --- | --- | --- | --- |
| `integer`, `serial` | `int` | `INTEGER` | |
| `bigint`, `bigserial` | `long` | `BIGINT` | |
| `numeric(p,s)`, `real`, `double precision` | `double` | `DOUBLE` | OLake Go stores decimals as doubles. The `orders.amount` sums on this page matched Postgres to the cent in every engine; round at query time when you need exact decimal arithmetic. |
| `timestamptz`, `timestamp` | `timestamptz` (UTC) | `TIMESTAMP WITH TIME ZONE` | `timestamp` has no zone in Postgres; it is read as UTC. |
| `varchar`, `text`, `uuid`, `json`, `jsonb` | `string` | `VARCHAR` | Parse JSON with DuckDB's `json` extension. |
| `boolean` | `boolean` | `BOOLEAN` | |
| `bytea` | `binary` | `BLOB` | |

Postgres types in the table come from the [Postgres connector reference](/docs/connectors/postgres/#data-type-mapping). The DuckDB side comes from the [DuckDB Iceberg extension page](https://duckdb.org/docs/stable/core_extensions/iceberg/overview) (checked 2026-10-29) and from `DESCRIBE` on the tables of this run. OLake Go adds `_cdc_lsn` on Postgres tables, the WAL position each change came from.

## Cost and maintenance

- **Storage** is your bucket: you pay S3 or MinIO rates for the Parquet and delete files, and nothing to Polaris or DuckDB for holding them.
- **Compute.** OLake Go runs wherever you run Docker. DuckDB reads Parquet over the network on every query; for a table you hit all day, `CREATE TABLE local AS FROM polaris...` once and query the local copy.
- **Maintenance.** Nothing compacts the tables for you. A CDC table that gets a new small file and delete file per sync wants compaction; [OLake Fusion](/docs/fusion/getting-started/overview/) does this for the catalogs OLake Go writes to, and Spark's `rewrite_data_files` works through the same Polaris endpoint.
- **WAL disk.** The replication slot keeps WAL until OLake Go reads it. A job paused for a weekend on a busy server can hold tens of gigabytes. Drop the slot if you retire a job.
- **Credential rotation.** Polaris principals do not expire by default. Rotate the `olake` principal's secret on your own schedule with the management API; a rotated secret fails the next sync at the token exchange, before any data moves.

## Troubleshooting

### 1. DuckDB cannot resolve the store address

```text
IO Error: Could not resolve hostname error for HTTP GET to 'http://host.docker.internal:9000/lakehouse/...'
```

DuckDB used the store address Polaris vends, which resolves inside Docker but not on the laptop. Add an S3 secret with the address DuckDB can reach and attach with `ACCESS_DELEGATION_MODE 'none'`, as in step 6. On AWS S3 the vended address resolves everywhere and the secret is not needed.

### 2. Polaris cannot create a table

```text
{"error":{"message":"host must not be null.","type":"NullPointerException","code":500}}
{"error":{"message":"java.net.URISyntaxException: Expected scheme-specific part at index 5: http:","type":"RuntimeException","code":500}}
```

The store hostname contains an underscore (`lab_minio`), which Java's Uniform Resource Identifier (URI) parser rejects. Rename the container or host with a hyphen and update `endpoint` and `endpointInternal` on the catalog.

### 3. Polaris refuses to vend credentials

```text
{"error":{"message":"Credential vending was requested for table probe.t1, but no credentials are available","type":"IllegalArgumentException","code":400}}
```

The catalog has `stsUnavailable: true` but Polaris was given no static keys to hand out. Either remove `stsUnavailable` (MinIO and S3 both expose a Security Token Service (STS) endpoint), or configure the keys on the Polaris server.

### 4. The next sync waits on the slot

If a sync hangs after the snapshot, another process holds the replication slot, or `wal_sender_timeout` cut the connection during a quiet period. Check `pg_stat_replication` for a second consumer of `olake_slot`, and set `wal_sender_timeout = 0` for the OLake Go user as the prerequisites block shows.

### 5. The destination test fails at the token exchange

OLake Go's destination test exchanges the principal's credentials at `/api/catalog/v1/oauth/tokens` before anything else. Three causes cover nearly every failure.

A wrong client id or secret, a principal without a role that carries `CATALOG_MANAGE_CONTENT` on the catalog, or a wrong `Polaris Catalog Name`. Run the token check from the catalog setup; it returns the same error Polaris gives OLake Go.

<details>
<summary>How this compares with other ways to get Postgres data into DuckDB</summary>

| Method | Freshness | Updates and deletes | Where the data lands | What you run |
| --- | --- | --- | --- | --- |
| [DuckDB postgres extension](https://duckdb.org/docs/stable/core_extensions/postgres/overview) | Live, per query | Reads the current row | Nothing is copied; every query hits Postgres | A Postgres user DuckDB can log in with |
| `pg_dump` or `COPY TO`, then `COPY` into DuckDB | Hours to daily | No; full reloads only | A DuckDB file you rebuild | A script and a scheduler |
| Debezium and Kafka, then a consumer that writes Parquet | Seconds | Yes, with your own merge logic | Parquet files, then DuckDB | Kafka, Kafka Connect, Debezium and a consumer |
| Managed ELT to a warehouse, then DuckDB over it | Minutes, by plan | Varies by tool | Warehouse tables, a second copy you pay to move and store | Nothing; priced per row, per GB or per connector |
| **OLake Go to Iceberg on Polaris (this guide)** | CDC on a schedule down to one minute | Yes, as Iceberg row-level deletes | Apache Iceberg tables that DuckDB, ClickHouse, Trino and Spark all read | One Docker Compose stack, open source; your bucket plus your own compute |

The postgres extension is the simpler choice for a one-off query against a small table you can reach directly. Writing Iceberg once avoids hitting production Postgres from every notebook, and gives every engine the same rows.

</details>

## When not to use this

- **One analyst, one laptop, one small table.** The DuckDB postgres extension or a nightly `COPY` is less to run than a catalog and OLake Go.
- **Tables have no primary key.** Inserts replicate; updates and deletes cannot be matched to a row and are not applied. Add a primary key or set `REPLICA IDENTITY FULL` first.
- **DuckDB must read equality deletes.** DuckDB does not document them. Keep the job on positional deletes or deletion vectors, as on this page.
