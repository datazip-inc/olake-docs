Spark on Google Cloud Dataproc reads Iceberg tables in the BigLake catalog. BigQuery reads the same catalog.

**Short answer.** To process replicated tables on Dataproc, run OLake Go with the BigLake Iceberg REST (representational state transfer) catalog as the destination. Point Spark on Dataproc at it with Google authentication and **Iceberg 1.10 jars**, and Spark reads every delete format. If BigQuery also reads the tables, follow the BigQuery delete-format limits instead.

<TLDR title='Key takeaways'>

- Spark on Dataproc reads the Iceberg tables OLake Go commits to [BigLake](/docs/integrations/catalogs/biglake/).
- Spark reads every Iceberg delete format, so Dataproc adds no delete-format limit of its own.
- Spark on Dataproc and [BigQuery](/docs/integrations/bigquery/) share one copy of the data.

</TLDR>

_Last reviewed October 2026._

## How OLake Go gets data into Google Cloud Dataproc

OLake Go uses **change data capture (CDC)** where the source has it. It commits Iceberg tables to [BigLake](/docs/integrations/catalogs/biglake/). Spark on Dataproc and [BigQuery](/docs/integrations/bigquery/) then share one copy of the data.

No guide on this site runs Dataproc yet. The nine BigQuery guides write the same BigLake tables, and the [BigLake setup post](/blog/biglake-iceberg-rest-catalog-olake-go-setup/) covers the catalog.

## When to use it

- Spark jobs on Google Cloud should process tables that BigQuery also reads.
- The data already lives in Google Cloud Storage.

## When not to use it

- You register tables in Dataproc Metastore and expect BigQuery to see them. BigQuery does not see Dataproc Metastore tables.
- BigQuery is a reader and you want deletion vectors. Those are a BigQuery preview feature.
