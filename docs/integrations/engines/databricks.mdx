Databricks reads Apache Iceberg tables that live in Unity Catalog. OLake Go writes straight into a catalog that Databricks already governs.

**Short answer.** To replicate a database to Databricks, run OLake Go with the Unity Catalog Iceberg REST (representational state transfer) endpoint as the destination. The tables become Unity Catalog managed Iceberg tables. Under Unity Catalog, Databricks reads only Iceberg v3 deletion vectors. Add Databricks as a target query engine, and OLake Go writes them from the first sync.

_Last reviewed October 2026._

## How OLake Go gets data into Databricks

OLake Go uses change data capture (CDC) for Postgres, MySQL, MariaDB, MongoDB and SQL Server. It commits each sync to [Unity Catalog](/docs/integrations/catalogs/unity/). Databricks, DuckDB and Spark then query the same tables. Databricks sees AWS Glue and Hive Metastore tables only as read-only foreign tables.

The eight guides below ran on a 2X-Small serverless SQL warehouse. The [Unity Catalog writer page](/docs/writers/iceberg/catalog/rest/?rest-catalog=unity) holds the full destination reference.

## When to use it

- Databricks is the main reader and Unity Catalog governs your data.
- You want the same rows readable from DuckDB or Spark without a second copy.

## When not to use it

- You need to upsert a Kafka topic. OLake Go v1.1.0 upserts [Kafka](/docs/connectors/kafka/) with positional deletes, which Unity Catalog tables do not take. Kafka runs in Append mode instead.
- Athena or another engine on the job cannot read deletion vectors. OLake Go needs one delete format that all target engines read.
