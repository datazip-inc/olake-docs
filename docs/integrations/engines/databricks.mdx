Databricks reads Apache Iceberg tables that live in Unity Catalog. OLake Go writes straight into that catalog.

**Short answer.** To copy a database to Databricks, point OLake Go at the Unity Catalog Iceberg REST (representational state transfer) endpoint. The tables land as managed Iceberg tables, and on these Databricks reads only v3 deletion vectors. Add Databricks as a target query engine and OLake Go writes them from the first sync.

<TLDR title='Key takeaways'>

- OLake Go writes Unity Catalog managed Iceberg tables that Databricks governs and queries directly.
- With Databricks as a target query engine, OLake Go writes Iceberg v3 deletion vectors from the first sync.
- Eight guides ran end to end on [Unity Catalog](/docs/integrations/catalogs/unity/), with DuckDB and Spark reading the same tables.

</TLDR>

## How OLake Go gets data into Databricks

OLake Go uses **change data capture (CDC)** for Postgres, MySQL, MariaDB, MongoDB and SQL Server, and commits each sync to [Unity Catalog](/docs/integrations/catalogs/unity/). Databricks, DuckDB and Spark then read the same tables. Tables in AWS Glue or Hive Metastore show up in Databricks only as read-only foreign tables.

The eight guides below ran on a **2X-Small serverless SQL warehouse**. The [Unity Catalog writer page](/docs/writers/iceberg/catalog/rest/?rest-catalog=unity) holds the full destination reference.

## When to use it

- Databricks is the main reader and Unity Catalog holds your data.
- You want the same rows readable from DuckDB or Spark without a second copy.

## When not to use it

- You need to upsert a Kafka topic. OLake Go v1.1.0 upserts [Kafka](/docs/connectors/kafka/) with positional deletes, which Unity Catalog tables do not take. Kafka runs in Append mode instead.
- Athena or another engine on the job cannot read deletion vectors. OLake Go needs one delete format that all target engines read.
