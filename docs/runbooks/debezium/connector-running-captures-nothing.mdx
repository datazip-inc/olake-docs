import * as R from '@site/src/components/runbooks';

A Debezium connector and its task both report `RUNNING`, the log shows no exception, and the Kafka topics stay empty or are never created. This page lists the causes we reproduced on MySQL and PostgreSQL, the command that proves each one, and the fix we ran.

<R.Byline />

<R.Disclosure />

**The short answer.** Search the Kafka Connect log for `no changes will be captured`. If the line is there, a value in `table.include.list` does not match the full table name, which is `database.table` on MySQL and `schema.table` on PostgreSQL.

If the line is not there, four more checks remain: the snapshot mode, whether the topics exist, the PostgreSQL publication, and whether the connector has a task at all. Each is one command under [Confirm the diagnosis](#confirm-the-diagnosis).

<TLDR title='Key takeaways'>

- `RUNNING` is not a count of events. Five different mistakes left a connector `RUNNING` with nothing captured on Debezium 1.9.7 and on 3.7.1.
- A filter that matches no table is logged as a warning at start-up and nowhere else: `After applying the include/exclude list filters, no changes will be captured. Please check your configuration!`
- Correcting the configuration does not replay what was skipped. On MySQL the 4 rows that were in the table before the fix arrived only after the connector's offsets were removed and it took a new snapshot.

</TLDR>

## What you see

The status call answers `RUNNING` for the connector and for its task. This is Kafka Connect 4.3.1; version 3.2.0 gives the same states without the `version` fields.

```json
{
  "name": "my-filter",
  "connector": { "state": "RUNNING", "worker_id": "172.31.0.5:8083", "version": "3.7.1.Final" },
  "tasks": [{ "id": 0, "state": "RUNNING", "worker_id": "172.31.0.5:8083", "version": "3.7.1.Final" }],
  "type": "source"
}
```

The worker log holds one of the lines below, or none of them. They are from Debezium 3.7.1 on Kafka Connect 4.3.1, one per cause.

```text
WARN   MySQL||snapshot  After applying the include/exclude list filters, no changes will be captured. Please check your configuration!   [io.debezium.relational.RelationalDatabaseSchema]
INFO   MySQL||snapshot  Snapshot step 7 - Skipping snapshotting of data   [io.debezium.relational.RelationalSnapshotChangeEventSource]
WARN   ||  [Producer clientId=connector-producer-my-topics-0] The metadata response from the cluster reported a recoverable issue with correlation id 35 : {myt=UNKNOWN_TOPIC_OR_PARTITION}   [org.apache.kafka.clients.NetworkClient]
ERROR  ||  [Worker clientId=connect-172.31.0.5:8083, groupId=lab-connect] Failed to reconfigure connector's tasks (my-notask), retrying after backoff.   [org.apache.kafka.connect.runtime.distributed.DistributedHerder]
```

A PostgreSQL publication that lacks the table produces no log line at all.

### Names and messages by Debezium version

The filter properties were renamed once and the snapshot modes once. Use the row for the version you run.

| Debezium | Warning when the filters match no table | Filter properties | Snapshot mode that reads no rows |
| --- | --- | --- | --- |
| 1.2 and earlier | `After applying blacklist/whitelist filters there are no tables to monitor, please check your configuration` | `database.whitelist`, `schema.whitelist`, `table.whitelist`, `column.whitelist` | MySQL `schema_only`, PostgreSQL `never` |
| 1.3 to 1.9 | `After applying the include/exclude list filters, no changes will be captured. Please check your configuration!` | `database.include.list`, `schema.include.list`, `table.include.list`, `column.include.list`. The old names still work | MySQL `schema_only`, PostgreSQL `never` |
| 2.0 to 2.5 | Same as 1.3 | The `*.include.list` names only | MySQL `schema_only`, PostgreSQL `never` |
| 2.6 to 3.2 | Same as 1.3 | The `*.include.list` names only | `no_data`. The old values are deprecated and still present |
| 3.3 and later | Same as 1.3 | The `*.include.list` names only | `no_data` only |

The 1.9.7 and 3.7.1 rows are from the runs on this page. The other boundaries come from the Debezium release notes for [1.3](https://debezium.io/releases/1.3/release-notes) (the rename), [2.0](https://debezium.io/releases/2.0/release-notes) ("All deprecated configuration options were removed") and [3.3](https://debezium.io/releases/3.3/release-notes) ("Deprecated names of snapshot modes were removed"), and from the source at the [1.2.5](https://github.com/debezium/debezium/blob/v1.2.5.Final/debezium-core/src/main/java/io/debezium/relational/RelationalDatabaseSchema.java), [1.3.1](https://github.com/debezium/debezium/blob/v1.3.1.Final/debezium-core/src/main/java/io/debezium/schema/DatabaseSchema.java), [2.6.2](https://github.com/debezium/debezium/blob/v2.6.2.Final/debezium-connector-postgres/src/main/java/io/debezium/connector/postgresql/PostgresConnectorConfig.java) and [3.2.7](https://github.com/debezium/debezium/blob/v3.2.7.Final/debezium-connector-binlog/src/main/java/io/debezium/connector/binlog/BinlogConnectorConfig.java) tags.

What the old names do depends on which side of 2.0 you are on. On 1.9.7 a connector configured with `table.whitelist` and `column.whitelist` filtered as asked and logged a warning for each:

```text
WARN   ||  Using configuration property "table.whitelist" is deprecated and will be removed in future versions. Please use "table.include.list" instead.   [io.debezium.config.Configuration]
```

On 3.7.1 the same properties were ignored without a log line, and the connector captured every table with every column. After an upgrade across 2.0 a connector with old names therefore captures more, not less.

## Why it happens

None of the causes on this page throws an exception inside the task, so nothing moves the state to `FAILED`. The connector is connected to the database and is reading its log. What it reads is filtered out, was never requested, cannot be written to a topic, or is never sent by the database.

The fifth cause is the exception to that: the connector has no task at all, and the status shows `RUNNING` with an empty task list.

## Confirm the diagnosis

Run the checks in this order. The first one that shows the bad sign is your cause.

**1. The table filter.** Search the worker log, then compare the list with the names the database uses.

```bash
docker logs <connect-container> 2>&1 | grep 'no changes will be captured'
curl -s localhost:8083/connectors/<name>/config | jq 'with_entries(select(.key | test("include|exclude|whitelist|blacklist")))'
```

```sql
-- MySQL: the form table.include.list expects
SELECT CONCAT(table_schema, '.', table_name) FROM information_schema.tables WHERE table_schema = 'inventory';
-- PostgreSQL: the form table.include.list expects
SELECT schemaname || '.' || tablename FROM pg_tables WHERE schemaname NOT IN ('pg_catalog', 'information_schema');
```

**2. The snapshot mode and the stored offset.** The first call prints `null` when the mode is not set, which means the default, `initial`. The second call needs Kafka Connect 3.5 or later; on 3.2.0 it answered `HTTP 404 Not Found`.

```bash
curl -s localhost:8083/connectors/<name>/config | jq -r '."snapshot.mode"'
curl -s localhost:8083/connectors/<name>/offsets
```

**3. The topics.** List what exists for the connector's prefix, read the broker setting, and search the worker log.

```bash
kafka-topics.sh --bootstrap-server kafka:9092 --list | grep '^<prefix>'
kafka-configs.sh --bootstrap-server kafka:9092 --describe --entity-type brokers --entity-name 1 --all | grep auto.create.topics.enable
docker logs <connect-container> 2>&1 | grep -c UNKNOWN_TOPIC_OR_PARTITION
```

**4. The publication, on PostgreSQL.** The name is `dbz_publication` unless `publication.name` says otherwise.

```sql
SELECT pubname, puballtables FROM pg_publication;
SELECT pubname, schemaname, tablename FROM pg_publication_tables WHERE pubname = 'dbz_publication';
```

**5. The task list.** An empty `tasks` array with a `RUNNING` connector is the sign.

```bash
curl -s localhost:8083/connectors/<name>/status
docker logs <connect-container> 2>&1 | grep "Failed to reconfigure connector's tasks"
```

## Cause 1: the include list matches no table

The [MySQL connector documentation](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-property-table-include-list) says of `table.include.list`: "Each identifier is of the form databaseName.tableName." The [PostgreSQL one](https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-property-table-include-list) says: "Each identifier is of the form schemaName.tableName."

The MySQL page adds that the expression "is matched against the entire name string of the table; it does not match substrings that might be present in a table name."

These are the values we tried against a table named `customers`, in the `inventory` database on MySQL and in the `public` schema of an `inventory` database on PostgreSQL. The result was the same on 1.9.7 and 3.7.1.

| Database | `table.include.list` | Captured | Why |
| --- | --- | --- | --- |
| MySQL | `customers` | No | No database name |
| MySQL | `inventory.cust*` | No | A regular expression, not a wildcard: `t*` means any number of `t` |
| MySQL | `INVENTORY.CUSTOMERS` | Yes | The match ignores case |
| MySQL | `inventory.customers` | Yes | |
| PostgreSQL | `inventory.customers` | No | `inventory` is the database, the schema is `public` |
| PostgreSQL | `customers` | No | No schema name |
| PostgreSQL | `inventory.public.customers` | No | Three parts where two are expected |
| PostgreSQL | `PUBLIC.CUSTOMERS` | Yes | The match ignores case |
| PostgreSQL | `public.customers` | Yes | |

Wrong case is not a cause. Debezium compiles these lists with a case-insensitive flag ([source](https://github.com/debezium/debezium/blob/v3.7.1.Final/debezium-util/src/main/java/io/debezium/function/Predicates.java)), and the upper-case values captured the table in the runs.

Every "No" row left the connector and its task `RUNNING` and wrote the warning. MySQL wrote it twice, once in the snapshot phase and once in the streaming phase, and PostgreSQL wrote it once. On MySQL the schema change topic still received 8 records, so a topic named after the prefix exists and the table topics do not.

One PostgreSQL setting turns the silence into a failure. With `publication.autocreate.mode=filtered` the same wrong list failed the task on both versions:

```text
org.apache.kafka.connect.errors.ConnectException: Unable to create filtered publication pgg_pub for
Caused by: io.debezium.DebeziumException: No table filters found for filtered publication pgg_pub
```

### Fix: correct the list, then check what you got back

Send the whole configuration again with the corrected value. The warning did not come back on either database.

```bash
curl -X PUT -H 'Content-Type: application/json' localhost:8083/connectors/<name>/config \
  --data '{ "...": "your existing settings", "table.include.list": "inventory.customers" }'
```

What arrives next differs by database, because of what each connector had stored while it captured nothing.

**MySQL had an offset.** It had written schema change records, so a position was stored, and the corrected connector logged `A previous offset indicating a completed snapshot has been found.` and took no snapshot. It read the binary log (binlog) from the stored position: the 1 row inserted while the filter was wrong arrived, and the 4 rows from before did not.

**PostgreSQL had none.** The connector had written nothing, and after the fix it took a normal initial snapshot on both versions: all 5 rows arrived as read events (`op=r`).

On Kafka Connect 4.3.1 you can see the difference before you fix anything. `GET /connectors/<name>/offsets` returned `{"offsets":[]}` for the PostgreSQL connector, and the 3.7.1 log repeated `No previous offsets found` every 10 seconds, which is the offset flush interval of the lab.

### Fix: read the rows that were skipped

On MySQL the old rows need a new snapshot. On Kafka Connect 3.6 or later, stop the connector, delete its offsets and its schema history topic, and resume:

```bash
curl -X PUT localhost:8083/connectors/<name>/stop
curl -X DELETE localhost:8083/connectors/<name>/offsets
kafka-topics.sh --bootstrap-server kafka:9092 --delete --topic <schema history topic>
curl -X PUT localhost:8083/connectors/<name>/resume
```

In the run the table topic went from 2 events to 8: the 6 rows of the table were read as `op=r`. On Kafka Connect 3.2.0, which has neither endpoint, we deleted the connector and its history topic and registered the same configuration under a new name, with the same result.

Whatever consumes the topic sees the 2 rows that had already arrived a second time. An [incremental snapshot](https://debezium.io/documentation/reference/stable/connectors/mysql.html#debezium-mysql-incremental-snapshots) is the documented way to read a table without resetting the connector; it was not run in this lab.

### A column filter in the wrong format

`column.include.list` has the same trap one level down. With `column.include.list=id,email` and a correct table list, the connector wrote one event per row on both versions, and every event was empty:

```json
{ "before": null, "after": {}, "op": "r" }
```

The key was intact (`{"id": 6}`). Written as `inventory\.customers\.(id|email)`, the same list produced events with the two columns.

The MySQL documentation gives the form: "Fully-qualified names for columns are of the form databaseName.tableName.columnName."

## Cause 2: a snapshot mode that reads no existing rows

With `snapshot.mode=no_data` the connector reads the table structure and starts streaming. It never selects the rows that are already there. The value is `schema_only` on MySQL and `never` on PostgreSQL before Debezium 2.6.

In the run the table held 4 rows, and after start-up no table topic existed. One insert later the topic held 1 event, an insert (`op=c`).

The log says what happened, in different words per connector. These lines are from 3.7.1:

```text
INFO   MySQL||snapshot  According to the connector configuration only schema will be snapshot.   [io.debezium.relational.RelationalSnapshotChangeEventSource]
INFO   MySQL||snapshot  Snapshot step 7 - Skipping snapshotting of data   [io.debezium.relational.RelationalSnapshotChangeEventSource]
INFO   Postgres||snapshot  According to the connector configuration no snapshot will be executed   [io.debezium.connector.postgresql.PostgresSnapshotChangeEventSource]
```

On 1.9.7 the first line ends `only schema will be snapshotted` and the other two are the same.

Changing `snapshot.mode` to `initial` on the same connector did nothing on either database or version. The connector found its offset and skipped the snapshot. The line to look for differs:

| Version | Connector | Log line |
| --- | --- | --- |
| 3.7.1 | MySQL and PostgreSQL | `A previous offset indicating a completed snapshot has been found.` |
| 1.9.7 | MySQL | `A previous offset indicating a completed snapshot has been found. Neither schema nor data will be snapshotted.` |
| 1.9.7 | PostgreSQL | `Previous snapshot has completed successfully, streaming logical changes from last known position` |

### Fix: remove the offset, then snapshot

Set `snapshot.mode` to `initial` and use the same stop, delete offsets and resume sequence as in cause 1. PostgreSQL has no schema history topic to delete. On both databases the topic went from 1 event to 6: the 5 rows were read as `op=r`.

On Kafka Connect 3.2.0 we registered the configuration under a new connector name, with the same result. On PostgreSQL the new connector also got a new `slot.name`, and the old replication slot was dropped afterwards so that it stops holding write-ahead log (WAL) on the server.

### The old value on a new version

Debezium 3.7.1 refused the old names when the configuration was validated:

```text
The 'snapshot.mode' value is invalid: Value must be one of always, initial_only, configuration_based, when_needed, initial, custom, no_data, recovery
```

That was the MySQL connector with `schema_only`. The PostgreSQL connector answered the same way for `never`, without `recovery` in the list. The 3.7 documentation still lists `schema_only` as "Deprecated, see no_data."

The reverse fails too. Debezium 1.9.7 refused `no_data` with `Value must be one of never, initial_only, when_needed, initial, schema_only, schema_only_recovery`.

## Cause 3: the topics are never created

Two things can create a change topic: the broker, when `auto.create.topics.enable` is `true`, and Kafka Connect, when the connector carries `topic.creation.default.*` settings. The [Debezium documentation](https://debezium.io/documentation/reference/stable/configuration/topic-auto-create-config.html) puts the second one this way: "Kafka Connect automatic topic creation requires the replication.factor and partitions properties to be set for at least the default topic creation group."

The lab broker runs with `auto.create.topics.enable=false`. A connector without the two settings stayed `RUNNING` with a `RUNNING` task, and the producer inside the task kept logging a warning for the first topic it needed. On Kafka Connect 4.3.1 and on 3.2.0:

```text
WARN   ||  [Producer clientId=connector-producer-my-topics-0] The metadata response from the cluster reported a recoverable issue with correlation id 35 : {myt=UNKNOWN_TOPIC_OR_PARTITION}   [org.apache.kafka.clients.NetworkClient]
WARN   ||  [Producer clientId=connector-producer-my-topics-0] Error while fetching metadata with correlation id 734 : {myt=UNKNOWN_TOPIC_OR_PARTITION}   [org.apache.kafka.clients.NetworkClient]
```

Kafka Connect 4.3.1 wrote 33 of these lines in 30 seconds, and 3.2.0 wrote 733 in 75 seconds. No topic of the connector's prefix existed, the schema history topic did, and the task never failed.

### Fix 1: let Kafka Connect create the topics

Add the two required settings to the connector. Use the replication factor your cluster can satisfy; the lab has one broker.

```json
{
  "topic.creation.default.replication.factor": "1",
  "topic.creation.default.partitions": "1"
}
```

The task restarted, Kafka Connect logged `Created topic (name=myt.inventory.customers, numPartitions=1, replicationFactor=1, ...)`, and the snapshot arrived on both versions: 7 events for one table and 5 for the other.

This needs `topic.creation.enable` to be `true` on the worker, which is the default. With the worker set to `false`, a connector that carried both settings logged the same warning and wrote nothing, on both versions. No log line said the settings were being ignored.

### Fix 2: create the topics yourself

On a cluster where you may not change the connector or the worker, create each topic by hand. The connector does not need a restart.

```bash
kafka-topics.sh --bootstrap-server kafka:9092 --create --topic pgt.public.customers --partitions 1 --replication-factor 1
```

In the PostgreSQL run both table topics filled after they were created, with 6 and 5 events, on both versions. Turning `auto.create.topics.enable` on at the broker is the third way; the lab did not run it.

## Cause 4: the PostgreSQL publication does not contain the table

With the `pgoutput` plug-in PostgreSQL sends only the changes of tables that are in the connector's publication. The [Debezium documentation](https://debezium.io/documentation/reference/stable/connectors/postgresql.html#postgresql-property-publication-name) says: "If the publication already exists, either for all tables or configured with a subset of tables, Debezium uses the publication as it is defined."

In the run a publication for `public.orders` alone existed before the connector was registered with `table.include.list=public.customers,public.orders`. The snapshot read both tables, because a snapshot does not go through the publication. After one insert into each table, the `orders` topic had the new event and the `customers` topic did not:

```text
pgp_pub|public|orders
```

That is the whole output of the `pg_publication_tables` query: one table. The connector logged nothing about it, on either version.

### Fix 1: add the table to the publication

```sql
ALTER PUBLICATION pgp_pub ADD TABLE public.customers;
```

The next insert into `customers` arrived without a connector restart, on both versions. The row inserted before the statement never did: the table held 8 rows and the topic held 7 events.

### Fix 2: let Debezium maintain the publication

With `publication.autocreate.mode=filtered`, Debezium 3.7.1 changed the existing publication to match its include list when it started:

```text
INFO   Postgres||postgres-connector-task  Publication 'pgq_pub' has to be updated. Tables to add: [public.customers], Tables to remove: []   [io.debezium.connector.postgresql.connection.PostgresReplicationConnection]
INFO   Postgres||postgres-connector-task  Updating Publication with statement 'ALTER PUBLICATION pgq_pub SET TABLE "public"."customers", "public"."orders";'   [io.debezium.connector.postgresql.connection.PostgresReplicationConnection]
```

Both tables were in the publication afterwards and the next `customers` insert arrived.

Debezium 1.9.7 did not do this. With the same setting it left the existing publication as it was, with `orders` only, and the `customers` insert did not arrive. The release notes list the change, "Postgres existing publication is not updated with the new table" (DBZ-3921), under [1.9.8.Final](https://debezium.io/releases/1.9/release-notes) and [2.0.0.Alpha2](https://debezium.io/releases/2.0/release-notes).

## Cause 5: RUNNING with no task

Here the status shows a `RUNNING` connector and an empty task list:

```json
{
  "name": "my-notask",
  "connector": { "state": "RUNNING", "worker_id": "172.31.0.5:8083", "version": "3.7.1.Final" },
  "tasks": [],
  "type": "source"
}
```

### tasks.max above 1 on the MySQL connector

The documentation for [`tasks.max`](https://debezium.io/documentation/reference/stable/connectors/mysql.html#mysql-property-tasks-max) says that "changing the default value has no effect". In the run, `tasks.max=2` left the MySQL connector without a task on both versions, and the worker repeated these two lines:

```text
ERROR  ||  [Worker clientId=connect-172.31.0.5:8083, groupId=lab-connect] Failed to reconfigure connector's tasks (my-notask), retrying after backoff.   [org.apache.kafka.connect.runtime.distributed.DistributedHerder]
java.lang.IllegalArgumentException: Only a single connector task may be started
```

On Kafka Connect 3.2.0 the first line ends with a colon and is otherwise the same. The exception comes from the connector itself ([source](https://github.com/debezium/debezium/blob/v3.7.1.Final/debezium-connector-binlog/src/main/java/io/debezium/connector/binlog/BinlogConnector.java)).

Setting `tasks.max` back to `1` gave the connector its task, and the snapshot arrived. The PostgreSQL connector with `tasks.max=2` started one task and worked.

### Two workers that advertise the same address

This run was made on Debezium 3.7.1 only. Two workers in one group both advertised `localhost` as their REST address, which is what a container does when its advertised host name is left at a local value. A connector that landed on the worker that was not the group leader got no task:

```text
ERROR  ||  [Worker clientId=connect-localhost:8083, groupId=lab-connect-pair] Request to leader to reconfigure connector tasks failed   [org.apache.kafka.connect.runtime.distributed.DistributedHerder]
org.apache.kafka.connect.runtime.rest.errors.ConnectRestException: Internal request missing required signature
ERROR  ||  [Worker clientId=connect-localhost:8083, groupId=lab-connect-pair] Failed to reconfigure connector's tasks (pg-second), retrying after backoff.   [org.apache.kafka.connect.runtime.distributed.DistributedHerder]
```

The status gives it away before the log does: every `worker_id` reads `localhost:8083`. The fix was to give each worker an address the other one resolves, through `rest.advertised.host.name` in the worker file or `ADVERTISED_HOST_NAME` on the Debezium image. After both workers restarted, the task appeared and the snapshot arrived.

## Prevent it

- After registering a connector, check the topics and not only the state. A snapshot of a non-empty table should put events on its topic within minutes.
- Alert on the three log lines: `no changes will be captured`, `UNKNOWN_TOPIC_OR_PARTITION` and `Failed to reconfigure connector's tasks`.
- Write `table.include.list` as full names with escaped dots, for example `inventory\.customers`, and keep one list per connector in version control.
- Put `topic.creation.default.replication.factor` and `topic.creation.default.partitions` in every source connector. They work whether or not the broker creates topics.
- On PostgreSQL, decide who owns the publication. Either create it for the exact tables and check `pg_publication_tables` after every change to the include list, or use `publication.autocreate.mode=filtered` on Debezium 2.0 or later.
- Leave `tasks.max` at `1` for the MySQL and PostgreSQL connectors.

:::note[How OLake Go handles this]

OLake Go does not run on Kafka Connect, so causes 3 and 5 have no counterpart in it. Tables are chosen as named streams, in a file that its `discover` step writes first ([streams configuration](/docs/core/configs/streams-migration/)).

Cause 4 applies to it in the same way. Its PostgreSQL connector reads through a publication that you create, and the [connector documentation](/docs/connectors/postgres/#configuration) requires that it "include all tables for CDC capture", where CDC is change data capture. Its connection test checks that the publication exists and includes the required tables.

:::
