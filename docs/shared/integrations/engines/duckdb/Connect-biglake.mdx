DuckDB attaches BigLake as an Iceberg REST catalog with a Google access token. The catalog on this page is in end-user credential mode, so DuckDB also needs its own Cloud Storage credentials to read the files: an HMAC key for the service account (Cloud Storage, **Settings**, **Interoperability**, **Create a key for a service account**).

<CodeBlock language="sql" title="DuckDB 1.5.5">{`INSTALL iceberg; LOAD iceberg;
INSTALL httpfs;  LOAD httpfs;

-- gcloud auth print-access-token, or a token minted for the service account
CREATE SECRET biglake_catalog (
  TYPE iceberg,
  TOKEN '<access token>',
  EXTRA_HTTP_HEADERS MAP {'x-goog-user-project': '<project-id>'}
);
-- the HMAC key pair for the bucket
CREATE SECRET biglake_files (TYPE gcs, KEY_ID '<hmac access id>', SECRET '<hmac secret>');

ATTACH 'gs://<bucket>' AS biglake (
  TYPE iceberg,
  ENDPOINT 'https://biglake.googleapis.com/iceberg/v1/restcatalog',
  SECRET biglake_catalog
);

SHOW ALL TABLES;
SELECT id, name, city, tier FROM biglake.${props.schema ?? 'postgres_to_bigquery_shop_public'}.customers ORDER BY id;`}</CodeBlock>

The access token lives an hour; `CREATE OR REPLACE SECRET` with a fresh one when a query fails with `401`. If the catalog is in vended-credentials mode instead, drop the `gcs` secret and add `ACCESS_DELEGATION_MODE 'vended_credentials'` to the `ATTACH`: BigLake then hands DuckDB a short-lived storage token per table. DuckDB reads positional deletes, so the rows match BigQuery after every sync.
