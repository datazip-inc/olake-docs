There is no registration step and no external table to declare. A BigLake catalog is a BigQuery data source in the same project: the catalog is the bucket name, the namespace OLake Go created is the dataset, and the tables are the tables. Address them with the four-part name in backticks, and run the query in the bucket's region.

<CodeBlock language="sql" title="BigQuery SQL editor (location: the bucket region)">{`SELECT ${props.idCol ?? 'id'}, name, city, tier
FROM \`<project-id>.<bucket>.${props.schema ?? 'postgres_to_bigquery_shop_public'}.customers\`
ORDER BY ${props.idCol ?? 'id'};

SELECT status, count(*) AS n, ${props.amount ?? 'round(sum(amount), 2)'} AS total
FROM \`<project-id>.<bucket>.${props.schema ?? 'postgres_to_bigquery_shop_public'}.orders\`
GROUP BY status ORDER BY status;`}</CodeBlock>

From a terminal, `bq query --project_id=<project-id> --location=<region> --use_legacy_sql=false "<sql>"` runs the same statements. Set the location to the bucket's region (`us-central1` on this page); the default `US` multi-region returns `Not found: Dataset` for a catalog whose bucket is regional.

OLake Go adds four columns to every table: `_olake_id` (a hash of the primary key), `_op_type`, `_olake_timestamp` and `_cdc_timestamp`. `_op_type` is `r` for a row from the first snapshot, `c` for an insert, `u` for an update and `d` for a delete. Filter them out of dashboards, or use them to see when a row last changed.

BigQuery reads Iceberg v2 tables with positional and equality deletes, which is why the job on this page uses positional deletes. Deletion vectors on v3 tables are a preview feature in BigQuery with per-query limits, so keep the job off deletion vectors while BigQuery is a reader.
