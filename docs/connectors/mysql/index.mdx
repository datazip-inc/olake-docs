# Overview {/* #overview */}

In addition to MySQL, OLake Go also supports MariaDB flavor as CDC source. It supports multiple sync modes and offers features like parallel chunking, checkpointing, and automatic resume for failed full loads. This connector can be used within the OLake UI or run locally via Docker for open-source workflows.

## Sync Modes Supported

- **Full Refresh**
- **Full Refresh + CDC**
- **CDC Only**
- **Full Refresh + Incremental**

## Prerequisites

    ### Version Prerequisites
        MySQL Version: MySQL 5.7+
    ### CDC Prerequisite

    - [Binary Logging](/blog/binlogs) (Required):
      - log_bin=ON
      - binlog_format=ROW
      - binlog_row_image=FULL
      - binlog_row_metadata=FULL
      - Optional (enables microsecond precision for `_cdc_timestamp` column generated by OLake Go, by default it is seconds-precision timestamp):
        - enforce_gtid_consistency=ON (must be set before `gtid_mode`)
        - gtid_mode=ON

        :::info[Requirement]
        MySQL 8.0.1 or higher for microsecond-precision timestamp support
        :::

    - Server Config: Set unique server-id.
    - Access & Permissions: REPLICATION SLAVE, REPLICATION CLIENT, and SELECT privileges.

    - For detailed setup for different MySQL environments, see the guides in the section below.
        - [Aurora MySQL – CDC Setup Guide](/docs/connectors/mysql/setup/aurora)
        - [Amazon RDS MySQL – CDC Setup Guide](/docs/connectors/mysql/setup/rds)
        - [MySQL via Docker Compose – Local Setup](/docs/connectors/mysql/setup/local)
        - [Azure Database for MySQL – CDC Setup Guide](/docs/connectors/mysql/setup/azure)
        - [Google Cloud SQL for MySQL – CDC Setup Guide](/docs/connectors/mysql/setup/gcp)
        - [Generic MySQL – CDC Setup Guide](/docs/connectors/mysql/setup/generic)

### Connection Prerequisites

- Read access to the tables for the MySQL user.

**After initial Prerequisites are fulfilled, the configurations for MySQL can be configured.**

### 3. Test Connection

- Click **Set up source** to validate the configuration. The test performs three checks:

  <Figure src='/img/docs/sources/mysql/mysql-test-conn.webp' alt='Testing Source Configuration modal showing connection success, required MySQL CDC prerequisite checks, and optional CDC settings' />

  1. **Connection validation**: Verifies that OLake Go can reach the MySQL server using the provided host, port, credentials, and SSL settings.

  2. **Required CDC prerequisites validation** (when CDC is enabled): Evaluates required server-side settings to ensure reliable CDC operation:
     - `binlog_access`: User must have binlog read privileges
     - `log_bin`: Binary logging must be enabled
     - `binlog_format`: Must be set to `ROW`
     - `binlog_row_image`: Must be set to `FULL`

  3. **Optional CDC prerequisites validation** (when CDC is enabled): Evaluates optional server-side settings:
     - `binlog_row_metadata`: Binlog row metadata should be set to `FULL`
     - `binlog_retention`: Binlog retention must be sufficient for expected sync pauses

- If any required check fails, the test connection will show the current and recommended values. Fix the server-side settings and retry the connection.

- If any optional check fails, the test connection will show the current and recommended values. You can fix the server-side settings and retry, or continue and create the source without making changes.

- If all checks pass, the MySQL source is created successfully. Jobs can then be configured using this source.

- In case of connection failure, refer to the [Troubleshooting section](#troubleshooting).

### 3. Check Source Connection

To verify the database connection following command needs to be run:

```bash title="check command"
docker run --pull=always \
-v "[PATH_OF_CONFIG_FOLDER]:/mnt/config" \
olakego/source-mysql:latest \
check \
--config /mnt/config/source.json
```

- The `check` command runs three validations:

  1. **Connection validation**: Verifies that OLake Go can reach the MySQL server using the settings in `source.json` (host, port, credentials, and SSL settings).

  2. **Required CDC prerequisites validation** (when CDC is configured via `update_method`): Evaluates required server-side settings to ensure reliable CDC operation:
     - `binlog_access`: User must have binlog read privileges
     - `log_bin`: Binary logging must be enabled

     - `binlog_row_image`: Must be set to `FULL`

  3. **Optional CDC prerequisites validation** (when CDC is configured via `update_method`): Evaluates optional server-side settings:
     - `binlog_row_metadata`: Binlog row metadata should be set to `FULL`

## Troubleshooting {/* #troubleshooting */}

### 1. Failed to Get Current Binlog Position

    **Cause**: Binary logging not enabled, wrong format, or insufficient privileges. <br/>
    **Fix**:
    - Ensure binary logging is enabled:
    ```sql
    SHOW VARIABLES LIKE 'log_bin'; // Should return `ON`
    ```
     - Ensure row-based logging:

```sql
SHOW VARIABLES LIKE 'binlog_format'; // Should return `ROW`.
```

- Grant required privileges:

```sql
GRANT REPLICATION CLIENT, REPLICATION SLAVE ON *.* TO 'your_user'@'%';
```

### 2. Idle Timeout Reached, Exiting Binlog Syncer

- **Cause**: During CDC sync, OLake Go saves the binlog position as state. When the next CDC sync starts, OLake Go searches for this saved position in MySQL's binlog to resume from where it left off. If this search operation takes longer than the configured `initial_wait_time` (for example, if `initial_wait_time` is set to 10 seconds but searching the binlog takes 15 seconds), the timeout is triggered and the binlog syncer exits.
- **Fix**: Increase the `initial_wait_time` value in your source configuration to allow sufficient time for OLake Go to locate the saved binlog position. 

### 3. Column Count Mismatch: Expected X, Got Y

- **Cause**: Table schema changed after CDC started or incomplete binlog metadata.
- **Fix**:
  - Ensure full binlog metadata:
  ```sql
  SHOW VARIABLES LIKE 'binlog_row_metadata';
  ```
  Should return `FULL`. To set it:
  ```sql
  SET GLOBAL binlog_row_metadata = 'FULL';
  ```
  Update `my.cnf` or `my.ini` for persistence.
  - Restart the connector after schema changes.

### 4. Failed to Get or Split Chunks

- **Cause**: Table stats not populated or table contains 0 records.
- **Fix**: Run the following query to populate table statistics:

  ```sql
  ANALYZE TABLE <namespace>.<table_name>;
  ```

### 5. Failed to Load MySQL Timezone Location

- **Cause**: If you see the log message `failed to load mysql timezone location %s, falling back to UTC. Set jdbc_url_params.time_zone to override: %s`, it indicates that the MySQL timezone could not be loaded properly. This often occurs when timezone abbreviations (like **'IST'**) are used, which can lead to inconsistencies since multiple regions share the same short name (e.g., India, Israel, Ireland).
- **Fix**:
  - First, check the current timezone settings:
    ```sql
    SELECT @@session.time_zone, @@global.time_zone, @@system_time_zone;
    ```
    If any of these returns **IST** or another abbreviation, this can cause inconsistency issues.

  - **Option 1 (Set via JDBC using IANA timezone name)**:
    - Use IANA timezone names (e.g., `Asia/Kolkata`) instead of abbreviations. Set this in the JDBC URL parameters:
      ```json
      {
        "jdbc_url_params": {
          "time_zone": "Asia/Kolkata"
        }
      }
      ```
    - Verify that IANA timezones are available in your database:
      ```sql
      SELECT count(*) FROM mysql.time_zone_name;
      ```
      If this returns `0`, the timezone tables are not present. In this case you should use Option 2 instead.

  - **Option 2 (Use timezone offset)**:
    - If IANA timezone names are not available in your environment, use a fixed offset instead:
      ```json
      {
        "jdbc_url_params": {
          "time_zone": "+05:30"
        }
      }
      ```

**If the issue is not listed here, post the query on Slack to get it resolved within a few hours.**
